# R6 · 文件角色与扫描范围 —— 要加的字段清单（交总工落 `Models/**`）

> 冻结区规矩（AGENTS §3 / §8）：`Models/**` 由总工落。本文件是**申请单**，不是实现。
> WS-R6（RD-14~17）本轮已把不依赖新字段的部分做完：判据纯函数 + 分档累计 + 边界句上屏。
> 现在这些读数以**文本**形式经 `CodeMetrics.scanLimitations`（既有字段）落盘与上屏，
> 有两个读者（界面 `CodeMetricsView` 的扫描边界 ⓘ、CLI `score` 的「未量准」段），不阻塞交付。
> 下表要的是：把这些数从"句子"升级成"可展示、可评分、可对账的读数"。

## 1. 三条通用约束（每条字段都适用）

1. **一律 Optional、一律 `encodeIfPresent`**：非 Optional 带默认值会让 `db7d85c` 之前落盘的报告
   整份解码失败（AGENTS §5.9 第 2 条，本仓踩过）。
2. **"没量到"与"量到 0"必须是两个值**：键缺席 = 没量到（界面 `EmptyStateView`，写「本次未做角色分档」）；
   键在但计数为 0 = 量过了、真的是 0。**任何一格都不许把缺席渲染成 0 或"没有"**。
3. **写者与读者同批落地**（R10 第 0.6 条的教训）：字段不许只有界面读；`score` 文本或 JSON 至少要
   有第二个读者。每条字段下面都点名了读者。

## 2. 角色分档（RD-14）

新增类型（放 `Models/CodeMetrics.swift`，与 `LanguageShare` 同一形状）：

```swift
/// 一个文件角色的分档读数。`role` 用 `SourceFileRole.rawValue`（英文小写，稳定坐标）。
struct CodeFileRoleShare: Codable, Equatable, Sendable {
    var role: String
    var fileCount: Int
    var codeLines: Int
    var totalLines: Int
    /// 仅 `production` 档有意义：其中"只有语言证据、路径无角色线索"的弱判定文件数。
    var weakEvidenceFiles: Int?
    /// 可点名样本（≤6 条相对路径）。只有总数的分档不许上屏。
    var samplePaths: [String]?
}

struct CodeFileRoles: Codable, Equatable, Sendable {
    /// 八个档**全量列出**（含 0）：缺档 = 没量到，而不是"该档为 0"。
    var shares: [CodeFileRoleShare]
    /// 判据分布（`SourceRoleCriterion.rawValue` → 命中次数），回答"生成码是靠什么认出来的"。
    var criterionCounts: [String: Int]?
    /// 参与分档的文件数；与 `CodeMetrics.totalFiles` 不等 ⇒ 有文件没归到任何档（判据漏了）。
    var attributedFileCount: Int?
}
```

| 字段 | 类型 | 谁写 | 谁读 | 量不到时上屏打什么 |
|---|---|---|---|---|
| `CodeMetrics.fileRoles` | `CodeFileRoles?` | `FileSystemCodeAnalyzer.apply`（取 `SourceRoleTally(of: scan.files)`，判据在 `SourceFileRoleRules.decide`） | ① `Views/Code/CodeMetricsView` 新增「文件角色」分组表；② `HealthCodeDimensions` 用 `production.codeLines` 当分母，让构建产物/文档**不恶化生产码分**（工单原话）；③ CLI `scan` JSON；④ `report_parity.py` 对表 | 整键缺席 → `EmptyStateView("本次未做角色分档")`；某档缺席 → `--` |

**为什么不放别处**：角色是"这一份 codeLines 是在什么范围内量出来的"这件事的一部分，
放在 `CodeMetrics` 里才能与 `totalLines`/`codeLines` 同快照；放 `CodeScanCoverage` 就停在内存里
（那个类型不落盘，正是 `scanLimitations` 出现之前的老问题）。

## 3. 扫描范围与"跟不跟"（RD-15，§6 统一形状）

```swift
/// 一次扫描的范围读数。形状与 §6.1 一字对齐（totalCount / displayedCount / undisplayedCount / unmeasuredScope）。
struct CodeScanScope: Codable, Equatable, Sendable {
    var totalCount: Int?              // 遍历看到的条目数
    var displayedCount: Int?          // 逐条留了路径样本的条目数
    var undisplayedCount: Int?        // max(0, total - displayed)
    var unmeasuredScope: [String]?    // 没量到的范围，一行一条（带计数）
    var excludedLineCount: Int?       // 被剔除条目的行数；缺席 = 非审计模式没读过内容
    var linesCounted: Bool?           // 上一格到底数没数；false 时 `excludedLineCount` 必须为 nil
    var nestedRepositoryCount: Int?   // 根之下又出现的仓库标记数（算进本仓，不另算）
    var submoduleMarkerCount: Int?    // 其中 `.git` 是文件形状的
    var symbolicLinkFileCount: Int?
    var symbolicLinkDirectoryCount: Int?
    /// 名单外、被系统 bundle 判定剪掉的目录数（`*.xcarchive` 这类）。修前恒为"不知道"。
    var unlistedPrunedDirectoryCount: Int?
}
```

| 字段 | 谁写 | 谁读 | 量不到时上屏打什么 |
|---|---|---|---|
| `CodeMetrics.scanSurface` | `FileSystemCodeAnalyzer.coverage(from:duplication:options:lex:)` → `SourceScanScopeReadout` + `SourceTreeFollowingLedger` | ① `CodeMetricsView` 的「扫描范围」格（现在只有 ⓘ 里的句子）；② CLI `score` 的「未量准」段；③ 任何写「这个项目没有测试码」这类句子前的闸门（`blocksAbsenceClaims`） | `totalCount == nil` → 「本次没有范围台账」，**不许**显示「排除了 0 个」；`excludedLineCount == nil` → 「行数未统计」 |

硬判据（已落 `SourceScanScopeTests` 三条）：`.measured(0)` 与 `.notCounted(reason)` 渲染出的中文
永远不同；`unmeasuredScope` 非空 ⇒ 缺席型结论句子不成立。

## 4. 重复榜单口径（RD-17，不动任何阈值）

```swift
struct CodeDuplicateBoard: Codable, Equatable, Sendable {
    /// 重复率分子用的口径，写死成枚举而不是让读者猜：`DuplicationEngine.analyze` 用全量命中并集。
    var ratioCaliber: String?            // "allHits" | "boardOnly"
    var listedBlockLineCount: Int?       // 榜内各块行数之和（与 `duplicatedCodeLines` 不同尺）
    var droppedBlockCount: Int?          // 已有同名量在 coverage 里，落盘这一格才到得了界面
    var linesOutsideReportedBlocks: Int?
    /// 榜外块的稳定坐标（`DuplicatedBlock.id`），≤6 条。工单原话：不许只留一个总数。
    var outsideBoardCoordinates: [String]?
}
```

| 字段 | 谁写 | 谁读 | 量不到时上屏打什么 |
|---|---|---|---|
| `CodeMetrics.duplicateBoard` | `FileSystemCodeAnalyzer.apply`（`DuplicationResult.boardCaliberNote` 同源） | ① `Views/Code/CodeMetricsSections` 的「重复代码率」格 `captionHelp`；② `CodeRiskAdvice` 那句"压到 X% 以下"必须按 `ratioCaliber` 说话；③ CLI JSON | `ratioCaliber == nil` → 「重复率口径未记录」，格子照常显示百分比但**不许**配"没有重复块"这类句子 |

**明确不做**：`maxBlocks = 20`、`windowSize = 6`、`minNormalizedBytes = 4`、判档门限
全部保持原值，并有 `XCTAssertEqual(DuplicationEngine.maxBlocks, 20)` 当钉子。

## 5. 与别的流的接缝

- **R7（榜单口径）**：`fileRoles` 里的 `weakEvidenceFiles` 与 §6.1 的 `undisplayedCount` 同一族判据；
  如果 R7 那侧先落了共享的 `totalCount/displayedCount/...` 外层形状，我这三条直接挂进去，
  不另立第二套字段名。
- **R10（报告追溯）**：`nestedRepositoryCount` / `submoduleMarkerCount` 是"扫描范围算谁"的证据；
  溯源块若要以 git 身份划范围（`git ls-files`），本流的 `scanSurface` 就是它的对照读数 ——
  **两边都要在**，否则"按 git 划范围"与"按目录遍历划范围"各说一句话。
- **R2（Vue/RD-20 注释率）**：注释率分母按角色收窄时要读 `fileRoles.shares[.documentation].codeLines`；
  本轮没动分母，只在 `scanLimitations` 里明说"文档/生成物仍在分母里"。
