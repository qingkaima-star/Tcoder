### 根因与探针原始读数（同一棵树，只差这一档判定）

`curlyEnd` 允许"签名命中后向后最多 8 行借一个 `{`"当函数体，而它此前只挡一种借法：
后面那行**本身是一条新签名**。无花括号的箭头体因此把紧随其后的对象字面量 / `if` 块整段认作己有：

| 夹具 | 修前实读 | 修后实读 |
|---|---|---|
| `const add = (a, b) => a + b` + `const config = {…}` | `add@1+4 cc1`（假函数） | 无条目 |
| 同上 + 对象里带 `onSave() { if … }` | `add@1+9`＝整个文件，且 `onSave` **不再被扫到** | 只有 `.onSave@3+6 cc2` |
| `export const labelOf = (items) => items` 换行点号链 | 计入「边界推不出来」，无条目 | `labelOf@1+3`、参数 1、CC 1 |
| `const verdict = (score) => score > 90` 换行三元 | 同上，无条目 | `verdict@1+3`（CC 仍 1 ⇒ 见本节末 RD-80） |
| `export const pointOf = (raw) => ({…})` | `pointOf@1+4`（本来就靠花括号计数蒙对） | 一字未变 |

假条目与漏报**同源**（扫描线 `cursor = endLine + 1` 一步跨过被吃掉的区间），
所以这一笔同时属于第一批「消除误报」与「补齐漏报」。

### 落地形状

- `ComplexityEngine.statementEnd`：定界符配平 + 行尾算符 + 下一行开头算符三条一起判「本条说完」，
  窗口 `maxStatementLookahead` = 16 行，收不了尾一律不判（交回「边界推不出来」那句出声）。
  顺序是判据：**后面没有内容行了** 必须先看，否则收尾于 `:` 的跨行三元会在文件末尾判成「没说完」而整条不认。
- `curlyEnd` 拿它作硬上界（越过语句收尾的 `{` 属于下一条语句）；行尾 `;` 一律判说完 ⇒ 顺带管住 C 系原型声明。

  签名段取第一个 `=>` 所在行，参数计数不被体内的括号污染。
