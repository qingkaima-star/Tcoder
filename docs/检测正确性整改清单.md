> 用户 2026-09-22 交来一份整改意见，定调是：
> **「让 Tcoder 测得准确、解释准确、建议可执行」**，
> 并明确否掉三类完成标准 —— 自评分数变高、函数复杂度全部低于某阈值、文件行数全部低于某行数。
> 本文件是这一轮的**唯一台账**：条目只改状态、不删除，

>
> 整改的完成标准（用户原话）：
> **已确认误报被消除，已确认漏报被补齐，未知和缺证据被诚实表达；

## 0. 口径（什么算违反，怎么算修完）

| 档 | 判据 | 为什么算缺陷 |
|---|---|---|
| **X1 误报** | 报出来的东西在被扫对象里并不存在（伪函数、伪重复、伪扣分） | 用户按它改代码，改的是不存在的问题 |
| **X2 漏报** | 真实存在的结构没被识别，于是"没有发现"被长成"没有问题" | 比误报更安静：全绿本身就是假安心 |
| **X3 未知冒充结论** | 没测到 / 没核对 / 解析失败，渲染成 0、满分、"安全"、"无风险" | 本仓既有红线（[[评分诚实三态原则]]） |
| **X4 口径混用** | 榜单条数当真实总数、榜尾值当整改目标、声明范围当安装版本、尝试查询当核对成功 | 数字是真的，话是错的 |
| **X5 建议与对象不符** | 给 Java 推荐 Swift extension、给 lock 文件推荐抽公共基类 | 建议不可执行，等于噪声 |
| **X6 证据链断裂** | 查询身份与回填身份不一致、报告与源码无绑定 | 总览说有公告而依赖行没标记，两边都对不上账 |

**修完的定义**（每条都必须凑齐四件，缺一不算修完）：
① 复现夹具（本仓或 `.scratch/` 之内，**禁止**用本机其它项目当夹具）+ 独立真值；
② 正例 / 反例 / 未知态 / 失败态四种结果；
③ CLI 与 GUI 对表（`scripts/report_parity.py`）；
④ 新守卫要 sabotage 一次证明它有牙（[[扫描型测试要配元测试]]）。

## 3. 批次与并行编排（用户 §十一 的落地形状）

三条链路各自**统一契约**，不许不同人分头改同一链路后各自宣布完成：

| 链路 | 唯一契约持有 | 覆盖条目 |

| 依赖模型 → 查询 → 回填 → 行状态 → 总览 → 评分 | R3（一棵树内做完，禁止拆给两家） | RD-10~13 |

| 文件角色 → 扫描范围 → 重复候选 → 建议 | R4 | RD-14~17 |

**并行度**（AGENTS §7）：同时活跃对话 ≤3、每对话子代理 ≤3、每家同一时刻只跑 1 个编译。
第一批只开 R1 / R2 / R3 三棵工作树；第二批在第一批合入后排。
