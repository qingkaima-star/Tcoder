## 2026-09-24 补三条：类别不猜、点名按路径、以及"全量日志里没有读数"这件事本身

**1）覆盖率报告的"单元 / 集成"两格：没有标注就是没有标注，不猜。**
`CoverageAnalyzer.classify` 只看**被扫根之内**的相对路径里有没有 `unit` / `integration` / `e2e` 这类目录段；
切不出来或路径里没有这些段 ⇒ 一律 `.combined`。这不是"覆盖率低"，是**这一类没被标注**。
为什么宁可不猜：旧实现拿**绝对路径**做子串匹配，于是临时目录里那串随机十六进制名（含 `e2e` 的概率约 0.7%）
能把整棵夹具改判成"集成测试"——同一份夹具两次跑出两个数（这条案在整改台账里叫 RD-39，已结案，
守卫是 `testAmbientDirectoryNamesNeverLeakIntoKindOrNumbers`）。
⚠️ 已知未完项：**总览页那两格目前把"未标注"渲染成「无报告」**，读的人会得出"这个项目没跑单测"。
整改条目 RD-62（要补的是三态：有该类报告 / 有别的报告但没标注 / 一份都没有），修好之前请把那句话读成
"这一类没被标注"而不是"没有"。

**2）任何"举几条样本 / 点名清单"的读数按相对路径给，不按到达顺序。**
并发扫描下到达顺序是调度的产物。本仓为这件事立过两次案：RD-54（跳过台账的命中样本）、
RD-63（文件角色分档的点名样本，GUI 与 CLI 各点一枚、方向还会反过来）。
判据形状也随之写死：**要证明一个读数是确定性的，必须喂两种相反的顺序并要求同一结果**；
"重跑几次都一样"不构成证明（本仓 `testDigestIgnoresEnumerationOrder`、
`testExamplesAreChosenByPathNotByEncounterOrder` 就是这个形状）。
`SourceRoleTally`、`CoverageDisplayShape` 这类装配口都按路径升序取样。

**3）跑全量测试时，有一部分守卫的"现量/上限"读数不会出现在日志里（RD-64，机制未定位）。**
实测：`ConflictMarkerGuardTests`、`BoardLengthReadoutRatchetTests`、`EvidenceFreshnessTests` 三类
在全量跑里**执行并通过**，但它们 `print` 的读数在两份独立的全量日志里命中 0；同一批 `print` 在
`--filter` 单跑那趟打得出来。⇒ 所以：
- **「全量 N 例 / 0 失败」这句话不带测量证据**，它只说明没有断言失败；
- 要引用任何"现量/上限/扫了多少"的读数，**必须来自过滤跑那趟的原始输出**，并把原文抄进账；
- 新写这类判据时**别只 `print`**：把读数同时落成仓库内文件账（先例是双语台账与
  `.scratch/tcoder-caliber-visible-inventory.txt`），**落不进文件就等于没测**。

## 2026-09-24 午后补一条（RD-66）：文档里的**裸用例名**从这一天起算锚

写文档的人一直在两种形状之间踩空：点号锚（`类型.成员` 那种）有棘轮逐条判活，
而裸写一枚用例名（反引号包住、不带点号）**压根不成锚** —— 判活的索引里其实早有
`Tests/**` 的声明名，缺的只是让裸名被扫出来的那条提取规则。

现场证据（不是假设）：`cd4f3a3`（09-24 11:49）在「要证明一个读数是确定性的」那一段里
引了 `testDigestIgnoresEnumerationOrder`，而这枚用例当时只在**未合并的**
`ws/rd31-scandrift`（`a50c9e7`，10:56）上，main 要到 `f367c73`（12:41）才有它。
中间约 52 分钟里 main 挂着一句指向不存在之物的引用，而 12:13 那趟全量兜底
（`40f9446`，Executed 1745 tests, with 13 tests skipped and 0 failures）**全绿**。

现在的口径（判据与点号锚**并列、不并桶**，读数和上限同时落文件台账）：

- 反引号整段、形如 `test` 紧跟大写字母或下划线、整名不少于 9 个字符 ⇒ 必须是
  `Tests/**` 或 `Sources/**` **声明位**上的名字，找不到就判红；
- 门槛 9 由本仓最短的真实用例名自证（现量 9）：门槛一旦高过它就当场红，
  所以它不可能是「把短名字藏起来」的免检通道；
- 散文里的 test / tests / testing、没进反引号的名字、以及点号锚，一律不被这一类碰；
- 死名上限 0 条，且这一类的死引用**不许**塞进那条必须为空的 knownDeadAnchors 基线。

**没做到的两件事**（低等级结论按低等级写，别读成已封）：

1. 这一类的声明索引只剥整行注释，**不剥字符串字面量**，也不区分存储属性与函数体内的
   局部绑定 ⇒ 一个只被写在测试夹具字符串里的假用例名，仍可能被读成「有声明」而判活。
   本仓对此有一道点名核对（金丝雀必须真的不在索引里），但根上没封死 ——
   真要封住得解析 Swift 语法，那是另一个量级的活儿（与点号锚的「抓不到成员被挪去
   另一个类型」是同一条限度）。
2. 这一类只回答「这个名字在不在声明位」，**不回答这枚裸名指的是用例还是字段**。
   文档里 `testIdentifiers` 指的是 CodeIndex 的那个属性，它判活是因为它真在声明位上；
   如果哪天有人拿反引号包一枚恰好与某个局部绑定同名的假用例名，它会躲过判红。

## 2026-09-24 再补两格：报告上的「扫描期间源码」，和覆盖率那两格的四种说法

**1）溯源那一行现在多了一格：`扫描期间源码有变化（…）` / `…未量到（原因）` / `开工与收工两枚源码指纹一致`。**
一份报告要五路并行跑几十秒，期间只要有人切分支、保存文件、跑格式化，落进报告的就是
**来自不同时刻**的一批读数 —— 这一格就是把这件事说出来，健康评分页顶部会挂同一条横幅。
读法上要注意三件事：

- 它与「工作区脏不脏」是**两件事**。后者答的是"开工当时"，前者答的是"这段时间里动过没有"；
  脏工作区可以自始至终没动，干净工作区也可能中途被改又被还原。
- 判"一致"用的是**元数据指纹**（文件条数 + 字节数之和 + 路径集合摘要），一次都不读文件内容 ——
  代价是**等长改写测不出来**。所以那句只说「两枚指纹一致」，**不等于「源码没变」**；
  真要一个"期间内容一字未动"的保证，这把尺子给不了。
- **没量到是一格，不是零**。两侧任意一枚没采到（根目录读不动、树里有目录没权限、
  一趟超过条数预算）就整枚判未量到，并写明是哪一侧、为什么；不会拿一枚残缺指纹去比出"一致"。

**2）总览那张覆盖率卡的「单元测试 / 集成测试」两格现在有两种沉默说法，别混着读。**
以前这两格只有「百分数」和「无报告」两种取值，于是**"没标注类别"被写成了"没有报告"**：
一个项目明明有覆盖率、总覆盖率那一格有数，两格却写「无报告」，读的人只会得出"这项目没跑单测"。
现在按「这一类有没有报告」×「整份报告里有没有任何覆盖率报告」分开说：

| 屏上 | 真意思 |
|---|---|
| `78%` | 这一类有报告，取的是它自己的行覆盖率 |
| `未标注类别` | 有报告，但报告没说自己属于单元还是集成（一份普通的 `coverage/lcov.info` 就是这一态） |
| `未产出该类报告` | 有报告、也做了标注，只是没产出这一类 |
| `无报告` | 一份覆盖率报告都没有（⚠️ 这一支在**屏上**永远走不到：那张卡只在真有报告时才画；它只在 CLI 那句里出得来，JSON 侧存的不是句子而是"这一类没有报告"这个事实本身） |

中间那一态再分成两句是有原因的：合成一句就必有一句是假话 —— 把"已经做了标注"报成"没标注"，
和把"没标注"报成"没有报告"，是同一族毛病往两个方向各错一次。


## 「历史报告 N 次在窗口外」这一支今天永远不响（已知缺陷，不是设计）

`logs.crashEvidence` 里有 `historicalConfirmedCount` 这一格，界面脚注也备好了那句话
（`CrashEvidenceReadout` 的逐态装配：`historical > 0` 才追加「历史报告 N 次在窗口外」）。
**但这一格在任何输入下都读 0**：它的判据要求"确认崩溃 ∧ 有事件时间 ∧ **不在窗口内**"，
而窗口外的 `.ips` 在**进崩溃台账之前**就被窗口裁掉了（`FileLogAnalyzer` 那句注释写着
"八种原因直传同一个台账：同一次遍历、**同一次窗口裁剪**"）。
区分性实验见台账 §135：同一棵夹具树只把 `--window-days` 从 14 改到 30，
`countedCrashCount` 从 2 变 3（那份 20 天前的报告确实算得上的当前构建确认崩溃），
而 `historicalConfirmedCount` 两个窗口下都是 0。

**读这份报告时该怎么理解这两个数**：
| 看到的 | 真意思 | **不**等于 |
|---|---|---|
| `historicalConfirmedCount = 0` | 窗口外**没有报告被读到**（读到的都落在窗口内） | 「这个项目没有窗口外的历史崩溃」 |
| 脚注里没有「历史报告 N 次在窗口外」 | 这一格是 0 ⇒ 那句话按设计不出声 | 「工具查过了，没有历史」 |
| `undatedConfirmedCount = 1` | 这一格**是活的**：没有事件时间的确认崩溃照常单列 | 与上一格同类盲区 |

⇒ 也就是说：**"窗口外"这一维今天在屏上没有任何信号**，而 JSON 里那个 `0` 长得像"查过、没有"。
这条属于「读不到不许渲染成已排除」那一族（评分诚实三态），修法与代价点（抑制集要跟着扩、
`filesWithCountedEvidence` 分母会变、`CrashEvidenceWiringTests` 钉的同刻同源不许破）
都写在台账 §135，修完之后**这一节要删掉**——留着它就意味着缺陷还在。

> ⚠️ **本节上一节里"这一格在任何输入下都读 0"这句说重了**（§137 已更正）：
> 已证的是**文件 mtime 也落在窗口外**的那一类——它在读取前就被 `LogDiscovery` 淘汰；
> "文件在窗口内、事件时间在窗口外"那一态**还没测到**（我的探针那份文件压根没被崩溃通道接管，
> 全零读数就是没接通的自证）。所以准确的说法是：
> **窗口外的历史崩溃报告，今天至少有一类形状拿不出信号（文件也老的那一类）**，
> 而这一格是否对任何形状都恒为 0，未定位。

> ⚠️ **再更正一次（§138）**：本节上方"机制"的说法要换成——
> 发现层（`LogDiscovery`）对三个来源统一按**文件 mtime** 设候选上界，这是**成文设计**并给了理由；
> 而证据层那一格承诺"窗口外的确认崩溃绝不静默丢弃"，**也是成文设计**。两者相顶，
> 结果是那一格实际只覆盖"文件新、事件旧"这一窄态，最常见的"真·历史崩溃报告"进不来。
> ⇒ 这不是漏写一个过滤，是一条**需要日志链裁决的口径冲突**（两个方向各自的代价见 §138）；
> 在它裁定之前，**读 `historicalConfirmedCount` 的人要按窄态理解**。
