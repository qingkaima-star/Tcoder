## 77. RD-53 落地：`merge_stream.sh` 会把 no-op 合并报成「✅ 已合入 main」

**换工具不等于换掉病**。RD-53 点名的 `land-branch.sh` 早就不在了（被 `merge_stream.sh` 取代），
但同一个形状完整活在新脚本里：末行原本是无条件打
`echo "==> ✅ $BRANCH 已合入 main（$(git rev-parse --short HEAD)）"`。
对"分支头已是 main 祖先"的情况（两条队列并发时每天都发生），`--no-ff` 会造一个
**带入 0 个提交的空合并提交**，脚本就理直气壮地把那个新 sha 报成我的落地成果——
内容一样没动，只有账多了一笔。这正是 01:39 那次「LANDED 打的 sha 属于另一个会话」的同一件事。

**改了两处**（`TcoderMonitor/scripts/merge_stream.sh`）：
1. 新增 `0.6)` 判据：**先测 no-op，是 no-op 就不动 main** 并退出，
   提示语直接给"它为什么已在 main"那条自助命令（`git log --oneline --ancestry-path <头>..main`）；
2. 正常路径的落地行现在必须报**带入几个提交**（`git rev-list --count "$MAIN_BEFORE"..HEAD`），
   不是一句光秃秃的"已合入"。

**自助实证**（真跑，不是读码）：造一枚指向 main 头的探针分支 `ws/noop-probe`，
`MERGE_ALLOW_UNGATED=1 bash scripts/merge_stream.sh ws/noop-probe …` 的原始输出：

BEFORE=4d4b583a856f9d45da3d24d2c25ad92750c34751   AFTER=4d4b583a856f9d45da3d24d2c25ad92750c34751   ⇒ main 未移动 ✓

探针分支随后 `git branch -D` 删掉，主树只剩这一笔脚本改动。

**RD-53 原列的三条判据逐条对账**（不许含混过关）：
① 「落地判据永远是 `git merge-base --is-ancestor <分支头> main`，不是脚本的 LANDED 行」
   ⇒ **已机器化**：判据进了脚本本身，不再靠我记在脑子里；
② 「脚本要改成打印新建的合并提交 sha，或在 no-op 时明打 NO-OP 不动 main」

③ 「两条队列不要指向同一条分支」⇒ **没机器化，也不假装机器化**：那是派单纪律不是脚本能拦的事，

**证据等级要说清**：这是**一次真运行**，不是一条常驻守卫。`scripts/` 目录没有测试套件，
所以如果哪天有人把那 8 行删掉，不会有东西变红；正常路径那行新打印（带入 N 个提交）
**也还没在真合并上跑过一次**——它将在 R39 / R40 合流时取原文，取到之前这一格只算"半边已验"。

## 79. 立案 RD-69：`blocksAbsenceClaims` 这道门**在生产侧零读者**（09-22 就说过要如实记成交回件，我一直没记）

`SourceScanScopeReadout.swift` 里有这么一枚判据：

它的用处写在同文件注释里，而且写得很具体：**没看完的树不许说「这个项目没有测试码」那类缺席结论**。

**为什么 09-22 就发现却拖到今天才立案**：卷三 §34 当时写的是
