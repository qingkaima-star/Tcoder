## 4. 数据口径（看到数字前先读这节）

README 的「数据口径」一节已列了骨架，这里补齐**为什么**和**界面上具体长什么样**。

### 4.1 「0 个漏洞」有四种含义

判定分档只有一处：`DependencyEvidence.vulnerabilityCoverage`（RD-68，2026-09-24 收成一道闸），
产出三档 `full` / `partial` / `none`；命中数在前的那一档由 `DependencyReport.vulnerableCount` 决定。
四种情形与**界面上的原句**（话术同样只有一处：`DependencyVulnerabilityCoverage.statement`，
磁贴副标题 `DependencySafetyVerdict.summaryCaption`、安全公告空态 `DependencySafetyVerdict.advisoryEmptyCaption`
与无头出口逐字同源，所以你在任何一处看到的都是同一句）：

| 情形 | 界面上的说法 | 你该怎么读 |
|---|---|---|
| 有命中 | 「命中 N 条内置快照与安全公告」 | 真有问题，按公告升级 |
| **每一条**都核对过且零命中 | 「已核对 N / N 个依赖，未发现已知漏洞」 | 这才是「干净」这个结论，也是**唯一**允许发绿的一档 |
| 核成了几条、还剩几条没核成 | 「已核对 X / Y 个依赖，另外 Z 个没查 —— 这是「没查全」，不是「没有漏洞」」 | **不是干净，也不是没查**：琥珀色 + 徽标「部分核对」，缺口要自己补 |
| 一条都没核对成（含默认不联网） | 「共 N 个依赖，一条都没核对 —— 这是「没查全」，不是「没有漏洞」」；磁贴副标题另给一句「未联网核对，仅内置快照（覆盖 npm / Maven / Python），<快照截至由 `DependencySnapshot.asOfText` 现场算> · X / Y 项有版本数据」，可能还带「未覆盖生态：…」 | **未判定，不是安全** |

发绿由 `DependencySafetyVerdict.role` 决定（`.clean` 才是 `success`，`.partiallyCovered` 走 `warning`）；
徽标文字是 `DependencySafetyVerdict.badgeText` 那三档「已核对 / 部分核对 / 未核对」。
未核对与部分核对两档的悬停与图标都走 `.unverified`（`DependencyVerdictRows.SafetyVerdictBadge.body`），
不复用绿底对勾。钉住这件事的用例：`testEachStateSpeaksOneSentenceAtThreeExits`（三档各一句、三出口同句）、
`testPartialCoverageNeverClaimsTheSweepIsFinished`、`testFailedOrTimedOutLookupSitsInTheSameTierAsUnchecked`、
`testTheGateExpressionExistsInExactlyOnePlace`（第二条算式一出现就红，配 `testTheGateStillOwnsTheExpressionItIsGuarding` 防"删判据换绿"）。

**两条现读的边界，读这一节时必须一起看**：

1. **生态卡头那一格现在也读同一道闸**（RD-70，2026-09-24 由 R41 接上）：分档由
   `DependencyEvidenceLedger.subledger(forEcosystem:)` 取**本生态子账**后交给
   `DependencyEvidence.vulnerabilityCoverage`，画法则由
   `DependencyAdvisoryRows.DependencyEcosystemBadge.slot(riskLevel:coverage:)` 一处决定：
   `riskLevel != .none` 一律照旧显示真风险（坏消息不被覆盖度吞掉），
   `riskLevel == .none` **且**该生态覆盖度 `.full` 才允许 `RiskBadge(.none)` 那枚绿底对勾，
   `.partial` ⇒ 琥珀「部分核对」，`.none` ⇒ 中性「未核对」，悬停话术与总览同源（同一枚 `statement`）。
   ⚠ 子账**只用于分档**：`versionLookup` / `vulnerabilityLookup` / `scopeBreakdown` 三格是整份报告的账、
   原样透传，账本里没有"按生态分开"的那本 —— 读子账这三格会拿到全局数，边界写在
   `DependencyEvidenceLedger.subledger(forEcosystem:)` 的注释上。
   旧开关 `DependencyReport.hasVulnerabilityCoverage`（本体是"发起过查询或带回过公告"）
   已**整枚退役**（台账 RD-78，2026-09-24）：RD-70 关掉它最后一个上屏读者之后它在 `Sources/**` 零读者，
   而它想说的两件事各有唯一正主 —— 「发起过」= `DependencyReport.networkLookupPerformed`、
   「带回过公告」= `DependencyReport.advisories`。留着它只会继续被人当覆盖度用（RD-11 的病根就是这个形状）。
   `DependencyEcosystemCoverageTests+ScanGuards` 仍按字面把这个**名字**列为禁止再被接上屏的旧闸门标记
   （守卫扫的是字符串，属性删了这条约束照样有效）。
2. `DependencySafetyVerdict.mayClaimSafe` 目前在生产侧**没有读者**（台账 RD-71）：
   绿色实际来自 `role`。读到"唯一判据"这类字句时，先确认它有没有被调用，别把断言口当闸门。

**内置离线漏洞规则一共 10 条，只写了 npm（2 条）、Maven（5 条）、Python（3 条）三个生态**
（数组是 `VulnerabilitySource.bundled`，逐条 CVE 编号看每条的 `KnownVulnerability.cveIdentifiers`；
复算：`grep -c '            id: "TCODER-' Sources/TcoderMonitor/Services/Dependencies/VulnerabilitySource.swift` → 10）；
Gradle 与 Maven 坐标互通所以也受益（`DependencySnapshot.lookupScopes`）。
**SwiftPM、CocoaPods、Go、Cargo、RubyGems、NuGet 在离线时没有任何漏洞结论可给**。

再退一步，**在线核对也救不了全部**：OSV 侧只支持 npm / Maven(含 Gradle) / PyPI / Go / crates.io /
RubyGems / NuGet，**SwiftPM 与 CocoaPods 连在线都不查**（`DependencyNetworkLookup.swift` 的
`OsvPackageQuery.osvEcosystem` 对这两个生态返回 nil），界面在这种情况下会直说
「本项目没有可在线查询的生态（SwiftPM / CocoaPods 不在 OSV 覆盖范围内）」——这句话由
`ManifestDependencyAnalyzer.applyNetworkKnowledge` 写进 `DependencyReport.networkLookupNote`。

还有一层：版本号写成 `"*"`、`workspace:*`、分支名、修订号这类**无法比较**的值会被跳过，
不参与比对（离线侧的判据是 `KnownVulnerability.comparableCore`，被跳过的条数由
`ManifestDependencyAnalyzer.offlineCaveat` 数出来并写进提示），
所以「X / Y 项有版本数据」里的 Y−X 就是这部分。

内置快照有截止日期（代码里是 2026-09-19，`DependencySnapshot.snapshotDate`）。
**这个日期现在会直接显示在依赖页上**（#25）：离线判据句与「未核对」磁贴副标题都在句尾接上
「快照截至 2026-09-19（昨天）」，两个渲染点共用同一份文案 `DependencySnapshot.asOfText`，
免得分析器写一遍、视图再写一遍然后各自腐烂。括号里那段是**距今时长**，
由 `LogRecency.describe` 生成，所以它是「昨天 / N 天前 / N 个月前」这类相对说法，会变。

这条为什么值得单独说：**1 天前的快照和 1 年前的快照，以前在界面上长得一模一样**——
「漏洞判定只依据内置快照」这句话不带日期，用户读到「漏洞数 0」时无法判断这个结论有多旧，
而内置快照是写死在代码里的一份静态表，不会自己更新。现在这句话自己交代保鲜期。

日期**只到天**（#35）：旧实现把 `hour = 17` / `minute = 5` 写死在造日期的那一下，
渲染出来是「快照截至 2026-09-19 17:05」，而那张表只有「哪天抄的」这一级依据，
分钟级没有任何出处（那个时刻还是兜底常量的年份写错成 2025 的同一处挂钟），已删。
形状由 `HonestyP1SnapshotDateTests.swift` 钉住：日期段是十个字符的 年-月-日，整句不含时分冒号。
（第 7 节待确认清单里的第 2 条已随之关闭。）

### 4.2 提交总数 ≠ 作者榜求和，这是设计如此

「总提交数」含合并提交，作者榜与增删行用 `--no-merges` 统计。
Git 洞察页顶部有一条常驻口径条把差额讲清（`GitInsightsSections.GitRepositorySourceSection.discoveryDetail`），
三种文案：

- 未打满窗口：「N（含 M 次合并）· 作者与代码行统计基于 K 次非合并提交」
  ——此时差额**全部**是合并提交（`GitHistoryScope.windowLimit`）。
- 打满了窗口：「… 作者与代码行统计只覆盖最近 K 次非合并提交，更早的历史未纳入」
  ——差额 = 合并提交 **+ 没读到的更早历史**，不能全算成合并
  （判据是 `GitHistoryScope.Basis.windowCapped`，那句文案出自 `GitHistoryScope.headline`）。
- 旧报告里没有基准字段：明说「这份报告没有记录非合并提交数，作者与代码行仍按旧口径统计…重新分析后可拆分」
  （判据是 `GitHistoryScope.Basis.unknown`，同一句文案也在 `GitHistoryScope.headline`；
  「口径未知」这四个字是那个 case 的注释用词，不是界面原话）。

### 4.3 大仓库的历史是按窗口分析的

窗口上限 20,000 条非合并提交（`ShellGitAnalyzer.swift` 的 `ShellGitAnalyzer.maxCommits`）。
超限时页面做三件事：磁贴标题改成「窗口跨度」「窗口内作者」（`GitInsightsView.GitInsightsMetricGrid.body`）、
卡标题追加「 · 近 N 次提交窗口内」（`GitHistoryScope.authorTileCaption`）、
口径条用警告色并补一句「趋势、时段分布与作者占比都只是这段窗口的分布，不代表全部历史。」
（`GitInsightsSections.GitCommitScopeSection.body`）。
**注意两个字段不是一回事**：界面判断「是否被窗口截断」用的是派生判据
`GitHistoryScope.isWindowTruncated`（非合并窗口打满才是真），**不是**契约字段
`GitInsights.historyTruncated`——后者按 `已解析条数 < 全量提交数` 赋值，被合并提交污染，
本仓库 2026-09-20 实测 `git rev-list --count HEAD` = 290（含 127 次合并、非合并 163），
远未打满 20,000 的窗口，它照样是真。所以本文按界面行为描述，不按字段名描述。

### 4.4 健康评分：缺证据不给分，权重等比摊分

缺证据的维度直接 `return nil`，**不进分量表、不参与计分、也不得分**
（每个维度函数开头的 `guard` 就是判据，逐条列在下面那张表里。分派在 `WeightedHealthScorer.evaluate`，
实现自收官轮起按维度族分三份文件：`HealthCodeDimensions.swift`（代码四维）、
`HealthTeamDimensions.swift`（Git 历史两维）、`HealthRuntimeDimensions.swift`（日志·依赖·覆盖率三维）。
引用只写符号不写行号，理由见 `AGENTS.md` §4.6）。
然后评分器把分量表的权重**除以在场权重之和**归一到 1.0，使界面顶部那句「综合分 = Σ(得分 × 归一化权重)」
（`HealthComponentTable.body` 的卡副标题）能复现综合分（归一在 `WeightedHealthScorer.score` 里
`totalWeight` 那一步，紧接 `guard totalWeight > 0`）。
界面那句话说什么由 `HealthBreakdown.normalizationSummary` 分三种情况决定（`HealthComponentTable.swift`）：

- 有维度缺席：「缺失 N 个维度不参与计分、也不按 0 计入，其份额已按在场维度等比摊入。」+ 明细
  （明细由 `HealthBreakdown.shiftNotes` 生成）；
- 无缺席、且权重表合计就是 100%：「…没有维度缺席；权重未做摊分，乘数即表内原始值。」；
- **无缺席、但权重表合计不是 100%**（本 App 就是这种，合计 110%）：
  「…但内置权重表合计 110%，评分器发布前已整体折算，故各乘数不等于表内原始值。」

哪些情况会让维度缺席（这一条直接决定你的分数）：

| 维度 | 计分的最低证据 | 出处（评分器里的维度函数） |
|---|---|---|
| 复杂度 | 代码扫描有结果，且测到全仓均值或非空热点榜 | `WeightedHealthScorer.complexityOutcome`（两道 `guard`） |
| 重复代码率 | 代码扫描有结果且有效码行 >0 | `WeightedHealthScorer.duplicationOutcome` |
| 代码质量 | 文件数 >0 | `WeightedHealthScorer.codeQualityOutcome` |
| 注释与可维护性 | 总行数 >0 | `WeightedHealthScorer.documentationOutcome` |
| 提交活跃度 | 有 Git 数据且提交数 >0 | `WeightedHealthScorer.activityOutcome` |
| 协作分布 | 上一条之外还要求有榜首作者 | `WeightedHealthScorer.busFactorOutcome` |
| 运行稳定性 | `inputs.logs` 在场**且**真扫到日志（`totalLinesScanned > 0`）；零日志时整维缺席、只留一条建议（#46） | `WeightedHealthScorer.stabilityOutcome` |
| 依赖健康 | 依赖数 >0 **且漏洞核对状态为已核对**；未核对或查询失败整维缺席 | `WeightedHealthScorer.dependenciesOutcome`、`VulnerabilityEvidence.classify` |
| 测试覆盖 | 仓库真的产出了覆盖率报告且有**生产码**行分母（#37：`CoverageMetrics.overallLinePercent` 只算 `CoverageScope.isProductionSource` 为真的记录，见第 4.6 节） | `WeightedHealthScorer.testingOutcome`、`CoverageMetrics.hasData` |

「代码质量」这一行的分子是 `CodeMetrics.hugeFileCount`（越过行数线的**真个数**），不是
`CodeMetrics.hugeFiles` 的长度——后者是**封顶 20 项**的榜单，拿它当分子会让仓库越大越显干净
（本 App 扫自己一度把 38/190 = 20% 报成 10.5%）。缺该字段的旧报告退回榜内计数，
此时 detail 会写明「榜内只列 20 个」：偏松的口径必须自己承认。判据由 `HugeFileCountHonestyTests` 钉住。

#### 4.4.1 综合分之外的第二把尺：工程质量（代码口径）

综合分里 **21% 的权重**（提交活跃度 12% + 协作分布 9%）量的不是代码，而是 **Git 历史的既成事实**：

- 历史跨度不足 7 天时，活跃度按 `GitCadenceEvidence.shortHistoryScoreCeiling` 封顶 60 分——
  一个昨天才建的仓库，今天提交再密也拿不到这一维的高分，它到第 7 天才会解锁；
- 协作分布按**署名身份**归并，历史提交都记在同一个身份下时，头号作者占比会接近 100%，
  这一维只剩 6 分，而"谁写的、几个人写的"改代码改不动。

于是同一份代码在"新仓库"与"老仓库"身上会差出十几分，用户看不出该修什么。健康评分页因此并列
**两个数**：`HealthScore.overall`（综合，口径一字未改）与 `HealthScore.codeScope`
（`HealthSubScore`，「工程质量（代码口径）」）。后者的成员判据只有一条，写在
`HealthDimension.belongsToCodeScope`：**这项分数能不能靠改本仓库代码抬起来**——
计入代码质量、复杂度、重复度、注释与可维护性、测试覆盖；不含提交活跃度、协作分布、
运行稳定性、依赖健康。

三条防"挑好看的口径"的约束，都由 `HealthCodeScopeTests` 钉着：

1. 副读数**只能由已发布的同一批分量、同一套归一化权重**重算，不许有第二套公式；
2. `includedDimensions` / `excludedDimensions` / `note` 三样必须一起落盘上屏，排除项要逐个点名；
3. 没有任何代码维度在场时该字段为 `nil`，界面**不画 0 分**（0 会被读成"代码很差"）。

两个容易忽略的后果：

1. 「依赖健康」默认离线时**必然缺席**（未核对 → 不计分），所以离线扫描的综合分
   不含这一维度，权重被摊到别的维度上（提示文案「未做在线漏洞核对，依赖健康本维度暂不计分；
   开启「联网核对」后重扫才有结论。」，`WeightedHealthScorer.swift` 的 `evaluate` 里 `.dependencies` 分支）。
2. 「未调用外部模型」这句声明**只限评分本身**，不代表整个 App 不联网——
   依赖页的在线核对是真会发请求的（第 5 节）。
3. 「测试覆盖」在**本仓库自己的自扫里通常缺席**：真正的行覆盖率（44.97%）落在 `.build/` 下，
   而扫描器按隐藏目录规则跳过 `.build`。所以代码口径 90+ 是在
   **「测试覆盖这一维不在场」的前提下成立的**，不能被读成「覆盖率也是 90」。

#### 4.4.2 本仓库自扫的收官实测（2026-09-21 04:54，被测头 `07a8ae9`＝合流后的 main）

| 代码质量 | 90 | 0.1892 | 巨大文件占比 1.6%，平均函数 13 行，共 311 个文件，38 个超长函数扣 6 分 |

**综合 76（B 级）／工程质量（代码口径）92**。Σ(score·weight) 在两个口径下都能复现，
副读数用的就是上表同一批分量、同一套权重（代码口径按在场四维重新归一）。
同一份代码在合流前的 `2a6f117` 上读出的也是 92；本轮早些时候（六包还没落地、
同一把尺子）读的是 87。上表只有 Git 那两维的数字随提交数漂，四个代码维度一分未动。

**这 8 分扣在哪里、为什么今晚不修**（逐条对得上上表）：
- 代码质量 −10：其中 6 分是 38 个 >50 行的函数，绝大多数是 Tests 里的**字符串夹具生成器**
  （如 `writeManifestsMaven` 155 行、CC 1），已登记在 `X3TestSizeAuditTests` 的派工清单
  （成员名 longFunctionWorkList，它在 Tests 侧，按 §4.4 的锚点约定不钉成点号引用）；
  剩下的是 5 个 >400 行的 `.md` 文档进了「巨大文件」分母 —— 判据本身是产品缺陷（散文长度
  不该算代码可维护性），**但不为抬自己的分去改判据**。

#### 4.4.4 两道「证据不够」的地板：运行稳定性与协作分布（2026-09-22 R9b，被测头 `12f9e25`）

这一节写的是**两条把分打下去**的规矩，方向与"为提指标调阈值"正好相反。
两条地板的数值都是**推导**出来的，推导的两条前提都引用仓里已有的数，测试把推导本身当断言对象
（`ScoreEvidenceFloorTests`），不是"先拍一个数再让仓库刚好过"。

**① 运行稳定性：先分三态，再讲证据量**

`totalLinesScanned == 0`（一行真日志都没读到）以前只有一个出口、一句「没有可扫描的日志」。
RD-46b 把崩溃正文移出分母之后，「只有崩溃报告、零真日志行」的项目也落进了这一支，
那句话对它就是假的（崩溃报告就在日志目录里，已经被读到并且认了归属），
而那 N 次确认崩溃还随整维缺席一起不再扣分。现在拆成三态（判据只此一处：
`StabilityZeroDenominatorShape.assess`），**三态都不给分、都不按 0 计入**，但各说各的话：

| 输入形状 | 说出口的那一句 | 给分吗 |
|---|---|---|
| 真的什么都没有（零崩溃、零报告、无读不动项） | 「没有可扫描的日志…」（整改前那句，此时它是真话） | 否，整维缺席 |
| 有崩溃证据（确认次数或已读到的份数）但零真日志行 | 「读到 N 次确认崩溃（M 份崩溃报告），但零真日志行 ⇒ 错误密度算不出分母…崩溃明细见「错误日志」页」 | 否，整维缺席 |
| 只有读不动的崩溃报告 | 「有 M 份崩溃报告没能读出来…崩溃证据不确定…也不得读成「没有崩溃」」 | 否，整维缺席 |

判"有没有崩溃证据"**只读份数与次数**（`crashCount` / `crashReportCount` / `scannedFiles` 里
`role == .crash` 那几份），一律不碰行数 —— 行数正是这一支已经确定为 0 的东西。
**分子侧一行没动**：崩溃该怎么扣还怎么扣，这里只是把已经量到的数说出来。

有真日志行时另有一道**最小证据量**：`StabilityEvidence.minimumLogLines` = **2,000 行**。
推导：一份 N 行日志里"一次错误"的密度量子是 `1000/N` 每千行；要它不至于跨过曲线的最小台阶
（`HealthCurves.stability` 锚点表第一级 0 → 0.5 每千行），需要 `1000/N ≤ 0.5` ⇒ **N ≥ 2000**。
N = 1999 时一次错误 = 0.50025 每千行，单条事件就把人从「干净」档推出去；N = 2000 时正好落在台阶上。
低于下限的处理方式**故意不是缺席**，而是**保留分数但强制降档 + 上屏标「证据太薄·未判定」**：
缺席会把已确认崩溃的扣分一起抹掉（那正是 RD-49 的病灶，不能重犯）。
封顶值直接引用 `GitCadenceEvidence.shortHistoryScoreCeiling`（60 分），一个新数字都不造 ——
两处的语义同一件事：「样本不足 ⇒ 最多只能拿到普通稳定仓库的水位」。封顶是 `min`，
**只会压低、绝不抬高**（4 次确认崩溃的读数本来就在 60 以下，封顶对它是空操作，但标记照样上屏）。
同一道下限也管住优点句：3 行日志不许写「已扫描 3 行、窗口内未见确认崩溃」。

**② 协作分布：最小总体 = 7 笔非合并提交**

`BusFactorEvidence.minimumCommitBasisForShare` = **7**。推导：总体 N 笔时头号作者占比只能是 k/N，
即**一笔提交折合 1/N**；`HealthCurves.busFactor` 的调档边界是 0.35 / 0.5 / 0.7，
最窄的一档宽 0.15。要"一笔提交"不足以跨过最窄那一档，需要 `1/N ≤ 0.15` ⇒ **N ≥ 6.67 ⇒ 7**。
N = 6 时一笔 = 16.7% > 15%（跨档只要一笔）；N = 7 时一笔 = 14.3%（最窄档要两笔才跨得过去）。
语义定为**整维缺席**（不是封顶）：总体小到占比无法分辨时我们没有任何可说的结论，
理由句点名三个数（`commitBasis`、`activeAuthorCount`、一笔折合多少百分点）。

两条边界都写死了：

1. **单人就是单人**：`activeAuthorCount < 2` 是一条**已经确定**的结论（bus factor = 1，占比 100%），
   不是"样本不足"。地板对它**不适用** —— 单人 + 3 笔提交仍然出分、仍然是低分（反例用例专门钉这条）。
2. `commitBasis == 0` 沿用 R9 已定的 fail-loud 口径（"作者表里没有可算分布的提交"），
   **排在**新地板之前，不许被"样本不足"抢先兜住。
3. 数值不与 `GitCadenceEvidence.minimumSpanDays`（7 天）共用：那把尺子量时间跨度、
   这一把量总体分辨力，互不蕴含（一天里 squash 出 5,000 笔的仓库跨度不够、总体够；
   跨三年只留 3 笔的仓库反过来）。撞成同一个 7 是巧合，守卫还专门钉住两处**不许**互相引用。

### 4.5 内存口径

已用内存 = 总量 −（free + speculative + purgeable），**与活动监视器一致**；
inactive（文件缓存）**仍算已用**，所以这个数会比你以为的「真实占用」大
（`Services/Performance/SystemSampler.swift` 的 `VmCounters.reclaimableBytes` 是可回收量、`:155-156` 是口径注释、
`SystemSampler.memoryUsedBytes` 是实现 `:160-168`，注释明说 inactive 是文件缓存但监视器仍计入已用）。
页大小取 `vm_kernel_page_size`，Apple Silicon 上是 16 KB（`:253`，注释 `:248`）。
瞬时不一致有兜底：若可回收量算出来不小于总量，退化为 `active + wired + compressed`（`:163-165`）。
**取数失败时不再冒充满负荷**：早期版本 `host_statistics64` 一失败页计数全为 0，
会把内存画成接近 100% 占满（《20 WS-D 诚实性审计》P1 #10）；现在失败路径返回 nil、
界面显示 `--` 并声明被剔除的点数（`SystemSampler.vmCounters` 与 `SystemSampler.memoryUsedBytes` 的可选返回、
`LiveReadings.memoryUsedBytes` 与 `memoryGapReason`）。
换句话说：**再看到内存瞬间打满且曲线是一条竖线，那就是真的打满**。

### 4.6 覆盖率只读现成报告，不代跑测试

「覆盖率」这一页/这块**不会执行你的测试**：分析器只做「解析已存在的报告文件」，
`CoverageAnalyzer.swift` 顶部注释原话是 "Nothing here runs a test suite — it only parses existing
reports"——**那是代码注释，界面上不显示**。全仓唯一的子进程调用是 `git`（`SharedUtilities.swift`
的 `Shell.blockingRun`，调用方只有 `ShellGitAnalyzer.swift` 的 `ShellGitAnalyzer.run`），没有任何跑测试的路径。

- 认得五种报告（文件名白名单 `CoverageReportFormat.allFileNames`，按名分派在 `CoverageAnalyzer.parse`）：
  `lcov.info` / `lcov.dat`、`coverage-summary.json`（istanbul / nyc）、`jacoco.xml` / `jacocoTestReport.xml`、
  `coverage.xml`（coverage.py）、`clover.xml`。
- 发现限制：深度 ≤6、最多 40 个文件、单文件 ≤20,000,000 字节、单份 lcov 逐行账本 ≤300,000 行
  （`CoverageReportDiscovery.maxDepth`、`CoverageReportDiscovery.maxReportFiles`、
  `CoverageAnalyzer.maxReportBytes`、`CoverageLineLedger.defaultLineBudget`）。
  **上限本身不是缺陷，静默才是**：四条任一命中都会写进合并台账
  （`CoverageDiscoveryStats.notes` 与 `CoverageMergeLedger.statement`），句子里点名"哪个上限、影响几份"。
- **总数按四类身份合并，不再"取分母最大的 6 份直接相加"**（RD-25；旧形状是 `rank` 里那句 `prefix(6)`
  加上 `overallLinePercent` 的裸累加）。四格身份：格式 `CoverageReportFormat`、
  运行与模块 `CoverageReportIdentity`、源码侧 `CoverageSourceState`。合并判据在
  `CoverageMergePlanner.plan`：同一次运行的对偶落法只数一次、多份 lcov 按**源码行命中集合求并**
  （`CoverageLedgerMerge.merge`）、拿不出可核对行集合的重叠文件判冲突并摘出分母、
  只有汇总桶的报告不参与合并。
  **合不出可信并集时不给总数**（`CoverageTotalBasis.nothingMergeable`，`overallLinePercent` 是 `nil`
  而不是一个伪精确的百分数），被拒合并的读数原样留在台账里可查。
- **没有报告时这块整块不出现**，不是空态卡、更不是 0%：`DashboardView.swift` 的 `DashboardView.coverageStrip`
  外面就是一层 `coverage.hasData` 判断，为假时连分隔线都不画——README「数据口径」同一条。代码注释里那句
  「测试覆盖率只在仓库真出了报告时才出现，没报告就不画，避免读成一个假的 0%」写的是这个意图，**界面上不会显示它**。
  这条口径由 `RealRepositoryEvidenceTests.swift` 钉住（见 README「验收脚手架」）。

**主读数是「仅生产码」口径，全量口径降级为次要读数（#37）。**
覆盖率那块上最醒目的读数「生产码行覆盖」（`CoverageMetrics.overallLinePercent`）只把生产码算进分母，
先过契约里的四条 Swift 规则（`CoverageScope.isProductionSource`，四个标记各是一个常量）：
路径含 `/Tests/`、含 `PackageTests`、含 `/.build/`、文件名以「Tests.swift」结尾；
再叠一层多语言判定（`CoverageTestPathRules.isTestSource`，入口是
`CoverageSourceScope.isProductionSource`）：`.test.ts` / `.spec.tsx` 这类点号中缀、
`tests` / `__tests__` / `spec` / `it` 这类**整段**目录名、以及 `OrderTest.java`、`_test.go`、
`test_*.py`、`*_spec.rb` 各语言命名约定。叠加是**只减不加**：Swift 那四条一字未改。
双向表钉在 `Tests/TcoderMonitorTests/CoverageIdentityTests.swift` —— 20 条测试路径必须抓到、
15 条生产路径不许误伤（`latest.ts` 含 `test.ts` 子串、`Latest.java` 结尾是小写 `test.java`，
都是这里挡住的）。
口径本身写在读数旁边（`DashboardView.coverageCaliberLine`），原话是

## 5. 隐私

1. **全部分析在本机完成，不上传任何源码内容**（README「数据与隐私」）。
2. **在线查询默认关闭**，需要手动开：开关在「依赖分析」页第一张卡「分析选项」里，
   标题「分析时联网查询最新版本与漏洞库」（默认值 `false` 是 `AppState.allowNetworkLookups`；
   界面 `DependenciesView.NetworkOptionsCard.body`）。
   开启后**不会立刻生效**，页面就写着「开启后需要重新执行分析才会生效。」
   （`DependenciesView.NetworkOptionsCard.statusCaption`），
   必须再点一次「重新分析」。
3. **会连哪些地址**：只有 npm registry 与 OSV.dev，两个域名写死在
   `DependencyNetworkLookup.osvHost` 与 `npmRegistryHost`；会话是临时的、不带 cookie 也不落缓存
   （`DependencyNetworkLookup.swift` 的 `session`，`:337,341,343`）。npm 侧是 GET；
   **OSV 的批量查询接口是 POST**，请求体里只有包名与版本这一类查询条件
   （`OsvClient.swift` 的 `DependencyNetworkLookup.osvQueryBatch`，逐包回退 `osvQuerySingle` 同样是 POST）。
   换句话说：只读语义，但不是「只发 GET」。
4. **超时**：单次请求硬超时 5 秒（`DependencyNetworkLookup.requestTimeout`，npm 与 OSV 共用这一个常量）。
   但 npm 与 OSV 是**串行**发起的（先 `await` npm 再 `await` OSV，
   `ManifestDependencyAnalyzer.applyNetworkKnowledge`），所以整个在线阶段最长接近 10 秒而不是 5 秒
   （README「数据与隐私」实测值：黑洞地址下两边各 5.006s）。
   超时/失败会降级为内置离线快照并在页面写明，例如
   「OSV 查询超过 5 秒硬超时，本次在线漏洞结果整体放弃（含已取回但未来得及返回的公告）」
   （`DependencyNetworkLookup.osvBatch` 的 `.timedOut` 分支）、「达到时间预算，剩余 N 个包未查询」
   （`NpmClient.swift` 的 `DependencyNetworkLookup.performNpmLookup`）。
5. **进程监控只读**：不向任何进程发信号、不 kill、不重启、不附加调试器
   （纪律注释写在 `ProcessInspector.swift` 顶部的文件注释里；界面声明
   `PerformanceProcessTable.PerformanceProcessTableCard.coverageNote`「只读展示，不提供任何进程操作」——
   这是拿不到进程计数时的兜底分支，注意 `ProcessSortKey.title` 返回的是两个**排序列名**、不是这句话、
   `PerformanceMatcherEditor.body`「只读观测，不干预任何进程」、
   `PerformanceProcessGroups.PerformanceGroupCard.header`「只删规则，不干预任何进程」）。
   用到的只有 `sysctl` / `proc_listallpids` / `proc_pidinfo` / `proc_pidpath` / `proc_pid_rusage`
   这几类查询接口（调用点是 `ProcessInspector.processCount`、`listAllPids`、`bsdInfo`、`taskInfo`、
   `openFileCount`、`executablePath`、`rusageInfo`）。
   仓库里唯一的 `terminate()` 是给**自己起的 git 子进程**做超时收尾的
   （`SharedUtilities.swift` 的 `Shell.blockingRun`，调用方只有 `ShellGitAnalyzer.run`），与外部进程无关。
6. **本 App 没有 macOS 沙盒**（第 2.1 节），意味着它能读到你选中的目录树里的东西——
   所以**只添加你打算被扫描的目录**。

## 6. 常见问题

**Q：我的健康分比预期低，是不是项目真这么差？**
先看「维度分量」表和缺失维度那一句。缺证据的维度**不给分也不白送分**，
它的权重会被摊到别的维度上（第 4.4 节）。常见拉分点：没跑过覆盖率（「测试覆盖」缺席）、
没开联网核对（「依赖健康」缺席）、一行日志都没扫到（「运行稳定性」缺席，#46）、非 Git 目录（两个 Git 维度缺席）。
这些情况下你的分数不是"项目得分"，而是"在场指标的得分"。

**Q：依赖页为什么全是「未核对」？**
两种原因：①没开联网开关（默认关，`AppState.allowNetworkLookups`），或开了但没重新分析
（「开启后需要重新执行分析才会生效。」，`DependenciesView.NetworkOptionsCard.statusCaption`）；
②该生态没有内置规则——离线只有 npm / Maven / Python 共 10 条
（`VulnerabilitySource.swift` 的 `VulnerabilitySource.bundled`），SwiftPM 与 CocoaPods **连在线都不查**
（`OsvPackageQuery.osvEcosystem` 对它们返回 nil）。这是"没查"，不是"安全"。

**Q：第一次扫描很慢？**
正常。代码扫描要遍历目录树（上限 60,000 文件，`ScanOptions.maxFiles`）、
Git 要读最多 20,000 条提交的历史（`ShellGitAnalyzer.maxCommits`）、日志要扫最多 60 个文件
（`FileLogAnalyzer.maxDiscoveredFiles`），而这些阶段是**串行**跑的
（阶段文案在 `SharedComponents.swift` 的 `AnalysisPhase.label`）。
开了联网再叠最长约 10 秒（第 5 节第 4 条）。

**Q：「总提交数」和贡献者页的提交加起来对不上？**
不是 bug，差额就是合并提交（或更早的未读历史），Git 页顶部的「提交统计口径」条会直接告诉你
差额是多少、以及作者榜是基于多少个非合并提交算的（第 4.2 节）。

**Q：Git 页突然变成「尚未分析 Git 历史」，之前的数据没了？**
最可能是那次 `git log` 撞上 60 秒超时（`ShellGitAnalyzer.swift` 的 `ShellGitAnalyzer.init` 参数 `logTimeout`）。
本轮失败时上一轮的 Git 结果**不会被保留**（`AppState.scan` 每次新建报告），
页面会退回未分析空态（`GitInsightsSections.GitDataAbsence.emptyState`），总览页同时给一条
「未能完成：Git 分析」并可点重试（`DashboardView.failureCard`）。
大仓库建议接上电源后重试；**这一条是已知缺陷，不是你的操作问题**（见第 7 节）。

**Q：数据存在哪里？怎么清空？**
`~/Library/Application Support/TcoderMonitor/`（拼这段路径的是 `ProjectStore.resolveStorageDirectory`），
删掉这个目录即全清；只想撤一个项目就用侧栏右键「移除」（`ProjectSidebar.rowContextMenu`）。

**Q：为什么性能页的内存比 `top` 显示的大？**
口径不同但和活动监视器一致：文件缓存的 inactive 页也算已用（第 4.5 节）。

**Q：还有内置示例项目吗？**
没有了（2026-09-21 批次 P7-A 整条退役）。原先那份样例的所有数字都是写死的，
而且「示例」标记只覆盖 4 处、另外六页当真读数渲染 —— 用户口径是
「不能有假数据」，所以删除而不是补标。现在首启是引导卡 + 空态，
界面上每个数字都来自你选择的那个真实仓库。来龙去脉见 `docs/使用说明.md` 第 1 节
与 `docs/功能真实性清单.md` 的 S1 条。

## 4.7 函数计数这一档现在认到哪、还不认哪（RD-79，2026-09-24）

- **已修**：`export const useFoo = (…) => { … }` 以前整类漏认（`jsFunction` 收了 `export function`，
  但 `jsVariableArrow` 没有 `export` 前缀位）。交付二进制实测：同形两块体箭头，
  不带 `export` 计到 1、带上计到 0。ESM/TS 模块主流写法少认，直接把
  `analyzedFunctionCount`（平均 CC、热点榜、复杂度分母的共同分母）算小 ⇒ 前端项目**看起来比实际简单**。
  正例与两条反例（`export const config = {…}`、`export const n = 1` 都不许算函数）
  钉在 `CodeAnalyzerScanTests+ComplexityAndFunctions.swift`。
- **认到哪（RD-79 第二根因，同日修完）**：不带花括号的**箭头表达式体**现在能进函数数与 CC 了 ——
  点号链（`=> items\n.filter(…)\n.map(…)`）、三元换行、逐行参数表（`(\na,\nb\n) => …`）三类，
  边界由 `ComplexityEngine.statementEnd` 判（定界符配平 + 行尾算符 + 下一行开头算符三条一起看，
  窗口 `maxStatementLookahead` = 16 行，超出就不猜、照旧走「边界推不出来」那句出声）。
  同笔修掉一条更狠的：以前 `curlyEnd` 允许签名**向后最多 8 行去借一个 `{`**，
  于是 1 行的箭头会把紧跟其后的对象字面量整段当自己的体 ——
  夹具实读修前 = 一条 9 行的假 `add`，且那个对象里的真方法**整段不再被扫到**（扫描线一步跨过）。
  一条假条目与一处漏报同源，两条都钉在 `CodeAnalyzerScanTests+ArrowBodies.swift`（含反向对照：
  摘掉语句上界与箭头体这两档，15 条断言当场红）。
- **仍不认（两条限度，别读成「没有」）**：
  ① 单行表达式体（`const f = (x) => x + 1`）不进分母 —— 这**不是箭头特有**，
  是 `minFunctionLines = 2` 的全语言口径（Go/C 的单行函数同样不进，已钉在
  `testCodeMetricsOnKnownMarkersHugeFilesAndClones` 的手算账本里：该夹具 7 个单行函数被挡在分母之外）。
  ② **跨行的三元不计判定**（RD-80）：`? a` 换行 `: b` 读成 CC 1，同一行写完读成 CC 2 ——
  三元的尺子按行数（`ComplexityCounting.swift`），要求 `?` 与 `:` 同一行才计一次判定。
  两条方向都是**把复杂度与函数数算低**，读到"某前端仓函数很少、CC 很低"时要连着这两句一起读。

## 4.8 「时间窗口 N 天」到底框住了什么（日志链，2026-09-24 端到端复扫量出来的口径）

错误日志页与无头 `score` 都写着「时间窗口 N 天」（`LogsView.swift` 里那句「分析于 … · 时间窗口 N 天 · 扫描 M 行」的读数），
但**这个窗口框的是"挑哪些文件"，不是"算哪些行"**：

- `LogDiscovery.discover` 拿 `Date() - N×86,400` 当截止，
  对**三个发现来源一起生效**（按文件的修改时间筛文件）；
- 文件一旦被挑进来，`FileLogAnalyzer` 就把**该文件里的行全部计入** ——
  「每千行日志 X 个错误」的分母/分子都是"这个文件的全部扫描行"，**不逐行按时间过滤**。

实测（交付二进制 `score --window-days=1` 对 `--window-days=30`，同一份 5 行夹具、
其中 2 条 error 的时间戳是 14 天前）：两次的读数一字不变 ⇒
"文件足够新就被整份计入"这件事是真的，不是推测。

⇒ **读数时该怎么理解**：窗口变小不会把老事件的行数剔掉，只会让**整份文件**出局。
所以"近 7 天错误率"这种读法是**过度解读**；准确的读法是
"最近 7 天内被改动过的日志文件里，一共扫到 M 行、其中 E 行是错误"。
页脚那句 `扫描 N 行` 就是给这个用的 —— 它给的是**行数**而不是"窗口内事件数"。

**这句现在已经在屏上（RD-82，2026-09-25）**：`错误概览` 卡头副标题旁那枚 ⓘ
走 `LogsMetricGrid.windowCaliberNote`，说的就是「窗口按文件挑、不逐行过滤 ⇒ 分母是这些文件的全部扫描行」；
槽位用既有的 `GlassSection.subtitleHelp:` 而不是新增一行常驻长句（风格契约 8，
常驻长句棘轮 `TooltipMigrationGuardTests.visibleCaliberCeiling` 因此不受影响）。
自检 `LogWindowCaliberTooltipTests` 双向；**英文态把它读出来仍要重拍那一页**，静态腿不证明上屏。
