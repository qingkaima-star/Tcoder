# 中英双语方案（原生支持，不许乱翻译）

用户 2026-09-21 00:37 提的硬要求：**项目要原生支持中文跟英文，一定要正确显示，不要乱翻译。**

这一条和刚做完的「简约无界」观感返工是**咬合**的，不是并列的：
本轮把列宽按中文量过一遍（`56pt` 装 4 位数字、`72pt` 装「12,345 次」、名称列 `96pt`），
而英文普遍比中文长 1.5–2.5 倍。**同一套定宽在英文下会把「12,345 commits」截成「12,345 com…」**。
所以双语不是"把字符串换掉"就完事，它必须带着一次**双语言的排版复量**一起交付，
否则就是把刚修好的界面用另一种语言再弄乱一次。

---

## 1. 三条不可动摇的决定

### 1.1 源语言 = 简体中文（`CFBundleDevelopmentRegion = zh-Hans`）

现有全部文案是中文，且是逐条推敲过的诚实性文字（三态句式、口径说明、报告年龄、
分母交代）。**中文是权威文本，英文是译文**，不是反过来。
任何"先把界面写成英文再翻回中文"的做法都会把那些细节磨平。

### 1.2 本地化键 = 中文原文，不用 `page.health.title` 这种符号键

理由只有一条，但它是决定性的：**缺一条译文时，界面退回显示中文原文，
而不是漏出一个机器键。**

- 键 = 中文：漏翻 → 屏幕上是一句正确的中文（难看但绝不错）。
- 键 = 符号：漏翻 → 屏幕上写着 `contributor.busfactor.high`。这就是用户点名禁止的"乱翻译"最恶劣的一种。

代价是中文改一个字就要同步两个 `.strings` 文件 —— 用 §4 的守卫把这件事变成机器的事，不靠记性。

### 1.3 不许机翻

译文逐条人工写。三条判据：
- **术语表先行**（§3），同一个概念全仓一个译法，不允许一处 "Duplicate" 一处 "Duplication"；
- **单位与量词必须带数**：`行 / 次 / 人 / 天` 在英文里要单复数（`1 line` / `5 lines`），
  用 `stringsdict` 的 plural 规则，不用 `line(s)` 这种偷懒写法；
- **诚实性句式不许为了通顺而缩短**：「未联网核对，0 条命中只是"没有查"，不是"没有病"」
  这类句子的信息量是设计的一部分，译文必须保住"没查 ≠ 没病"这层对比。

## 2. 机制（SwiftPM 可执行 + 自建 .app，没有 Xcode 工程）

| 事项 | 做法 |
|---|---|
| 资源 | `Sources/TcoderMonitor/Resources/{zh-Hans,en}.lproj/Localizable.strings`，`Package.swift` 里 `resources: [.process("Resources")]` |
| 查找顺序 | `Text("中文")` / `String(localized: Bundle.main)` 走 **`Bundle.main`**。所以 `scripts/build_app.sh` 必须把两个 `.lproj` 拷进 `Tcoder.app/Contents/Resources/`（SwiftPM 生成的 `TcoderMonitor_TcoderMonitor.bundle` 对 `Text` 无效，不能只靠它） |
| Info.plist | 加 `CFBundleLocalizations = [zh-Hans, en]`、`CFBundleDevelopmentRegion = zh-Hans`。缺这两条时 macOS 可能整段不查表，或语言菜单里出现混合态 |
| 复数 | `en.lproj/Localizable.stringsdict`（`NSStringPluralRuleType`） |
| 切语言验证 | 不改系统设置：`open -n Tcoder.app --args -AppleLanguages "(English)" -AppleLocale en_US`，取证脚本已经支持传 argv |
| 数字/日期 | 审 `NumberFormat` / `DateFormat` / `ByteFormat` 是否硬编码 `en_US_POSIX` 或中文格式串；轴标签**保持 POSIX**（那是刻意的，见 `ChartChrome.axisLocale` 注释），只有面向人读的时间/数字跟 locale |

## 4. 守卫（每条都要配元测试，扫描型守卫不配元测试等于没配）

实现落在 `Tests/TcoderMonitorTests/LocalizationGuardTests.swift`（4 例，含元测试）。

1. **完工清单**（`migratedFiles`）：清单里的文件不许出现"没登记的中文界面串"。
   **不用"全局未迁移计数棘轮"** —— 一个基线数字会随任何人加一句中文而涨，
   涨了就"合法"，等于没有闸门；而"某个文件已经干净"是可复核的事实，退回去立刻红。
   清单只许变长。（P1 阶段清单为空，测试显式 `return` 不假装有结论。）
2. **登记了就必须翻**：`en` 里值 = 键、或值为空串 → 红。允许例外，但例外要写理由。
3. **译文不许烂尾**：`en` 里每个键必须在 `Sources/**` 真实出现，否则是"改了原文没同步目录"。
4. **双语言排版复量**（P5 交付，尚未实现）：`scripts/width_audit.swift`
   —— **报告器，不是闸门**，与 `pixel_audit.swift` 同一档。对每个键按目标字号用 CoreText
   量出像素宽，与它所在列的定宽比对，列出"英文会截断"的清单。闸门仍是人眼 + 实拍；
   量出来的数只负责让"哪几格要改弹性列"这件事不再靠猜。

### 4.1 元测试当场抓到两个假绿（记下来，这两类错误一定会再来）

- ICU 正则**不认** Swift 的 `\u{4E00}`，只认 `\u4E00`。写成前者时正则编译失败，
  而 `try?` 把失败吞成 `nil`，函数返回空 → "扫到 0 条违规"，**看起来像代码很干净**。
  改成 `try!`：正则坏了就该炸，不该静默通过。
- 逐行状态机剥块注释时，**同行开合**的 `/* … */` 会把下一行也当成注释吃掉，
  于是 27 条键解析出 0 条，而"目录是空的"这个结论一路传到"没有未翻译的键"。
  改成按跨度删（`/\*.*?\*/` 非贪婪 + 可跨行）。

## 4.2 机制修正（P1 落地时发现的，原文写错了两处）

- **不需要 `zh-Hans.lproj`**。键就是中文原文，源语言下 macOS 直接显示键本身。
  所以"两语言键集相等"这条查法是错的（它假设两边都有目录），已换成上面第 2、3 条。
- **`Text(String变量)` 不查表**。`Theme.Page.Header` 的 `title` 是 `String`，
  `Text(title)` 走 verbatim 初始化 —— 目录里翻了也一个字都不变。
  必须写 `Text(LocalizedStringKey(title))`。这是双语最容易的空转：
  机制接好了、表也翻了、界面没动。**每迁一个组件都要先确认它落在哪一侧。**
- 语言资源**不能**走 `Package.swift` 的 `resources:`：那只会产出
  `TcoderMonitor_TcoderMonitor.bundle`，而 `Text` 查的是 `Bundle.main`。
  所以文件放在 `TcoderMonitor/Resources/*.lproj/`，由 `scripts/build_app.sh`
  拷进 `Contents/Resources/`；一个 `.lproj` 都没拷到就**拒绝出包**
  （宁可不打包，也不交付一个"看起来支持英文、其实整段不查表"的包）。

## 7. P2 落地时发现的两个真问题（写下来，别让 P3 重新踩）

### 7.1 `Text(String变量)` 与 `GlassButton(_ title: String)` 都不查表

`Text` 只有在**字面量**上才会自动得到 `LocalizedStringKey`。凡是
`Text(someString)`、`GlassButton("…")`（它的 init 收的是 `String`）、
`SemanticBadge(text:role:)` 这类"组件收 String 再 `Text(变量)`"的路径，
**登记了译文也不会变**——这是双语最容易的空转：机制通了、表也翻了、界面一个字没动。

`Theme.Page.Header` 已经按这个改过（`Text(LocalizedStringKey(title))`）。
其余组件不能照抄这一行，原因是下一条。

### 7.2 把组件入参改成 `LocalizedStringKey` 会在两类调用点上崩

- **非字面量实参**：`GlassButton(isExpanded ? "收起" : "展开")`（依赖分析页）
  是三元表达式，不是字符串字面量，`LocalizedStringKey` 只 conform
  `ExpressibleByStringLiteral`，编译不过；改成 `LocalizedStringKey(variable)`
  又落到 7.3 的风险里。
- **枚举 rawValue**：`SemanticBadge(item.severity.rawValue, …)`、
  `DataReadout(value: …)` 这类值来自 `String` 枚举，**根本没有字面量可供当键**。

### 7.3 因此：`LocalizedStringKey(变量)` 这条路要先解决 `%` 再走

本仓大量文案含百分号（「95% 的提交由 …」「100% = 全部核心跑满」）。
`Text` 带实参时会走 `String(format:)`，一个裸 `%` 后面跟非转换字符，
轻则输出被截、重则崩。所以**含 `%` 的串不能机械地塞进 `LocalizedStringKey(变量)`**。

P3 的做法定下来是：给这类"值来自枚举/变量"的文案建**显式映射**
（`enum LogSeverity { var uiLabel: LocalizedStringKey { … } }`，
键仍是中文原文、写在字面量位置上），而不是把组件入参换成 `LocalizedStringKey` 后到处强转。
这样 `%` 只出现在字面量里，与今天 `Text("95% …")` 的行为完全一致，不引入新风险。

## 9. 实测：裸 `%` 会被 `String(format:)` **静默吃掉**（不是崩溃）

```
$ swift /tmp/pct.swift
[95% 的提交由 Tcoder Team 一人完成] -> [95 的提交由 Tcoder Team 一人完成]  相同=false
[100% = 全部核心跑满]              -> [100 = 全部核心跑满]                相同=false
[50%% 安全写法]                    -> [50% 安全写法]                      相同=false
```

比"会崩"更糟：**不报错、只是把数字后面的百分号删掉**。
「95% 的提交由一人完成」变成「95 的提交由一人完成」—— 一个诚实性陈述被静默改义。
今天没踩到，是因为 `Text("95% …")` 这种**无实参的字面量**不走 format 这条路；
一旦某个串经由 `Text(LocalizedStringKey(变量))` 或带实参的插值字面量走 format，就会中招。

由此定两条硬规矩：
1. **不许把组件入参从 `String` 机械改成 `LocalizedStringKey`**（见 §7.2 的两类崩点），
   枚举/变量来源的文案走显式 `var uiLabel: LocalizedStringKey`，让 `%` 只出现在字面量位置。
2. **守卫查键值两端的格式占位符必须一致**
   （`LocalizationGuardTests.test_catalogPlaceholdersMatch`）：
   键里有 `%@` / `%lld` 而值里没有（或反过来、或顺序不同）就红。
   这条抓的是"翻译时把占位符翻丢/写错"，是机翻最常见的静默错误。
   裸 `%`（后面不跟转换字符）不算占位符，所以「95% …」这类中文键今天就能过。
