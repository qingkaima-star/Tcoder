## §184 开第十二卷，并把「写盘」补进 T5 的同步 I/O 词表（`.write(to:)` 此前只抓读、不抓写）

**为什么这一节属于本目标**：判据③ 的原话是「body/Mark 内**零同步 I/O**」，
而 T5 那条 `syncFileIO` 的词表里只有**读**的形状（`Data(String)(contentsOf:)`、
`contentsOfDirectory`、`attributesOfItem`、`fileExists`、`stat`、路径解析、起子进程），
**一个写盘的形状都没有**——`§182`/`§183` 未闭里都挂着这一条（`.write(to:` 那族）。
写盘和读盘在这件事上一样贵，`.atomic` 那一路还多一次 `rename`。

**先量会不会当场点红**（#65 立下的前置：补词表之前先读现量，别拿门禁当探针）：
`.write(to` 在**扫描面**（`Views/**` ＋ `Design/**`）里只有 **1 处**，位置是
`Design/LocalizedCopyKit.swift` 的 `flush()`——那是一个普通方法，既不是 `var body:` 也不是 `Chart {`，
而该文件**没有任何跨度**，所以跨度扫描对它是空集；`Services/**` 里那 4 处
（`ProjectStore` 三处报告/注册表/历史落盘 ＋ `CLIOutput` 一处重定向输出）
本来就在这条判据的作用面之外——**它管的是渲染路径，不是所有 I/O**。
⇒ 加词**零代价**：上限仍 `1/1`（那一格真债是 §72 留下的 `LogsView` 计算属性，未变），
新增形状今天不抓到人，只是把"以后写了会被抓"这句话变成真的。

**落了什么**：

1. 词表补 `.write(to…):` 一族形状（raw string 里是 `\.write\(to(?:URL)?:`），
   一条正则同时命中 `Data.write(to:options:)` 与 `String.write(to:atomically:encoding:)` 两种真形状；
2. `syncFileIO` 的**坏样例**跟着补两行（两种真形状各一行）——这条既有牙
   （`testScannerFiresOnBadSamples`）会在模式打不中时当场红，不用新造判据；
3. spec §D 里 T5 那句枚举补上「`.write(to:)` 写盘」，让"读与写都在这一条里"写在权威文档上，
   而不只写在注释里（`syncPrefs` 那段的原话就是"真实射程写在 spec 里，不靠注释撑"）；
4. **牙在同一天第二次兑现**（第一次是 §182 那两条）：我第一版用文本手术往那条正则**中间**插字符，
   把 Swift 的 raw string 收尾 `"#` 弄成了 `":,"#` ⇒ 模式末尾多吃到一个 `",`，
   **编译照过、门禁照绿**，只有 `testScannerFiresOnBadSamples` 把它打回来
   （原话还是那句「规则「syncFileIO」命中不了坏样例，它已经废了」）。
   ⇒ 两条记法：① 含 raw string 的那一行要**整行替换**，不要在中间插字符；
   ② 换完先在本地把模式从源码里抠出来、拿四个样例（两新一旧）跑一遍再进编译——
   本轮就是这么验的：四个全中，且**旧的两条不 regress**（防止把 `resolvingSymlinks` 那一族改废）。

**回执**：`--filter PerfHitch` ⇒ `Executed 22 tests, with 0 failures`，
台账行仍是 `syncFileIO 1/1`（**加词之后一处没多抓** ⇒ 与 19:09 那次现读一致：今天是零代价加面）。
**一条边界（防止把粗尺当成好尺）**：只加带 `to`/`toURL` 标签的 `.write(`，
**不**加裸 `write(`——后者会打到 `FileHandle.write(Data…)`、`Text(...)` 上的同名方法等
不属于"同步落盘"的形状，那是第 24 类「会误报的粗尺不上闸」正对着的形状：
误报会把人训练成"红了就忽略"。宁可窄一点，等真出现别的写盘形状再按同一套现读流程补。

## §185 反向探针自己也要被验：变异那一格现在过三道关（改没改进文件、输出变没变、红是不是这条判据撞的）

**为什么这一格在本目标里**：完成标准是"测得准、解释准"，而 selfcheck 里那些**反向格**（故意把尺子改坏、
要求它必须变红）是"测得准"这句话唯一的机器读者。它们此前只看一件事：**变异之后退出码非零**。
单向判据有两个空洞，本仓都记过账（第 46 类：产物为空也印「✓ 完成」；第 20 类：没读者的机制不算落地）：

1. **`sed -i ''` 在 macOS 上模式打不中就是静默落空**（不改文件、也不报错）⇒ "什么都没做"
   也可能满足"它红了"——红完全可能来自别的原因（夹具本身坏掉就算过一次）；
2. 更隐蔽的一层：**变异改进去了，但报告根本不读那一行** ⇒ 输出与变异前逐字相同，
   此时"红"与这条判据无关，把它算作牙，等于给守卫发一张空头的合格证。

**改了什么**（`perf_selfcheck_ruler_shapes.sh` 第 8 项 `selfcheck_migration`）：
变异前留一份快照 → ① `cmp` 断言**文件确实被改动**；② 抓变异前后的**完整输出逐字比**，
相同就直接报"这一格不算牙"并**不**去看退出码；③ 只有前两道过了，才有资格判红不红。
ok 那行同时把这件事印出来（**回执要能看出牙在哪**）：
「读不到守卫常量就炸（拒绝退回手抄正则）；且变异自己过「文件变了＋输出变了」两道验」。

**三格全部实测过**（不是两格＋一格推理）：

| 格 | 造法 | 尺子说什么 |
|---|---|---|
| 正格 | 原样跑（真把 `coarsePattern` 改名） | 两行 ✓，`oks=2 fails=0` |
| 变异落空 | 把 sed 的搜索串改成一个不存在的名字 | ✗「变异没改进文件（sed 静默落空）——这一格从「有牙」退化成「什么都没做」」 |
| 惰性变异 | 往夹具里加一个**报告不读**的常量，只改它 | ✗「变异之后输出与变异前逐字相同 ⇒ 那句「读不到守卫常量」根本没发生」 |

后两格都在 `/tmp` 的脚本副本上造（`mig_harness.sh` 把这一项单独 source 出来跑），
**没有动交付物**，也**没有**把"验不到"写成"已验"。

## §191 冷启动那条「字典/字符串 churn」找到了承载者：我们自己的私有类型把窗口自动保存键变成每构建换一次，实测 3608 键 / 1.53 MB

**为什么这一节属于本目标**：§177 把启动后半段（1551~3851 ms）的叶子自耗时归因写成

**先说量到的事实**（全部由一次性脚本直接读 `~/Library/Preferences/com.tcoder.monitor.plist`，
用仓里已有的探针与 plist 口径，不是估算）：

| 读数 | 值 |
|---|---|
| 顶层键数 | **3608** |
| 域大小 | **1,613,978 字节**（≈1.53 MB） |
| `NSWindow Frame*` | 1574 条（564,684 字节，36.8%） |
| `NSSplitView Subview Frames*` | 2030 条（966,456 字节，63.0%） |
| 其余键（真正属于用户状态的） | **只有 5 条**（2,868 字节，0.2%） |
| 不同「构建地址」个数 | **2029** |

键名长这样（一条实测样本，去掉无关部分）：

```
NSWindow Frame SwiftUI.ModifiedContent<…TcoderMonitor.RootView,
  SwiftUI._EnvironmentKeyWritingModifier<Optional<TcoderMonitor.AppState>>>,
  SwiftUI._FlexFrameLayout>, SwiftUI._BackgroundModifier<
  TcoderMonitor.(unknown context at $100e3f7a8).CaptureWindowSizer>>-1-AppWindow-1
```

**根因是我们自己写的字**：`App/TcoderMonitorApp.swift` 里那个
`private struct CaptureWindowSizer`（2026-09-21 为「取证窗口要能开高」加的）。
Swift 给**文件私有作用域里的类型**生成的名字带一段 `(unknown context at $<地址>)`，
而这个地址随每次构建的二进制布局变 ⇒ **每构建一次，SwiftUI/AppKit 的窗口自动保存键就换一个**，
旧键永不再被读取、也永不清理。实测三条互相咬合的证据：
① 1574 个类型名对应 1574 条键（**每个恰好一条** ⇒ 没有任何键被复用）；
② 不同地址 2029 个；
③ 键名里除 `CaptureWindowSizer` 那一段以外其余部分（`RootView`／`_FlexFrameLayout`／
`_EnvironmentKeyWritingModifier`）**逐字相同**。
⇒ 一句话：**是我们把一个类型声明成 `private`，把每用户一次的窗口几何记忆变成了每构建一次的垃圾**。

**这正好是 §177 那把尺子的形状**：启动时 AppKit 要把这整个域读进来，
并按当前那个 320 字符长的键在 3608 条字典里查找——`objectForKey:` + 长字符串 `isEqual:` +
`memcmp`。⇒ **假设**（还没证，别当结论用）：后半段那 42.1% 的字符串-字典 churn 的主要承载者
就是这个膨胀的 prefs 域，而不是"SwiftUI 天生如此"。

## §197 第 17 项吃的是宿主的构建产物：没建过 release 产物的树里它**假红**（当场挡住别的流的门禁）——顺手把「错配⇒拒」那一向钉成常驻臂

**怎么撞上的**：§195 末尾自己留了一句限度——「闸门组装层的『错配⇒拒』没有常驻臂」。
顺着这句话往下想了一步：装配层那一次真跑是在**我这棵树**上跑的，它读的现场是
`PERF_BIN` 的默认值 `$PWD/dist/Tcoder.app/Contents/MacOS/TcoderMonitor`。
⇒ 那么**没有 `dist/` 的树**里，这一项还剩什么？
这次没有推演，直接造现场：`git worktree add --detach .scratch/nodist-probe main`（头 `4096406`，
新建的树天然没有 gitignore 掉的 `dist/`）——

```
SCRATCH=$PWD/.scratch ./scripts/perf_harness.sh selfcheck        # rc=1
  ✗ 六维全合格却被拒 ⇒ 又造出一条永远不可能通过的闸门
```

**成因链（三节，缺一节都不红）**：① `perf_selfcheck.sh` 是被 `perf_harness.sh` **source 进同一进程**的，
所以 harness 那行 `PERF_BIN=` 默认值在 selfcheck 里是活的；② `preflight_gates_identity` 的内容对账
取的是 `${TARGET_BINARY:-${PERF_BIN:-}}`；③ 没产物 ⇒ `被量的二进制不在场` ⇒ `hard=1`
⇒ 矩阵的「全合格⇒放行」这一行判红。**红的话术还指错地方**（说闸门恒拒，其实是夹具没现场）。

**分母（这次不靠印象）**：`git worktree list` 逐棵数 `dist/RELEASE_MANIFEST.env` 在场与否——
11 棵树里 **4 棵没有**：`.worktrees/x6-scale`、`.scratch/selfscan-1845/after`、
`.scratch/selfscan-1845/before`、`/Users/one/WorkBuddy/Worktrees/Tcoder/main-3128694f`。
其中 **`ws/x6-scale` 是一棵要过门禁的活跃流树** ⇒ 这条假红不是理论风险，是**此刻堵着别人**。

**修法（三处，判据一条不放宽）**：
1. 把「manifest 出处」收成**唯一一个可覆盖点**，放在 `provenance_manifest_value`（唯一的读点）里：
   `PROVENANCE_MANIFEST` 未设时仍是 `dist/RELEASE_MANIFEST.env` ⇒ 真实测量一字不变。
   ⚠ 刻意**不**在 `provenance_binary_matches` 里再填一份默认值——同一件事两把手尺子的老账（本卷开头就记过）。
2. 第 17 项**自带现场**：`$out/provenance-fixture/` 里放两枚内容不同的假产物（A/B）＋一份只记 A 的 manifest，
   `gate_feed` 把 `TARGET_BINARY` 指过去 ⇒ 这一项不再读宿主的 `dist/`。
   顺带一条 bash 账：`gate_feed` 里是**裸赋值**，改的是全局 ⇒ 项末必须把
   `TARGET_BINARY`／`PERF_BIN`／`PROVENANCE_MANIFEST` 还回去，不然后面的项读到我那枚 10 字节的假文件。
3. §195 未闭① 因此可闭：矩阵多一行「内容与 manifest 不符 ⇒ 拒」（用 B 那枚）。

**双向验收（都在真环境里跑，不是"应该没问题"）**：
```
无 dist 的树（.scratch/nodist-probe，头 4096406）    修前：✗ 六维全合格却被拒（rc=1）
                                                    修后：◇ selfcheck：79 项通过，0 项失败（rc=0）
破坏验证（把内容对账改成永远 return 0）              ◇ 77 项通过，5 项失败
                                                    ✗ …却在装配层没闸   ← 新增那一行有牙
                                                    ✗ 第 14 项四格（函数层的臂照旧在）
复原后                                              ◇ 79 项通过，0 项失败
有 dist 的树（本流树，产物 dac2d7e）                 ◇ 79 项通过，0 项失败 ← 反向没退化
出处读点三向：默认=dac2d7ed15e…／PROVENANCE_MANIFEST=/tmp/nope.env→空／显式第二参数=dac2d7ed15e…
真产物对真 manifest 的内容对账：rc=0
```

**这一族的教训（写通用，不写这一次）**：一条守卫**只在"宿主机恰好有某物"的环境里绿过**，
就等于从没在无它的环境里跑过。本仓已有的形状都是"夹具继承宿主身份"的兄弟：
第 17 项继承 `PERF_BIN`、上一轮第 17 项的 manifest 继承同一次构建（§195 查到的那格），
以及 .scratch 夹具落在仓库树内会继承宿主 git 身份。**判据不是"它绿了"，是"它在缺环境量的树里也绿"。**
所以往后加夹具时的自问句：**这枚夹具要的现场，是我给的，还是机器恰好有的？**
