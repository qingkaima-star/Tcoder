### 58.3 真因与修法（全部有代码在位为证）

旧形状：`CoverageAnalyzer.classify(url:)` 拿 **绝对路径** 做子串匹配判 unit / integration / combined。
而用例的夹具根是 `NSTemporaryDirectory()/tcoder-cov-<UUID>`——那串 UUID 是十六进制，
含 `e2e` 的概率约 **0.7%**（32 字符 × 30 个三字符窗口 × 1/16³）。命中时**整棵夹具**被判成「集成测试」
⇒ `metrics.unit` 变 nil，而用例写的是 `metrics.unit?.linePercent ?? 0`
⇒ 断言报「期望 78.0、实得 0.0」。**同一份夹具两次跑出两个数**，与执行顺序无关。
这里有两层错叠在一起：判据吃了环境量（根因），`?? 0` 又把「读不到」伪装成 0（表现层，见 58.5）。

- **修**：`e3723e2` 把签名换成 `classify(url:root:)`，只看**被扫根之内**的相对路径；切不出来一律 `.combined`（**不猜**）。
- **守卫**：`91c9af3` 的 `testAmbientDirectoryNamesNeverLeakIntoKindOrNumbers`（把沙箱**直接命名**成
  `e2e-integration-test-fixture` 与 `plain-fixture` 各跑一次，比归类与读数）。
- 旧用例被 R5 拆成两条后继（`testUnitAndIntegrationWithoutLineRecordsProduceNoFakeUnion`
  与 `testUnitAndIntegrationWithLineRecordsAreUnioned`），断言的是同一批不变式，**不是改名混过去**。

### 58.4 定向复现实验：不必赌那 0.7%

做法是把 `classify` 在 **detached 探针树**里退回旧形状（`scoped = url.path`），跑那两类名沙箱——
必中，而且不用重烧整套：

```

  → Executed 18 tests, with 0 failures        rc=0
破坏（只改那一行，同一条命令）

       ("2") ≠ ("1")        —— 同一批内容换沙箱名就换归类 ⇒ 环境名字漏进了判定：[.integration, .unit]
       (.integration) ≠ (.combined)   —— 相对路径里没有那些目录段 ⇒ 本该不猜，却猜了
       ("Optional(1)") ≠ ("Optional(2)") —— 两种沙箱名各跑一次才算对比
```

⇒ 守卫**有牙**（三条断言各中一次，且 203 那行的输出把两个 kind 直接印出来了）。

修 + 反例守卫 ✔（外加 `CoverageNoSilentDropTests` 里那条「刚写下的合法报告不许保持沉默」双向钉）。
**⇒ RD-39 结案**，不再挂 R5c。

### 58.5 顺出来的新案 RD-62：「没标注」被渲染成「没有报告」

`classify` 不再猜之后，「报告存在但没标注类别」（`.combined`）成了**常态**——这正是上一节
破坏实验里第二条断言钉住的行为（一份普通的 `coverage/lcov.info` 必须判 `.combined`）。
而消费侧 `DashboardView` 覆盖率那张卡里的「单元测试 / 集成测试」两格只有两种取值：
该 kind 有报告 ⇒ 百分数；否则 ⇒ 写死「无报告」。

⇒ 一个项目明明有覆盖率报告、总覆盖率那一格有数，「单元测试 / 集成测试」两格却写「无报告」，
读的人只会得出「这个项目没跑单测」——**「没标注」被写成了「没有」**，与「读不到不许渲染成已删除」同族。
表现层修法方向（**不动判据、只补三态**）：区分「有 `.combined` 报告但未标类别」与「一份报告都没有」，
走同一张卡上「生产码行覆盖」那一格已经在用的 `DataAbsence` 三态出口；验收要含一条真夹具用例
（写一份普通 lcov ⇒ 两格不得写「无报告」），并登记新增文案进双语目录。屏上实拍未做
（AGENTS 2.1/2.2：起 App 要单独授权），所以这一条只到「代码 + 模型层证据」。

## 59. RD-63：对表抓出来的**真红**被记成了「抖动」——点名样本吃的是到达顺序

R25b 交回 RD-60 时全量有 6 处红，它把 `test_guiAndCliReportTheSameCrashEvidence` 归为
「不碰崩溃文案的顺序敏感抖动，一行没修」。这个归属**对了一半**：确实与 RD-60 的文案无关，
但"抖动"两个字把一条真缺陷放走了。按卷二 §14 立过的规矩先复跑定性：

```
cd TcoderMonitor && for i in 1 2 3; do ./scripts/locked_build.sh test --filter CrashEvidenceParityTests; done
趟 1 rc=1  ✗ shares[0].samplePaths[0]: 'Sources/Cart.swift' vs 'Sources/Ledger.swift'（4 处）
趟 2 rc=1  ✗ 同上，但**方向反过来**（GUI 给 Cart、CLI 给 Ledger）
趟 3 rc=0  两处都不等 ⇒ 0 处
```

⇒ 三趟两红一绿、**方向会变**，这不是"环境偶然"，是**取样规则本身把偶然写进了读数**：
`SourceRoleTally.init(of:)` 按"文件被递进累计器的顺序"取前 `exampleLimit` 条点名样本，
而并发扫描下这个顺序是调度的产物。与 RD-54（跳过台账的命中样本清单顺序不可复现）同族。

**修（总工窄修 `b1b68db`，改一行）**：累计前先按 `relativePath` 升序。累计量全是加法、与顺序无关，
所以这条排序只改"点哪几条名"，不改任何读数（行数守恒那条用例照旧绿）。
守卫 `SourceRoleTruthTests.testExamplesAreChosenByPathNotByEncounterOrder`：
**正序递与逆序递必须点出同一批名**，期望值由测试自己排序算出，并断言 `exampleLimit` 真被撞到
（否则这条绿是空转）。修后复跑三趟：`14 例 / 0 失败` ×3。

**⇒ 一条可复用的判据（与 RD-39 配成对，写在这里免得下次又走偏）**：
- RD-39 是**输入的名字**进了判定（绝对路径里的随机 UUID 改了归类）；
- RD-63 是**输入的顺序**进了判定（并发调度改了点名）。
- 两者都不是"偶发"，都是确定性缺陷。**"两趟读数一致"永远不构成确定性的证明**；
  要证确定性必须**喂两种相反的顺序并要求同一结果**——这个形状比"重跑 N 次看有没有红"便宜，也不会被运气骗。
