## 1. 开始之前：先理解「三种状态」

这是一款监控工具，最常见的误读不是算错，而是**把「没查」看成「没问题」**。
所以全 App 的数字只有三种状态，看懂这三行就够了：

| 状态 | 界面上长什么样 | 该怎么读 |
|---|---|---|
| ① 测到了 | 一个具体数字，可能是真实的 0 | 「本次测得 0 次崩溃」——0 本身就是结论 |
| ② 查了，但没东西 | `0` 且说明里写明「已完成扫描 / 未发现」（该句式出自《40 WS-H 设计语言规范》§7.3） | 确实扫过了，只是没有匹配项 |
| ③ 没查 / 查不了 | 显示 `--`，不是 0、也不是绿色对勾 | 还不知道。`--` 定义在 `Design/ThemeTokens.swift:16` |

占位符 `--` 的渲染在 `Design/SharedComponents.swift:135`。
**只要看到 `--`，就意味着这个数字眼下不存在**，不要脑补成 0，也不要当成好消息。
最需要警惕的是「依赖分析」页的漏洞数——第 4.1 节专门讲它。

### 内置示例项目不是真实测量

侧栏可以「加载示例项目」，它叫「Tcoder 示例项目」，里面**所有数字都是预先写死的一组样例**
（例如 2,351 个代码文件、224,900 行、1,842 次提交、124 个错误——
见 `Services/Demo/DemoData.swift:58,59,119` 与 `:163-166`），
**不是对你机器上任何目录的测量结果**。它的作用是让新人在没添加项目前也能看到完整界面长什么样。

⚠ 一个重要提醒：示例标记目前**只在两处**能看到——侧栏项目名旁的「示例」徽标
（`Views/Shell/ProjectSidebar.swift:97-100`）和性能页标题旁的「示例」标签
（`Views/Performance/PerformanceView.swift:50`）。
**总览、代码规模、复杂度风险、Git 洞察、贡献者、健康评分这六页不带任何标记**，
数值却全是写死的样例；错误日志页只有切换时间窗口时才弹出提示
「示例项目使用内置固定数据，时间窗口不影响结果。」（`Views/Logs/LogsView.swift:170-171`）。
所以：**看懂界面之后请立刻换成自己的项目**，别拿示例项目的分数当真。
（性能页是例外：它永远读实时数据，示例项目也一样显示你机器的真实 CPU/内存，
见 `Views/Performance/PerformanceView.swift:20-22`。）

## 2. 上手

### 2.1 安装

1. 由开发机构建后产出可双击的 App：`dist/Tcoder Monitor.app`
   （打包名来自 `scripts/build_app.sh:8` `BUNDLE_NAME="Tcoder Monitor.app"`；
   构建命令见 README「构建与运行」）。
2. 双击它即可。要求 Apple Silicon 机型、macOS 14 及以上（README 首节的「仅 arm64 · macOS 14+」）。
3. 首次打开若出现 macOS 提示「无法验证开发者」一类弹窗，是 ad-hoc 签名的正常现象
   （打包只做本地签名 `codesign --force --sign -`，`scripts/build_app.sh:62`）。
4. 关于权限：本 App **没有开启 macOS 沙盒**，也没有申请任何额外权限
   （`Resources/Info.plist` 里既无 `com.apple.security.app-sandbox` 也无用途描述键，
   仓库内没有 `.entitlements` 文件），因此平时不需要授权它读文件。
   唯一例外是系统级保护目录：按 README「已知限制」——
   **首次扫描 `~/Documents`、`~/Desktop` 下的目录时，macOS 可能弹一次文件访问授权**，批准即可。

### 2.2 添加项目（三种入口，效果相同）

| 入口 | 位置 |
|---|---|
| 「添加项目」 | 侧栏底部按钮，`Views/Shell/ProjectSidebar.swift:72` |
| 「选择目录…」 | 还没有项目时的空态大按钮，`ProjectSidebar.swift:39` |
| 「添加项目…」⌘O | 顶部菜单「文件」区，`App/TcoderMonitorApp.swift:16-19` |

点开的是系统的**目录选择器**（只能选文件夹、不能多选，`ProjectSidebar.swift:54-62`）。
**不支持把文件夹拖进窗口**——全仓没有拖放接收逻辑。
想先看看界面长什么样，就用「加载示例项目 (Tcoder 示例项目)」（`App/TcoderMonitorApp.swift:21`），
但它显示的是写死的样例数字，见第 1 节的提醒。

选中一个从未分析过的项目时会**自动开始一次扫描**（`Views/ProjectDetailView.swift:47-50`；
示例项目不会，因为它本来就自带数据）。

### 2.3 重新分析

按钮统一叫「重新分析」，出现在这些地方：窗口工具栏（`Views/RootView.swift:36`，
悬停说明「对当前项目重新执行全部分析器」）、菜单 ⌘R（`App/TcoderMonitorApp.swift:27-30`）、
以及健康评分页（`Views/Health/HealthView.swift:177`）、依赖分析页（`Views/Dependencies/DependenciesView.swift:334`）、
错误日志页（`Views/Logs/LogsView.swift:92`）里的同名按钮。
性能页另有一个「重新采样」（`Views/Performance/PerformanceView.swift:56`），它只刷一次实时读数。

扫描中会看到进度遮罩，文字是「项目名 · 阶段」（`Design/SharedComponents.swift:265`），
阶段依次为「正在扫描代码规模…」「正在分析 Git 历史…」「正在解析错误日志…」
「正在检查依赖…」「正在计算健康评分…」（`SharedComponents.swift:276-286`）。
**分析器是串行跑的，大仓库第一次扫要等一会儿**，属正常现象。

某一步失败时：总览页出现「未能完成：代码扫描、Git 分析…」横幅并给一个「重试」按钮
（`Views/DashboardView.swift:293-301,313`）；错误日志页顶部会显示具体失败原因
（`Views/Logs/LogsView.swift:41-43`）。给示例项目点重扫会被拒：「示例项目已内置数据，无需扫描。」
（`App/AppState.swift:102-103`）。

### 2.4 移除项目、数据存在哪、怎么清空

- 移除：侧栏项目行**右键 →「移除」**（`ProjectSidebar.swift:28`）。
  没有「清空全部项目」按钮。
- 落盘位置：`~/Library/Application Support/TcoderMonitor/`
  （`Services/ProjectStore.swift:27-31`），里面是 `projects.json`（项目列表）、
  `score-history.json`（评分历史）、`reports/<项目 UUID>.json`（每份分析报告）
  （`ProjectStore.swift:124-130`）。
- 清空：删掉上面那个目录即可。「移除」单个项目时会连带删掉它的报告文件
  （`ProjectStore.swift:65-70`）。

## 3. 九页逐页说明

页面名称取自侧栏（`Views/Shell/SectionNav.swift:15-23`），从上到下依次是：
**总览、代码规模、复杂度风险、Git 洞察、贡献者、性能监控、错误日志、依赖分析、健康评分。**

### 3.1 总览

- **给我看什么**：健康评分环 + 四枚读数（CPU、内存、今日错误、最近提交）+ 代码规模与语言占比、
  实时性能迷你曲线、最近提交、高频错误、测试覆盖率（README「功能」表首行）。
  健康环取的是本次评分的综合分（`Views/DashboardView.swift:18` → `Views/Shell/DashboardHero.swift:95-97`），
  没评过分则画空心环加 `--`（`DashboardHero.swift:11-12,55`）。
- **数字怎么算**：本页不产生新数字，全部是其余页面的汇总。
  「今日错误」= 趋势里与**当天**同一个桶的 错误+异常+崩溃 之和
  （`Models/LogInsights.swift:23-26`），按天分桶用的是**你本机的时区**
  （`Services/Logs/LogClustering.swift:264`）。
- **什么时候会不准**：某一项分析失败时，本页对应的读数会退回 `--` 或走空态；
  先看横幅有没有「未能完成：…」。示例项目下本页数字全是样例。

### 3.2 代码规模

- **给我看什么**：四张磁贴「代码文件 / 代码行数 / 注释行数 / 空行数」
  （`Views/Code/CodeMetricsView.swift:77,85,93,101`）、
  总行数、语言分布、TODO / FIXME、最大文件榜。
- **数字怎么算**：每一行被归为空行 / 注释行 / 代码行三类之一
  （`Services/Code/SourceFileClassifier.swift:5-8`，逐文件计数 `:109`），
  汇总后满足界面上那句「总行数（= 空行 + 注释 + 代码）」，页面上会自行核对这条不变式
  （`CodeMetricsView.swift:135,201-226`）。
- **什么时候会不准**：扫描有硬上限，超限部分是**静默不计入**的，数字会偏小——
  最多 60,000 个文件、单文件最大 2,000,000 字节（`Models/Project.swift:97-98`）、
  单文件最多计到 200,000 行（`SourceFileClassifier.swift:39`）；
  `.git`、`node_modules`、`build`、`DerivedData`、`Pods`、`logs` 等目录直接跳过
  （`Project.swift:105-112`），二进制后缀不读（`:114-119`）。
  榜单本身也截断：最大文件只列 20 个、语言只列前 8 种（`CodeMetricsView.swift:14-15`）。

### 3.3 复杂度风险

- **给我看什么**：平均圈复杂度、圈复杂度最高的函数榜、超长/巨大文件与拆分建议、
  **重复代码率**与重复块明细（卡标题「重复代码率」，`Views/Code/CodeRiskView.swift:113`）。
- **数字怎么算**：
  - 圈复杂度：函数基线 1，命中一个分支关键字就 +1。计入的关键字表在
    `Services/Code/ComplexityCounting.swift:18-21`
    （`if`、`elif`、`for`、`while`、`case`、`when`、`catch`、`except`、`guard`、`match`、`and`、`or` 等），
    `&&`、`||`、`??`、`?.`、三元 `? :` 也各计一次（`:58-103`），`#if` 这类预处理行不计（`:35-40`）。
    函数边界识别见 `Services/Code/FunctionRecognition.swift`。
  - 重复代码率：把每行归一化（数字/字符串/标识符折成 N/S/I）后取 **6 行滑动窗口**指纹
    （`Services/Code/DuplicationEngine.swift:12`），在全库找同指纹片段，再用原文相似度确认；
    分子是被克隆覆盖的代码行并集，分母是全部有效代码行（口径总说明 `:46-61`）。
  - 风险分档：函数严重 CC≥31、高≥21、中≥11；超过 50 行算超长函数；
    文件 1,500 / 800 / 400 行分别是严重 / 高 / 中（`Services/Code/FileSystemCodeAnalyzer.swift:202-208`）。
- **什么时候会不准**：
  - **重复代码率会低估**。代码里自己写明了两处：单文件参与滑窗的归一化行硬截断在 20,000 行
    （`DuplicationEngine.swift:23`）；同一文件内每行形状都相同的表格式代码（例如生成的数据表）
    整段自拷贝进不了比率，注释里给的实测原话是「实测这种合成文件（100 行 × 2 份）报 0%」（`:141`）；
    只有一个文件的项目整体不参评（`files.count >= 2`，`:75-77`）。
  - YAML / JSON / Markdown / SQL 这类没有函数体的文件，圈复杂度算不出条目
    （`Services/Code/ComplexityEngine.swift:39-40` 直接返回空），
    所以「函数榜是空的」**不等于没有复杂度**，可能只是这门语言的写法识别不了。
  - 重复块明细只列 20 个（`DuplicationEngine.swift:24`），但注释说明比率本身不受这个截断影响（`:55-57`）。

### 3.4 Git 洞察

- **给我看什么**：五枚磁贴「总提交数 / 作者统计基准 / 项目年龄（窗口内时叫「窗口跨度」）/
  最近修改 / 活跃作者（截断时叫「窗口内作者」）」（`Views/Git/GitInsightsView.swift:45,53,63,71,78`）、
  提交趋势、「24×7 活跃分布」、仓库信息（当前分支 / HEAD / 远端）、最近提交列表
  （`GitInsightsSections.swift:124,208,240-248`）。
- **数字怎么算**：
  - 提交总数走 `git rev-list --count HEAD`，**含合并提交**。
  - 作者、增删行、趋势、时段分布走另一条命令 `git log --no-merges -n <窗口>`，
    **不含合并提交**（`Services/Git/ShellGitAnalyzer.swift:44-45`），窗口上限 20,000 条
    （`:17`），最近提交列表只展示 20 条（`:19`）。
  - 24×7 热力按**每位作者自己提交时的本地时区**合并，不做时区归一
    （界面说明 `GitInsightsSections.swift:232`，实现口径 `Services/Git/GitAggregation.swift:15-16,70,86,96`）。
    也就是说跨时区团队的作息会被混在同一格里。
  - 仓库识别：先试你选的目录，再向上最多找 6 层父目录、向下最多进 3 层子目录找 `.git`
    （`ShellGitAnalyzer.swift:22,24`，嵌套候选上限 20 个 `:26`）。
- **什么时候会不准**：
  - **总数和作者榜对不上是设计如此**，页面顶部有常驻口径条解释（见第 4.2 节）。
  - **历史被窗口截断时**，趋势 / 时段 / 作者占比都只是「最近 2 万次非合并提交」这一段
    （2 万即 `ShellGitAnalyzer.swift:17` 的窗口上限，界面那句文案把它填成实际条数），
    页面会在相关卡标题后追加「 · 近 N 次提交窗口内」，并把「首次提交」改标为
    「窗口起点，非仓库首次提交」（`Views/CodeGit/GitHistoryScope.swift:130-131`、
    `Views/Git/GitInsightsSections.swift:276`）。
  - 目录选在 monorepo 的子目录时，探路会成功但 `git log` 不带路径限定，
    **显示的是整个 monorepo 的历史**，不是你选的那份代码。
  - `git log` 有 60 秒硬超时（`ShellGitAnalyzer.swift:53`）。超时会抛错，
    本轮 Git 结果整块置空，页面上退回「尚未分析 Git 历史」，
    上一轮成功拿到的 Git 数据**不会保留**——这是已知行为，见第 6 节 FAQ。

### 3.5 贡献者

- **给我看什么**：贡献者排行（`Views/Git/ContributorsView.swift:169`）与
  「贡献集中度」= Bus Factor（`:204-206`，形如「Bus Factor 3 · 前 3 名合计 78%」）。
  每人展示排名、提交次数、增/删行、活跃时段。
- **数字怎么算**：按提交数降序排列，同分按显示名（`Views/Git/ContributorRows.swift:10-15`）；
  默认最多展示 30 人（`ContributorsView.swift:164`），其余合并成一行
  「另有 N 位贡献者未展示」（`:182`）。占比的分母是**非合并提交数**，
  悬停说明原样写着「占非合并提交 N 次的比例」（`ContributorRows.swift:134`）。
  Bus Factor 取前 3 名合计（至少 1），风险等级按榜首占比：>0.7 高、>0.5 中，
  单人且样本 >50 次判严重（`ContributorRows.swift:44-52`）。
- **什么时候会不准**：**同一个人是按 email 认的，不是按名字**
  （`Services/Git/GitAggregation.swift:13-14,37-43`：只按规范化后的邮箱合并，
  显示名取该邮箱**最后一次提交**里的名字）。
  后果有两个方向：`张三 <a@x>` 与 `张三 <b@x>` 会被算成**两个人**；
  而 `张三 <a@x>` 与 `Zhang San <a@x>` 会被并成**一个人**，且页面上显示的是后改的那个名字。
  空仓库或历史里只有不带作者的合并提交时给空态（`Views/Git/ContributorsView.swift:18-19`）；
  「未知作者」是提交里没填作者信息的那些（`Views/Git/ContributorRows.swift:19`）。
  所有统计同样受 3.4 的窗口与 `--no-merges` 口径影响。

### 3.6 性能监控（杀手功能）

- **给我看什么**：系统四指标 CPU / 内存 / 磁盘 / 网络 + 实时曲线 +
  卡标题为「工程进程组」的分组网格（副标题「按匹配模式在全系统进程中查找，与所选项目无关」，
  `Views/Performance/PerformanceView.swift:155`）+ 进程占用排行表 + 底部「匹配模式」编辑器（`:237`）。
  页面明确标注：**「只读展示，不提供任何进程操作」**（`PerformanceView.swift:180`）。
- **数字怎么算**：
  - 采样每 1,500 毫秒一次（`App/AppState.swift:36`），历史环形缓冲存 600 点
    （`Services/Performance/MachSystemMonitor.swift:36`），曲线只画最近 90 点
    （`PerformanceView.swift:17`）。可「暂停」/「继续」（`:59`），
    暂停时顶部常驻黄条：「采样已暂停：下方数值为最后一次采集结果，点击「继续」恢复实时刷新。」（`:30`）。
  - CPU = 1 − 空闲增量 / 总增量，逐核差分（`Services/Performance/SystemSampler.swift:103-127`）。
  - **内存口径与活动监视器一致**：已用 = 总量 −（free + speculative + purgeable）
    （`SystemSampler.swift:24-27,128-138`，注释解释 inactive 仍算已用）。
  - 磁盘取 IOKit `IOBlockStorageDriver` 的读写字节累计再按秒差分（`:245-267`），
    **不按进程累加**（原因写在 `:239-244`）；网络取各网卡收发字节求和、排除 `lo0`（`:289-308`），
    计数器只有 32 位精度，跨零点做了 2³² 补正（`:156-167`）。
  - 内存压力三档：≥0.85「紧张」、≥0.7「偏高」、否则「正常」（`SystemSampler.swift:169-173`）。
  - 进程分组：对进程名与命令行做**大小写不敏感的包含匹配**
    （`MachSystemMonitor.swift:51-58`），说明文案
    「匹配模式对进程名与命令行做包含匹配，例如 java、nginx、mysqld。」（`PerformanceView.swift:246`）。
    内置 5 组：Java 服务 / Node 服务 / MySQL / Redis / Nginx（`Models/Performance.swift:89-95`，
    界面上标「内置」`PerformanceView.swift:266`）。
- **什么时候会不准**：
  - **没有 root 时逐进程指标只覆盖当前用户可见的进程**，页面如实写
    「只读展示 · 已取指标 X / 全系统 Y 个进程」（`PerformanceView.swift:181`）；
    进程**总数**走 `sysctl(KERN_PROC_ALL)`（`Services/Performance/ProcessInspector.swift:51-64`），
    与 `top` / `ps -A` 同源。句柄数受时间预算时还会追加
    「句柄数因时间预算仅覆盖部分进程」（`PerformanceView.swift:183`；预算 fd 600ms / sweep 1500ms，
    `ProcessInspector.swift:40-42`）。
  - 分组未命中任何进程时给的是说明而不是四个 0：「未检测到匹配进程」（`:386`）。
  - 采样在后台跑时点「重新采样」会拿到上一帧（`Services/Performance/MachSystemMonitor.swift:113-116`），
    刷新没变就是它在跑，不是坏了。
  - 内存取数失败时压力档给「未知」而不是猜一个：`MemoryPressure.unknown`
    （`Models/Performance.swift:37-40`）由采样路径在 `available == false` 时产出
    （`Services/Performance/SystemSampler.swift:199-203`），并由
    `PerformanceMemoryHonestyTests` 两条用例钉住。没有读数既不是「正常」也不是「紧张」。

### 3.7 错误日志

- **给我看什么**：错误 / 异常 / 崩溃 / 警告 四个计数、错误趋势、
  「高频错误」聚类列表（这一页卡标题目前仍是英文原文「Top Errors」，
  `Views/Logs/LogsView.swift:346`；总览页同一概念已叫「高频错误」，
  `Views/DashboardView.swift:215`）、受影响源文件、已扫描文件清单。
- **数字怎么算**：解析三类来源——项目内递归找 `.log` / `.out` / `.ips`
  （`Logs/` 目录下额外接受 `txt`、`err`、`trace`、`logrotate` 与无后缀文件，
  `Services/Logs/LogDiscovery.swift:192-202`）、`~/Library/Logs/<项目名>/*.log`（`:138-149`）、
  `~/Library/Logs/DiagnosticReports/*.ips` 且**只认文件名主名等于项目名**的那些（`:151-170`）。
  也可以手动附加：工具栏里用系统文件选择器挑 `error.log`、`crash.log` 等
  （`Views/Logs/LogsView.swift:180-200`）。
  每条高频错误展示 级别 + 签名 + 次数 + 原文 + 「第一次: … · 最近: …」，
  可展开样例行与堆栈顶帧（`LogsView.swift:500-594`）。
- **什么时候会不准**：
  - 工具栏「时间窗口」（最近 1/3/7/14/30 天，默认 7 天，`LogsView.swift:117-122`、
    `App/AppState.swift:26`）**只真正作用于崩溃报告（`.ips`）的筛选与趋势分桶**
    （`LogDiscovery.swift:158,166-168`、`Services/Logs/FileLogAnalyzer.swift:14,19`）。
    项目内的日志文件不按窗口过滤，所以「异常 N」可能覆盖全部历史。
    切换窗口会自动重新分析（悬停说明 `LogsView.swift:128`）。
  - 读取有上限：单文件 20,000,000 字节 / 50,000 行、最多发现 60 个文件、
    高频错误取 20 类（`FileLogAnalyzer.swift:7-10`）；已扫描文件表最多列 40 行（`:19`）。
  - 日志格式千奇百怪，签名聚类靠规则，同一问题的不同写法可能被拆成两类。

### 3.8 依赖分析

- **给我看什么**：页面上方第一张卡是「分析选项」（联网开关 + 「重新分析」，
  `Views/Dependencies/DependenciesView.swift:20-24,327-334`）；
  然后是四枚读数「依赖总数 / 运行时 · 开发 / 版本过旧 / 漏洞数」（`:77-105`）、
  「风险总览」（`:131`）、按生态分组的依赖表、「安全公告」（`:277`）。
  每行依赖右侧有五种状态之一：
  **「有漏洞」「过旧」「正常」「仅版本比对」「未核对」**
  （`Views/Dependencies/DependencyVerdictRows.swift:38-42`）。
- **数字怎么算**：
  - 支持的清单文件共 16 个文件名：`package.json`、`pom.xml`、`build.gradle`、`build.gradle.kts`、
    `settings.gradle`、`settings.gradle.kts`、`Package.swift`、`requirements.txt`、`pyproject.toml`、
    `setup.py`、`Pipfile`、`go.mod`、`Cargo.toml`、`Podfile`、`Gemfile`、`packages.config`
    （`Services/Dependencies/ManifestParsers.swift:36-53`；`requirements*.txt` 变体按 Python 处理，`:58-61`）。
    扫描深度不超过 6 层、不跟随符号链接、Maven 多模块最多展开 200 个
    （`ManifestDependencyAnalyzer.swift:11,12,100`）。
  - **依赖总数只算清单里直接声明的**，不含锁文件解析出的传递依赖
    （界面原话 `DependenciesView.swift:81`），锁文件只在旁边标注「只说明可复现，未计入依赖数」（`:203`）。
  - 每个生态默认只显示 40 行，其余收进「展开其余 N 项」（`:189,253-256`）。
- **什么时候会不准**：**这一页是「没查 ≠ 安全」最容易翻车的地方，必读第 4.1 节。**
  另外版本新旧判定依赖内置版本快照，快照没收录的包返回「未核对」而不是「过旧」
  （`Services/Dependencies/DependencySnapshot.swift:23-24` 注释：没把握的包一律不收录，查不到返回 nil）。

### 3.9 健康评分

- **给我看什么**：分数环 + 等级 + 趋势 + 一句结论，旁边一句常驻声明
  「启发式加权计算，未调用外部模型」（常量定义 `Views/Health/HealthView.swift:27`，渲染在 `:165`）；
  「维度分量」表（`:246-250`）；缺失维度披露（`:315-327`）；优点 / 问题 / 建议；「评分趋势」（`:479`）。
- **数字怎么算**：综合分 = Σ(维度得分 × 归一化权重)，全部由本机规则从扫描结果算出，
  **不访问网络、不调用任何外部模型**（悬停说明原样是这句，`HealthView.swift:169`）。
  九个维度与各自的原始权重（`Models/HealthScore.swift:38-47,51-59`）：

  | 维度 | 原始权重 | 维度 | 原始权重 |
  |---|---|---|---|
  | 复杂度 | 0.18 | 提交活跃度 | 0.12 |
  | 运行稳定性 | 0.16 | 依赖健康 | 0.10 |
  | 代码质量 | 0.14 | 测试覆盖 | 0.10 |
  | 重复度 | 0.13 | 注释与可维护性 | 0.08 |
  | 协作分布 | 0.09 | | |

  ⚠ 这九个原始权重加起来是 **1.10**，不是 1.0（详见第 4.4 节与第 7 节待确认清单）。
  各维度的打分锚点表在 `Services/Health/ScoreCurves.swift`，测试覆盖的分段得分在
  `Services/Health/WeightedHealthScorer.swift:221-228`。
  等级边界：A ≥85、B 70–84、C 55–69、D 40–54、E <40（`Models/Project.swift:43-48`）。
- **什么时候会不准**：分数低不一定是项目差，很可能是**有维度没证据可计分**（第 4.4 节）。
  反过来，「运行稳定性」在**没扫到任何日志**时仍会计分，但走的是默认值 85
  （`ScoreCurves.swift:236-238`，detail 会写「未扫描到运行日志，本维度按默认值计」）——
  这一维度看着正常，其实没依据。全部维度都缺证据时不给分：
  综合分 0 只代表「无数据」（`HealthView.swift:197,203-204`）。
  「评分趋势」在只有 1 个历史点时是空的，提示「至少完成两次分析后可以看到趋势。」（`:503-505`）。

## 4. 数据口径（看到数字前先读这节）

README 的「数据口径」一节已列了骨架，这里补齐**为什么**和**界面上具体长什么样**。

### 4.1 「0 个漏洞」有三种含义

判定逻辑在 `Views/Dependencies/DependencyVerdictRows.swift:92-104`：
先看命中数，再看**是否真的做过比对**（字段 `hasVulnerabilityCoverage`，
定义 `Models/DependencyReport.swift:47-49`）。三种情形：

| 情形 | 界面上的说法 | 你该怎么读 |
|---|---|---|
| 有命中 | 「命中 N 条内置快照与安全公告」 | 真有问题，按公告升级 |
| 做过比对、零命中 | 「全部 N 项已比对，未发现已知漏洞」或「X / Y 项已比对，未发现已知漏洞」 | 这才是「干净」这个结论 |
| 没联网也没拿到任何在线公告 | 「未联网核对，仅内置快照（覆盖 npm / Maven / Python）· X / Y 项有版本数据」，可能还带「未覆盖生态：…」 | **未判定，不是安全** |

只有第二种允许出现绿色「安全」类结论（代码里那个唯一判据叫 `mayClaimSafe`，
`DependencyVerdictRows.swift:106-110`）。漏洞数读数的后缀也会随之变成
「条已核对」或「条（未核对）」（`DependenciesView.swift:147`）。
未核对徽标悬停原文：「默认不联网时漏洞判定恒为 0 条，这是「没有查」，不是「没有病」。」
（`DependencyVerdictRows.swift:169`）。

**内置离线漏洞规则一共 10 条，只写了 npm（2 条）、Maven（5 条）、Python（3 条）三个生态**
（`Services/Dependencies/VulnerabilitySource.swift:69-222`，逐条 CVE 编号见 `:72,89,106,124,140,156,174,190,206,222`）；
Gradle 与 Maven 坐标互通所以也受益（`Services/Dependencies/DependencySnapshot.swift:61-67`）。
**SwiftPM、CocoaPods、Go、Cargo、RubyGems、NuGet 在离线时没有任何漏洞结论可给**。

再退一步，**在线核对也救不了全部**：OSV 侧只支持 npm / Maven(含 Gradle) / PyPI / Go / crates.io /
RubyGems / NuGet，**SwiftPM 与 CocoaPods 连在线都不查**
（`Services/Dependencies/DependencyNetworkLookup.swift:33-39`），
界面在这种情况下会直说「本项目没有可在线查询的生态（SwiftPM / CocoaPods 不在 OSV 覆盖范围内）」
（`Services/Dependencies/ManifestDependencyAnalyzer.swift:291`）。

还有一层：版本号写成 `"*"`、`workspace:*`、分支名、修订号这类**无法比较**的值会被跳过，
不参与比对（离线侧 `ManifestDependencyAnalyzer.swift:216,222`），
所以「X / Y 项有版本数据」里的 Y−X 就是这部分。

内置快照有截止日期（代码里是 2026-09-19，`DependencySnapshot.swift:25`），
**但这个日期目前没有显示在任何页面上**——离线结论有多旧，得看本文或代码（见第 7 节）。

### 4.2 提交总数 ≠ 作者榜求和，这是设计如此

「总提交数」含合并提交，作者榜与增删行用 `--no-merges` 统计。
Git 洞察页顶部有一条常驻口径条把差额讲清（`Views/Git/GitInsightsSections.swift:99-111`），
三种文案：

- 未打满窗口：「N（含 M 次合并）· 作者与代码行统计基于 K 次非合并提交」
  ——此时差额**全部**是合并提交（`Views/CodeGit/GitHistoryScope.swift:31-33,85-86`）。
- 打满了窗口：「… 作者与代码行统计只覆盖最近 K 次非合并提交，更早的历史未纳入」
  ——差额 = 合并提交 **+ 没读到的更早历史**，不能全算成合并（`:34-35,90-92`）。
- 旧报告里没有基准字段：明说「这份报告没有记录非合并提交数…口径未知」（`:36-38,94`）。

### 4.3 大仓库的历史是按窗口分析的

窗口上限 20,000 条非合并提交（`ShellGitAnalyzer.swift:17`）。
超限时页面做三件事：磁贴标题改成「窗口跨度」「窗口内作者」（`GitInsightsView.swift:63,78`）、
卡标题追加「 · 近 N 次提交窗口内」（`GitHistoryScope.swift:118,130-131`）、
口径条用警告色并补一句「趋势、时段分布与作者占比都只是这段窗口的分布，不代表全部历史。」
（`GitInsightsSections.swift:111`）。
**注意**：这个「是否截断」在界面里用的是派生判据 `isWindowTruncated`
（`GitHistoryScope.swift:65-67`，只在非合并窗口打满时为真），
而**不是**契约字段 `GitInsights.historyTruncated`——后者被合并提交污染，两者不等价。
所以本文按界面行为描述，不按字段名描述。

### 4.4 健康评分：缺证据不给分，权重等比摊分

缺证据的维度直接 `return nil`，**不进分量表、不参与计分、也不得分**
（`WeightedHealthScorer.swift:16,87,117,140,150,197,200,219` 八处缺席分支）。
然后评分器把分量表的权重**除以在场权重之和**归一到 1.0，使界面顶部那句「综合分 = Σ(得分 × 归一化权重)」能复现综合分
（`:44-48`）。界面对应两句原话：
「缺失维度不参与计分也不得分，其权重已按比例摊到在场维度。」+ 明细
「（复杂度 18%→33% · …）」（`HealthView.swift:323,382-389`）；
一个维度都不缺时改说「这次扫描的输入覆盖了全部可计分维度，权重未做摊分。」（`:316`）。

哪些情况会让维度缺席（这一条直接决定你的分数）：

| 维度 | 计分的最低证据 | 出处 |
|---|---|---|
| 代码质量 / 复杂度 / 重复度 / 注释 | 代码扫描有结果；「代码质量」还要求文件数 >0；「复杂度」要求至少测到函数体 | `WeightedHealthScorer.swift:87,117` |
| 提交活跃度 / 协作分布 | 有 Git 数据且提交数 >0；「协作分布」另需榜首作者 | `:140,150` |
| 运行稳定性 | 有日志数据在场（没扫到日志仍计分，但走默认 85） | `:164`、`ScoreCurves.swift:236-238` |
| 依赖健康 | 依赖数 >0 **且漏洞核对状态为已核对**；未核对或查询失败整维缺席 | `:188,192-200`、`ScoreCurves.swift:27-32` |
| 测试覆盖 | 仓库真的产出了覆盖率报告且有行分母 | `:218-219`、`Models/CoverageMetrics.swift:13,20-21` |

两个容易忽略的后果：

1. 「依赖健康」默认离线时**必然缺席**（未核对 → 不计分），所以离线扫描的综合分
   不含这一维度，权重被摊到别的维度上（提示文案「开启「联网核对」后重扫才有结论。」，
   `WeightedHealthScorer.swift:195`）。
2. 「未调用外部模型」这句声明**只限评分本身**，不代表整个 App 不联网——
   依赖页的在线核对是真会发请求的（第 5 节）。

### 4.5 内存口径

已用内存 = 总量 −（free + speculative + purgeable），**与活动监视器一致**；
inactive（文件缓存）**仍算已用**，所以这个数会比你以为的"真实占用"大
（`Services/Performance/SystemSampler.swift:128-138`，注释就写明了这一点）。
页大小取 `vm_kernel_page_size`，Apple Silicon 上是 16 KB（`:213`）。
极端情况有兜底：若可回收量算出来不小于总量（内核页计数瞬时不一致），
退化为 `active + wired + compressed`（`:134-136`）。
另有一个已知风险：`host_statistics64` 调用失败时页计数全为 0，会让内存显示成接近 100% 占满
（《20 WS-D 诚实性审计》P1 #10）——真看到内存瞬间打满且曲线是一条竖线，先怀疑这个。

### 4.6 覆盖率只读现成报告，不代跑测试

「覆盖率」这一页/这块**不会执行你的测试**：分析器只做「解析已存在的报告文件」，
代码注释原话「Nothing here runs a test suite — it only parses existing reports」
（`Services/Coverage/CoverageAnalyzer.swift:7-8`）。全仓唯一的子进程调用是 `git`
（`Utilities/SharedUtilities.swift:46`，调用方只有 `Services/Git/ShellGitAnalyzer.swift:376`），
没有任何跑测试的路径。

- 认得五种报告（文件名白名单 `Services/Coverage/CoverageAnalyzer.swift:12-15`，
  按名分派 `:80-88`）：`lcov.info` / `lcov.dat`、`coverage-summary.json`（istanbul / nyc）、
  `jacoco.xml` / `jacocoTestReport.xml`、`coverage.xml`（coverage.py）、`clover.xml`。
- 发现限制：深度 ≤6、最多 40 个文件、单文件 ≤20,000,000 字节
  （`:51,10`）。
- **聚合只取分母最大的 6 份**报告（`:256` `prefix(6)`）。多模块仓库里「整体行覆盖」
  实际是这 6 份的合计，不是全项目。
- **没有报告时是空态，不是 0%**：`hasData == false` 就不画（`CoverageMetrics.swift:13`），
  总览页原话「测试覆盖率只在仓库真出了报告时才出现，没报告就不画，避免读成一个假的 0%。」
  （`Views/DashboardView.swift:248`）。这条口径由 `Tests/TcoderMonitorTests/RealRepositoryEvidenceTests.swift`
  钉住（见 README「验收脚手架」）。

## 5. 隐私

1. **全部分析在本机完成，不上传任何源码内容**（README「数据与隐私」）。
2. **在线查询默认关闭**，需要手动开：开关在「依赖分析」页第一张卡「分析选项」里，
   标题「分析时联网查询最新版本与漏洞库」（`App/AppState.swift:25` 默认 `false`；
   界面 `Views/Dependencies/DependenciesView.swift:330`）。
   开启后**不会立刻生效**，页面就写着「开启后需要重新执行分析才会生效。」（`:349`），
   必须再点一次「重新分析」。
3. **会连哪些地址**：只有 npm registry 与 OSV.dev，域名写死在代码里
   （`Services/Dependencies/DependencyNetworkLookup.swift:128-129`），不带 cookie、不缓存会话
   （`:311-319`）。npm 侧是 GET；**OSV 的批量查询接口是 POST**，
   请求体里只有包名与版本这一类查询条件（`Services/Dependencies/OsvClient.swift:129,197`）。
   换句话说：只读语义，但不是"只发 GET"。
4. **超时**：单次请求硬超时 5 秒（`DependencyNetworkLookup.swift:115-116`，npm 与 OSV 共用这一个常量）。
   但 npm 与 OSV 是**串行**发起的（先 `await` npm 再 `await` OSV，
   `ManifestDependencyAnalyzer.swift:258,274`），所以整个在线阶段最长接近 10 秒而不是 5 秒
   （README「数据与隐私」实测值：黑洞地址下两边各 5.006s）。
   超时/失败会降级为内置离线快照并在页面写明，例如
   「OSV 查询超过 5 秒硬超时，本次在线漏洞结果整体放弃（含已取回但未来得及返回的公告）」
   （`DependencyNetworkLookup.swift:202-203`）、「达到时间预算，剩余 N 个包未查询」（`NpmClient.swift:17`）。
5. **进程监控只读**：不向任何进程发信号、不 kill、不重启、不附加调试器
   （纪律注释 `Services/Performance/ProcessInspector.swift:7-10`；界面声明
   `Views/Performance/PerformanceView.swift:180,237`「只读展示 / 只读观测」）。
   用到的系统调用只有 `proc_listallpids` / `proc_pidinfo` / `proc_pid_rusage` / `sysctl`
   这类查询接口（`ProcessInspector.swift:54,61,72,187,196,206,214,221,230,277`）。
   仓库里唯一的 `terminate()` 是给**自己起的 git 子进程**做超时收尾的
   （`Utilities/SharedUtilities.swift:46,95`），与外部进程无关。
6. **本 App 没有 macOS 沙盒**（第 2.1 节），意味着它能读到你选中的目录树里的东西——
   所以**只添加你打算被扫描的目录**。

## 6. 常见问题

**Q：我的健康分比预期低，是不是项目真这么差？**
先看「维度分量」表和缺失维度那一句。缺证据的维度**不给分也不白送分**，
它的权重会被摊到别的维度上（第 4.4 节）。常见拉分点：没跑过覆盖率（「测试覆盖」缺席）、
没开联网核对（「依赖健康」缺席）、非 Git 目录（两个 Git 维度缺席）。
这些情况下你的分数不是"项目得分"，而是"在场指标的得分"。

**Q：依赖页为什么全是「未核对」？**
两种原因：①没开联网开关（默认关，`App/AppState.swift:25`），或开了但没重新分析
（「开启后需要重新执行分析才会生效。」，`DependenciesView.swift:349`）；
②该生态没有内置规则——离线只有 npm / Maven / Python 共 10 条
（`VulnerabilitySource.swift:69-222`），SwiftPM 与 CocoaPods **连在线都不查**
（`DependencyNetworkLookup.swift:39`）。这是"没查"，不是"安全"。

**Q：第一次扫描很慢？**
正常。代码扫描要遍历目录树（上限 60,000 文件，`Models/Project.swift:97`）、
Git 要读最多 20,000 条提交的历史（`ShellGitAnalyzer.swift:17`）、日志要扫最多 60 个文件
（`FileLogAnalyzer.swift:9`），而这些阶段是**串行**跑的
（阶段文案 `Design/SharedComponents.swift:276-286`）。
开了联网再叠最长约 10 秒（第 5 节第 4 条）。

**Q：「总提交数」和贡献者页的提交加起来对不上？**
不是 bug，差额就是合并提交（或更早的未读历史），Git 页顶部的「提交统计口径」条会直接告诉你
差额是多少、以及作者榜是基于多少个非合并提交算的（第 4.2 节）。

**Q：Git 页突然变成「尚未分析 Git 历史」，之前的数据没了？**
最可能是那次 `git log` 撞上 60 秒超时（`ShellGitAnalyzer.swift:53`）。
本轮失败时上一轮的 Git 结果**不会被保留**（`App/AppState.swift:148-150` 每次新建报告），
页面会退回未分析空态（`GitInsightsSections.swift:15-18`），总览页同时给一条
「未能完成：Git 分析」并可点重试（`Views/DashboardView.swift:293-313`）。
大仓库建议接上电源后重试；**这一条是已知缺陷，不是你的操作问题**（见第 7 节）。

**Q：数据存在哪里？怎么清空？**
`~/Library/Application Support/TcoderMonitor/`（`Services/ProjectStore.swift:27-31`），
删掉这个目录即全清；只想撤一个项目就用侧栏右键「移除」（`ProjectSidebar.swift:28`）。

**Q：为什么性能页的内存比 `top` 显示的大？**
口径不同但和活动监视器一致：文件缓存的 inactive 页也算已用（第 4.5 节）。

**Q：示例项目的分数能拿去汇报吗？**
不能。那是 `DemoData.swift` 里写死的样例数字（第 1 节），
而且示例项目**点「重新分析」是无效的**（「示例项目已内置数据，无需扫描。」，
`AppState.swift:102-103`）。
