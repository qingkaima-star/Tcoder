# Tcoder 项目监控 · 使用说明

面向**使用者**的说明书：怎么装、每一页在看什么、数字是怎么算出来的、什么时候会不准。
不需要会写代码。

- 想**构建、打包、跑测试、取证**？请看仓库根 [`README.md`](../README.md) 的「构建与运行」
  与「验收脚手架」两节，本文不重复那些命令。
- 并行开发规约见 [`TcoderMonitor/AGENTS.md`](../TcoderMonitor/AGENTS.md)。
- 文中路径相对 `TcoderMonitor/`。代码出处一律写**符号锚点**（`类型.成员`，同名成员遍地时写
  `文件名.类型.成员`），不钉行号——规约见 `AGENTS.md` §4.6，由 `DocReferenceRatchetTests` 机器校验；
  同段内省写的 `:NNN` 回指该段最近的那个文件名，越不越界由 `DocBareLineReferenceTests` 逐条核验。
  界面引号「」里的字，都是页面上原样能看到的中文。

## 1. 开始之前：先理解「四种状态」

这是一款监控工具，最常见的误读不是算错，而是**把「没查」看成「没问题」**。
所以全 App 的数字只有四种状态，看懂这四行就够了：

| 状态 | 界面上长什么样 | 该怎么读 |
|---|---|---|
| ① 测到了 | 一个具体数字，可能是真实的 0 | 「本次测得 0 次崩溃」——0 本身就是结论 |
| ② 查了，但没东西 | 数字位是 `0`，说明里写明「已完成扫描 / 未发现」；日期、名称这类不能写 0 的格子给「无记录」 | 确实扫过了，只是没有匹配项（`DataAbsence.measuredEmpty`） |
| ③ 查了，但算不出来 | 显示「算不出」——**不是** `--`，也不是 `0` | 扫描做过了，可是分母是 0（总行数 0、函数数 0、非合并提交 0），这个比值没有定义（`DataAbsence.indeterminate`，悬停会点出分母） |
| ④ 没查 / 查不了 | 显示 `--`，不是 0、也不是绿色对勾 | 还不知道：没扫、没采到帧、不适用（`DataAbsence.notAnalysed`；`--` 这个字面本体是 `Theme.Placeholder.missingValue`） |

四态的字面只有**一处**定义：`DataAbsence.display`（文件在 `Sources/TcoderMonitor/Design/` 下的 `DataAbsence.swift`）；
文字格子走 `DataAbsence.textDisplay`，悬停说明走 `DataAbsence.help`，
磁贴的缺值渲染 `MetricTile.displayValue` 也取它。
**只要看到 `--`，就意味着这个数字眼下没被查到**，不要脑补成 0，也不要当成好消息；
看到「算不出」则相反——我们查过了，是这个项目的这一项没法算（例如一个函数都没识别出来，
平均圈复杂度就没有分母）。最需要警惕的是「依赖分析」页的漏洞数——第 4.1 节专门讲它。

### 内置示例项目不是真实测量

侧栏可以「加载示例项目」，它叫「Tcoder 示例项目」，里面**所有数字都是预先写死的一组样例**
（例如 2,351 个代码文件、224,900 行、1,842 次提交、124 个错误——
见 `DemoData.swift` 的 `DemoData.codeMetrics`、`DemoData.gitInsights`、`DemoData.logSummary` 三处写死），
**不是对你机器上任何目录的测量结果**。它的作用是让新人在没添加项目前也能看到完整界面长什么样。

⚠ 一个重要提醒：示例标记目前出现在**四处**——侧栏项目名旁的「示例」徽标
（`ProjectSidebar.ProjectRow.body`）、性能监控页（`PerformanceView.header`）、
错误日志页（`LogsView.header`）、健康评分页（`HealthView.header`）的「示例」标签。
**其余六页不带任何标记**：总览、代码规模、复杂度风险、Git 洞察、贡献者、依赖分析——
数值却全是写死的样例；错误日志页另有一句只在切时间窗口时才弹出的提示
「示例项目使用内置固定数据，时间窗口不影响结果。」（`LogsView.rescanForNewWindow`）。
所以：**看懂界面之后请立刻换成自己的项目**，别拿示例项目的分数当真。
（性能页是例外：它永远读实时数据，示例项目也一样显示你机器的真实 CPU/内存。）

## 2. 上手

### 2.1 安装

1. 由开发机构建后产出可双击的 App：`dist/Tcoder Monitor.app`
   （打包名来自 `scripts/build_app.sh` 里的 `BUNDLE_NAME="Tcoder Monitor.app"`；
   构建命令见 README「构建与运行」）。
2. 双击它即可。要求 Apple Silicon 机型、macOS 14 及以上（README 首节的「仅 arm64 · macOS 14+」）。
3. 首次打开若出现 macOS 提示「无法验证开发者」一类弹窗，是 ad-hoc 签名的正常现象
   （打包只做本地签名 `codesign --force --sign -`，见 `scripts/build_app.sh` 的签名步骤）。
4. 关于权限：本 App **没有开启 macOS 沙盒**，也没有申请任何额外权限
   （`Resources/Info.plist` 里既无 `com.apple.security.app-sandbox` 也无用途描述键，
   仓库内没有 `.entitlements` 文件），因此平时不需要授权它读文件。
   唯一例外是系统级保护目录：按 README「已知限制」——
   **首次扫描 `~/Documents`、`~/Desktop` 下的目录时，macOS 可能弹一次文件访问授权**，批准即可。

### 2.2 添加项目（三种入口，效果相同）

| 入口 | 位置 |
|---|---|
| 「添加项目」 | 侧栏底部按钮，`ProjectSidebar.sidebarFooter` |
| 「选择目录…」 | 还没有项目时的空态大按钮，`ProjectSidebar.AddProjectGuideCard.body` |
| 「添加项目…」⌘O | 顶部菜单「文件」区，`TcoderMonitorApp.body` 的 `.commands` 里 |
| **直接把文件夹拖进侧栏** | 支持，`ProjectSidebar.body`（`.dropDestination(for: URL.self)`） |

点开的是系统的**目录选择器**（只能选文件夹、不能多选）。拖拽也真的能加项目，
拖上去时侧栏会有高亮反馈（`ProjectSidebar.isDropTargeted`）。
想先看看界面长什么样，就用「加载示例项目 (Tcoder 示例项目)」（`ProjectSidebar.AddProjectGuideCard.body`、
菜单项同处 `TcoderMonitorApp.body`），但它显示的是写死的样例数字，见第 1 节的提醒。

选中一个从未分析过的项目时会**自动开始一次扫描**（`ProjectDetailView.maybeAutoScan`；
示例项目不会，因为它本来就自带数据）。

### 2.3 重新分析

按钮统一叫「重新分析」，出现在这些地方：窗口工具栏（`RootView.detailToolbar`，
悬停说明「对当前项目重新执行全部分析器」就写在同一个成员里）、菜单 ⌘R（`TcoderMonitorApp.body`）、
以及健康评分页（`HealthView.ScanControls.body`）、依赖分析页（`DependenciesView.NetworkOptionsCard.body`）、
错误日志页（`LogsView.controls`）里的同名按钮。
性能页另有一个「重新采样」（`PerformanceView.controls`），它只刷一次实时读数。

扫描中会看到进度遮罩，文字是「项目名 · 阶段」（`SharedComponents.swift` 的 `ProgressOverlay.body`），
阶段依次为「正在扫描代码规模…」「正在分析 Git 历史…」「正在解析错误日志…」
「正在检查依赖…」「正在计算健康评分…」（同一文件的 `AnalysisPhase.label`）。
**分析器是串行跑的，大仓库第一次扫要等一会儿**，属正常现象。

某一步失败时：总览页出现「未能完成：代码扫描、Git 分析…」横幅并给一个「重试」按钮
（`DashboardView.failureCard`）；错误日志页顶部会显示具体失败原因
（`LogsView.body`）。给示例项目点重扫会被拒：「示例项目已内置数据，无需扫描。」
（`AppState.swift` 的 `AppState.scan` 开头就拒）。

### 2.4 移除项目、数据存在哪、怎么清空

- 移除：侧栏项目行**右键 →「移除」**（`ProjectSidebar.rowContextMenu`）。没有「清空全部项目」按钮。
- 落盘位置：`~/Library/Application Support/TcoderMonitor/`（`ProjectStore.swift` 的
  `ProjectStore.storageDirectory`，解析规则在 `ProjectStore.resolveStorageDirectory`），里面是
  `projects.json`（项目列表）、`score-history.json`（评分历史）、`reports/<项目 UUID>.json`（每份分析报告；
  三个名字分别来自 `ProjectStore.registryURL`、`historyURL`、`reportsDirectory`）。
- 清空：删掉上面那个目录即可。「移除」单个项目时会连带删掉它的报告文件（同一个文件里的 `ProjectStore.remove`）。

## 3. 九页逐页说明

页面名称取自侧栏（`SectionNav.DetailSection`），从上到下依次是：
**总览、代码规模、复杂度风险、Git 洞察、贡献者、性能监控、错误日志、依赖分析、健康评分。**

### 3.0 本节举例用的真实数字（不是编的，也没用示例项目）

下面九行里出现的每个数字都是**真实测量结果**，来自两条既有取证：
`TCODER_REAL_REPO=1 … test --filter RealRepositoryEvidenceTests`（压测对象 `/opt/homebrew`）与
`SelfScanDogfoodTests`（用 Tcoder 扫 Tcoder 自己）。
**测量时间 2026-09-19 23:50，源码基线 `a4a4260`。**
此后 WS-M/WS-C 又改过分析器与界面，重跑数字会小幅漂移；`/opt/homebrew` 本身也在天天变。
所以这些数字用来说明**界面长什么样、该怎么读**，不要当成你机器上的复现值。

### 3.1 总览

- **给我看什么**：健康评分环 + 四枚读数（CPU、内存、今日错误、最近提交）+ 代码规模与语言占比、
  实时性能迷你曲线、最近提交、高频错误、测试覆盖率（README「功能」表首行）。
  健康环取的是本次评分的综合分（`DashboardView.body` → `DashboardHero.HealthHeroCard.body`），
  没评过分则画空心环加 `--`（`DashboardHero.HealthRing`）。
  测试覆盖率那一横条（`DashboardView.coverageStrip`）除了读数还带**两行口径小字**：
  一行说这个数是按什么口径算的（仅生产码），一行说这些数有多旧（最旧那份报告的生成时间）——
  两条分别见第 4.6 节的 #37 与 #38。
- **数字怎么算**：本页不产生新数字，全部是其余页面的汇总。
  「今日错误」= 趋势里与**当天**同一个桶的 错误+异常+崩溃 之和
  （`LogInsights.swift` 的 `LogSummary.todayErrorCount`），按天分桶用的是**你本机的时区**
  （`LogClustering.swift` 的 `LogAggregator.buckets`，走 `Calendar.current`）。
- **什么时候会不准**：某一项分析失败时，本页对应的读数会退回 `--` 或走空态；
  先看横幅有没有「未能完成：…」。示例项目下本页数字全是样例。

### 3.2 代码规模

- **给我看什么**：四张磁贴「代码文件 / 代码行数 / 注释行数 / 空行数」
  （`CodeMetricsView.CodeMetricsSummaryGrid.body`）、总行数、语言分布、TODO / FIXME、最大文件榜。
- **数字怎么算**：每一行被归为空行 / 注释行 / 代码行三类之一
  （`SourceFileClassifier.swift` 的 `SourceFileClassifier.SourceLineKind`，逐文件计数在 `SourceFileClassifier.classify`），
  汇总后满足界面上那句「总行数（= 空行 + 注释 + 代码）」，页面自己会核对这条不变式（`CodeMetricsView.CodeScaleSection.body`）。
- **什么时候会不准**：扫描有硬上限，超限部分是**静默不计入**的，数字会偏小——
  最多 60,000 个文件、单文件最大 2,000,000 字节（`Project.swift` 的 `ScanOptions.maxFiles`、`ScanOptions.maxFileBytes`）；
  单文件最多计到 200,000 行（`SourceFileClassifier.maximumLineCount`，超出只计前若干行并置
  `ScannedSourceFile.lineCountTruncated`）；`.git`、`node_modules`、`build`、`DerivedData`、`Pods`、`logs`
  等目录直接跳过（`ScanOptions.defaultSkipDirectories`），二进制后缀不读（`ScanOptions.defaultBinaryExtensions`）。
  榜单本身也截断：最大文件只列 20 个、语言只列前 8 种（`CodeMetricsView.languageHeadCount`）。

### 3.3 复杂度风险

- **给我看什么**：平均圈复杂度、圈复杂度最高的函数榜、超长/巨大文件与拆分建议、
  **重复代码率**与重复块明细（卡标题「重复代码率」，`CodeRiskView.CodeDuplicationSection.body`）。
- **数字怎么算**：
  - 圈复杂度：函数基线 1，命中一个分支关键字就 +1。关键字表在 `ComplexityCounting.swift` 的
    `ComplexityCounting.allBranchKeywords`（`if`、`elif`、`for`、`while`、`case`、`when`、`catch`、`except`、
    `guard`、`match`、`and`、`or` 等），`&&`、`||`、`??`、`?.`、三元 `? :` 也各计一次
    （`ComplexityCounting.branchSymbols`），`#if` 这类预处理行不计（`ComplexityCounting.complexity`）。
    函数边界识别见 `FunctionRecognition.swift`。
  - 重复代码率：把每行归一化（数字/字符串/标识符折成 N/S/I）后取 **6 行滑动窗口**指纹
    （`DuplicationEngine.swift` 的 `DuplicationEngine.windowSize`），在全库找同指纹片段，再用原文相似度确认；
    分子是被克隆覆盖的代码行并集、分母是全部有效代码行，且 `ratio = duplicatedCodeLines / totalCodeLines`
    不做二次截断（口径总说明写在 `DuplicationEngine.analyze` 的文档注释里）。
  - 风险分档：函数严重 CC≥31、高≥21、中≥11；超过 50 行算超长函数；文件 1,500 / 800 / 400 行分别是严重 / 高 / 中
    （`FileSystemCodeAnalyzer.swift` 的 `criticalFunctionComplexity`…`mediumFileLines` 一组常量）。
- **什么时候会不准**：
  - **重复代码率会低估**。代码里自己写明了两处：单文件参与滑窗的归一化行硬截断在 20,000 行
    （`DuplicationEngine.maxWindowedLines`）；同一文件内每行形状都相同的表格式代码（例如生成的数据表）
    整段自拷贝进不了比率，注释里给的实测原话是「实测这种合成文件（100 行 × 2 份）报 0%」（同一个 `analyze`）；
    只有一个文件的项目整体不参评（`files.count >= 2`）。
  - YAML / JSON / Markdown / SQL 这类没有函数体的文件，圈复杂度算不出条目
    （`ComplexityEngine.functions` 对识别不了的语言直接返回空数组），
    所以「函数榜是空的」**不等于没有复杂度**，可能只是这门语言的写法识别不了。
  - 重复块明细只列 20 个（`DuplicationEngine.maxBlocks`），但代码明说**比率不受这个截断影响**——
    因预算未展开成明细的拷贝窗口数单独记账，ratio 已含它们
    （计数在 `DuplicationResult.fragmentsDroppedByBudget`）。

### 3.4 Git 洞察

- **给我看什么**：五枚磁贴「总提交数 / 作者统计基准 / 项目年龄（窗口内时叫「窗口跨度」）/
  最近修改 / 活跃作者（截断时叫「窗口内作者」）」（`GitInsightsView.GitInsightsMetricGrid.body`）、
  提交趋势、「24×7 活跃分布」、仓库信息（当前分支 / HEAD / 远端）、最近提交列表
  （`GitInsightsSections.GitCommitScopeSection.message`）。
- **数字怎么算**：
  - 提交总数走 `git rev-list --count HEAD`，**含合并提交**。
  - 作者、增删行、趋势、时段分布走另一条命令 `git log --no-merges -n <窗口>`，
    **不含合并提交**（`ShellGitAnalyzer.swift` 的 `ShellGitAnalyzer.logArguments`），窗口上限 20,000 条
    （`ShellGitAnalyzer.maxCommits`），最近提交列表只展示 20 条（`ShellGitAnalyzer.recentCommitLimit`）。
  - 24×7 热力按**每位作者自己提交时的本地时区**合并，不做时区归一（界面说明 `GitInsightsSections.GitActivitySection.body`，
    实现口径 `GitAggregation.activityByHour` 与 `GitAggregation.activityByWeekday`，时区契约写在 `GitAggregation.swift` 顶部注释里）。
    也就是说跨时区团队的作息会被混在同一格里。
  - 仓库识别：先试你选的目录，再向上最多找 6 层父目录、向下最多进 3 层子目录找 `.git`
    （`ShellGitAnalyzer.swift` 的 `maxUpwardHops`、`maxNestedDepth`，嵌套候选上限 20 个 `maxNestedCandidates`）。
- **什么时候会不准**：
  - **总数和作者榜对不上是设计如此**，页面顶部有常驻口径条解释（见第 4.2 节）。
  - **历史被窗口截断时**，趋势 / 时段 / 作者占比都只是「最近 2 万次非合并提交」这一段
    （2 万即 `ShellGitAnalyzer.swift` 的 `ShellGitAnalyzer.maxCommits`，界面那句文案把它填成实际条数），
    页面会在相关卡标题后追加「 · 近 N 次提交窗口内」，并把「首次提交」改标为「窗口起点，非仓库首次提交」
    （`GitHistoryScope.windowSuffix`、`GitInsightsSections.GitRepositoryInfoSection.body`）。
  - 「首次提交」那一格有**两种**空，别读成同一种：是仓库、也确实一次提交都没有 → 写「无记录」
    （`DataAbsence.measuredEmpty`）；压根没跑 Git 分析、或这目录不是仓库 → 才写 `--`（`DataAbsence.notAnalysed`），
    实现见 `GitInsightsSections.GitRepositoryInfoSection.firstCommitCaption`。
  - 目录选在 monorepo 的子目录时，探路会成功但 `git log` 不带路径限定，
    **显示的是整个 monorepo 的历史**，不是你选的那份代码。
  - `git log` 有 60 秒硬超时（`ShellGitAnalyzer.swift` 的 `ShellGitAnalyzer.init` 里 `logTimeout` 的默认值）。
    超时会抛错，本轮 Git 结果整块置空，页面上退回「尚未分析 Git 历史」，
    上一轮成功拿到的 Git 数据**不会保留**——这是已知行为，见第 6 节 FAQ。

### 3.5 贡献者

- **给我看什么**：贡献者排行（`ContributorsView.ContributorRankingSection.body`）与
  「贡献集中度」= Bus Factor（`ContributorsView.ContributorConcentrationSection.body`，
  形如「Bus Factor 3 · 前 3 名合计 78%」）。
  每人展示排名、提交次数、增/删行、活跃时段。
- **数字怎么算**：按提交数降序排列，同分按显示名（`ContributorRows.ContributorAnalysis.sorted`）；
  默认最多展示 30 人（`ContributorsView.ContributorRankingSection.displayLimit`），其余合并成一行
  「另有 N 位贡献者未展示」（同一个 `body` 里）。占比的分母是**非合并提交数**，
  悬停说明原样写着「占非合并提交 N 次的比例」（`ContributorRows.ContributorRow.body`）。
  这个分母是 0 时（例如窗口里全是合并提交）占比一格写「算不出」而不是 `--`——
  这里没有「没查」这一说，是查了以后除法没有定义（`DataAbsence.indeterminate`）。
  Bus Factor 取前 3 名合计（至少 1），风险等级按榜首占比：>0.7 高、>0.5 中，
  单人且样本 >50 次判严重（`ContributorRows.ContributorAnalysis.busFactorRisk`）。
- **什么时候会不准**：**同一个人是按 email 认的，不是按名字**
  （`GitAggregation.swift` 的 `GitAggregation.authorStats`：只按 `GitLogParser.normalizeEmail`
  规范化后的邮箱合并，显示名取该邮箱**最后一次提交**里的名字）。
  后果有两个方向：`张三 <a@x>` 与 `张三 <b@x>` 会被算成**两个人**；
  而 `张三 <a@x>` 与 `Zhang San <a@x>` 会被并成**一个人**，且页面上显示的是后改的那个名字。
  空仓库或历史里只有不带作者的合并提交时给空态（`ContributorsView.body`）；
  「未知作者」是提交里没填作者信息的那些（`ContributorRows.ContributorAnalysis.displayName`）。
  所有统计同样受 3.4 的窗口与 `--no-merges` 口径影响。

### 3.6 性能监控（杀手功能）

- **给我看什么**：自上而下是工具条 → 状态横幅 → 系统四指标（CPU / 内存 / 磁盘 / 网络）→
  实时曲线 → **「进程分组」**卡（副标题「按匹配模式在全系统进程里查找，与所选项目无关」，
  `PerformanceProcessGroups.PerformanceProcessGroupsCard.body`）→「进程占用排行」表
  （`PerformanceProcessTable.PerformanceProcessTableCard.body`）→ 页底「匹配模式」编辑器
  （`PerformanceMatcherEditor.body`）。分区顺序写在
  `PerformanceView.swift` 顶部注释（版面顺序说明）里。
  页面明确标注：**「只读展示，不提供任何进程操作」**（`PerformanceProcessTable.PerformanceProcessTableCard.coverageNote`
  的兜底分支——拿不到下面那两个计数时页面只说这一句）。
- **数字怎么算**：
  - 采样每 1,500 毫秒一次（`AppState.swift` 的 `AppState.init`）；曲线是**画窗**而不是缓冲区——只画最近
    90 点 ≈ 135 秒（`PerformanceView.chartPointLimit`），底层环形缓冲存 600 帧
    （`MachSystemMonitor.swift` 的 `MachSystemMonitor.historyCapacity`）。按钮「重新采样」/「暂停」/「继续」在
    `PerformanceView.controls`，暂停时顶部那条常驻横幅「采样已暂停：下方为最后一次采集结果，
    点「继续」恢复实时刷新。」出自 `PerformanceView.statusBanners`。
  - CPU = 1 − 空闲增量 / 总增量，逐核差分（`SystemSampler.swift` 的 `SystemSampler.cpuUsage`，
    核数变化或计数器回退时该帧判为不可信 `:131,139-140`）。
  - **内存口径与活动监视器一致**：已用 = 总量 −（free + speculative + purgeable）（同一个
    `SystemSampler.swift` 的 `VmCounters.reclaimableBytes` 是可回收量、`:155-156` 口径注释、
    `SystemSampler.memoryUsedBytes` 是实现（`:160-168`），注释明说 inactive 是文件缓存但监视器仍计入已用）。
  - 磁盘走 IOKit `IOBlockStorageDriver` 的 `Bytes (Read)` / `Bytes (Write)` 累计再按秒差分
    （`SystemSampler.swift` 的 `BlockStorageSampler.ioBytes`，`:287-289,303-304`），**不按进程累加**——
    理由带着实测数字写在 `:283-286`（无权限时逐进程磁盘量恒 0，与 `top` 差三个数量级）。
  - 网络取各网卡 `ifi_ibytes` / `ifi_obytes` 求和（`SystemSampler.swift` 的 `SystemSampler.networkBytes`，
    `:331,346-347`），**排除 `lo0` 回环**（`:341-343`，理由：本机回环就有 247 GiB，算进去会把流量凭空翻几十倍）；
    本进程拿到的计数只有 32 位精度（`:323`），跨零点按 2³² 补回
    （`SystemSampler.bytesPerSecondHandling32BitWrap`，`:186-197`），并有一道合理性闸门：还原后速率超过
    50 GB/s 判为假回绕、退回 0（`:181,195`）。
  - **注意单位**：网络磁贴显示的是 **bit/s**（`PerformanceSystemTiles.networkTile`），磁盘磁贴是
    **Byte/s**（`PerformanceSystemTiles.diskTile`），两者不是一回事。
  - 内存压力四档「正常 / 偏高 / 紧张 / 未知」（`Models/Performance.swift` 的 `MemoryPressure`，`:37-40`）：
    ≥0.85 紧张、≥0.7 偏高、否则正常，取不到数时是未知（`SystemSampler.swift` 的 `SystemSampler.pressure`，`:201-205`）。
  - 进程分组的匹配模式是**不区分大小写的子串匹配，命中进程名或完整可执行路径**（`ProcessInspector.swift` 的
    `ProcessInspector.matches`，由 `ProcessInspector.groupSnapshots` 调用），界面说明「匹配模式对进程名与
    命令行做包含匹配，例如 java、nginx、mysqld。规则本身不改变任何进程。」（`PerformanceMatcherEditor.body`）。
    同一个 `PerformanceMatcherEditor.swift` 里还有输入框占位「匹配模式，例如 java」`:22`、
    「分组名称，例如 后端服务」`:25`、按钮「添加分组」`:28`。出厂自带 5 组（Java 服务 / Node 服务 / MySQL /
    Redis / Nginx，`Models/Performance.swift` 的 `TrackedProcessGroup.builtInDefaults`，`:89-95`），但**界面上
    不打「内置」标记、也不保护它们**——内置组同样可以被删掉（见第 7 节）。
  - 进程占用排行按 **CPU 核当量**（`1.00` 就是占满一个核）或按内存切换排序，两种口径都是全系统范围
    （`PerformanceProcessTable.ProcessSortKey`，它的 `title` 就是这两个列名），默认列 20 行（`PerformanceProcessTableCard.rowLimit`）。
- **什么时候会不准**：
  - **没有 root 时逐进程指标只覆盖当前用户可见的那部分进程**。两个数都与工具同源，本机 2026-09-20 实测：
    全系统 **789** 个（`ProcessInspector.swift` 的 `ProcessInspector.processCount`，走 `sysctl(KERN_PROC_ALL)`，
    与 `ps -axc | wc -l` 同一个数），一次 sweep 真取到指标的 **98** 个（`ProcessInspector.sweep`，
    子集口径见 `ProcessInspector.visibleProcessCount`）。页面把两个数都摊开写：「已取指标 N / 全系统 M 个
    进程 · 只读」（`PerformanceProcessTable.swift` 的 `PerformanceProcessTableCard.coverageNote`，为什么两个数
    都要写见 `PerformanceProcessTableCard.shown`，句柄列受预算时追加「 · 句柄列受时间预算限制」`:54`）。
    预算 fd 600ms / sweep 1500ms 是 `ProcessInspector.swift` 里的 `fdBudgetNanos`、`sweepBudgetNanos`，
    那里也写了为什么不能用 `proc_listallpids` 数总数。
  - 分组状态分四档「等待样本 / 采样暂停 / 零命中 / 命中中」（`PerformanceProcessGroups.swift` 的
    `PerformanceGroupCard.badgeText`，分工写在 `:5-6`），**刻意把"暂停中所以没数"和"真的零命中"分开**。
    零命中时是三段式说明而不是四个 0：「未检测到匹配进程」+「全系统 N 个进程里没有任何条目命中「pattern」…」+
    「确认该服务已启动，或在「匹配模式」里把规则改宽一点（例如从 mysqld 改成 mysql）。」（`:158-160`）。
    一个分组都没有时空态写「还没有分组规则」（`:30-31`）。
  - **曲线不足 3 个点不画**（`PerformanceLiveCharts.swift` 的 `PerformanceLiveCharts.minPointsToPlot`）；内存曲线
    还额外要求可信点 ≥3，否则只给「N/M 点可用」的说明。纵轴可能收窄成非 0 起点，卡面会明写（`:114-119`）——
    所以别把曲线的上下沿当成 0% 和 100%。
  - 采样在后台跑时点「重新采样」会拿到上一帧（`MachSystemMonitor.swift` 的 `MachSystemMonitor.sampleNow`），
    刷新没变就是它在跑，不是坏了。
  - **内存取不到数时既不画成 100% 也不画成 0%**：`host_statistics64` 失败时 `SystemSampler.vmCounters` 返回 nil
    （`SystemSampler.swift` 的 `:262,275`），`SystemSampler.memoryUsedBytes` 是可空返回（`:160-161`），
    压力档落 `.unknown`（`:100`，`:202`）；界面把这帧判为不可信、显示 `--` 并声明剔除了多少点
    （`LiveReadings.trustedMemoryPoints` 与 `rejectedMemoryPoints`、横幅 `PerformanceView.statusBanners`），
    并由 `PerformanceMemoryHonestyTests` 的 `testFailedVmReadProducesUnknownPressure` 与
    `testUnknownIsTheOnlyWayToReachTheUnknownCase` 两条用例钉住。早期版本"一次内核调用失败被画成内存
    100% 占满"的缺陷（WS-D P1 #10）已修；残留问题是模型字段仍非可选、失败时落回 0
    （`SystemSampler.swift` 的 `SystemSampler.snapshot` 自陈，`:95-99`），靠视图层兜住。

### 3.7 错误日志

- **给我看什么**：四个计数磁贴「今日错误 / 异常 / 崩溃 / 警告」（`LogsMetricGrid.body`）、
  错误趋势、「高频错误」聚类列表（卡标题 `LogsErrorClusters.LogsErrorClustersCard.body`，
  副标题「共 N 类签名 · 按出现次数排序」（`LogsErrorClusters.LogsErrorClustersCard.subtitle`；这一页以前叫英文 `Top Errors`，现已收口）、
  受影响源文件（`LogsFileTables.LogsAffectedFilesCard.body`）、已扫描文件清单（`LogsScannedFilesCard.body`）。
- **数字怎么算**：解析三类来源——项目内递归找 `.log` / `.out` / `.ips`（`Logs/` 目录下额外接受 `txt`、`err`、
  `trace`、`logrotate` 与无后缀文件，见 `LogDiscovery.swift` 的 `LogDiscovery.isLogFile`）、
  `~/Library/Logs/<项目名>/*.log`（同文件的 `LogDiscovery.libraryLogCandidates`）、
  `~/Library/Logs/DiagnosticReports/*.ips` 且**只认文件名主名等于项目名**的那些
  （`LogDiscovery.diagnosticReportCandidates` 与 `LogDiscovery.isOwnDiagnosticReport`）。
  也可以手动附加：工具栏「附加日志」与「清空附加」都在 `LogsView.swift` 的 `LogsView.controls` 里，
  点开的是系统文件选择器（`LogsView.chooseLogFiles`，提示语就是「附加」两个字），挑的是 `error.log`、
  `crash.log` 一类后缀。每条高频错误展示 级别徽标 + 签名 + 次数 + 原文 + 「第一次 … · 最近 …」
  （`LogsErrorClusters.LogErrorClusterRow.body`），可展开「样例与堆栈」——三处上限都写在同一个
  `LogsErrorClusters.swift` 里：样例行最多 5 条（`:113-114`）、堆栈顶帧最多 6 帧（`:130-131`）、
  来源文件一行（`:144`）。「今日错误」取的是与当天同一个趋势桶的 错误+异常+崩溃 之和
  （`LogInsights.swift` 的 `LogSummary.todayErrorCount`）。
- **什么时候会不准**：
  - 工具栏「时间窗口」（最近 1/3/7/14/30 天，默认 7 天，`LogsView.header`、`AppState.swift` 的
    `AppState.logWindowDays`）**只真正作用于崩溃报告（`.ips`）的筛选与趋势分桶**
    （`LogDiscovery.diagnosticReportCandidates` 的 cutoff 与 `FileLogAnalyzer.swift` 的 `FileLogAnalyzer.analyze`）。
    项目内的日志文件不按窗口过滤，所以「异常 N」可能覆盖全部历史。切换窗口会自动重新分析（悬停说明 `LogsView.header`）。
  - **没有日志数据时四个磁贴一律显示 `--`，不是 0**（`LogsMetricGrid.swift` 的 `LogsMetricGrid.LogReading.count`，
    副标题「…下方数值一律 --」`:68-69`；「尚未分析」与「未发现日志文件」是两种不同小注 `:20-21`）。
  - 读取有上限：单文件 20,000,000 字节 / 50,000 行、最多发现 60 个文件、
    高频错误取 20 类（`FileLogAnalyzer.swift` 的 `maxBytesPerFile`…`topErrorLimit` 四个常量）；
    已扫描文件表最多列 40 行（`LogsScannedFilesCard.rowLimit`），受影响源文件只列前 10 项（`LogsAffectedFilesCard.itemLimit`）。
  - 日志格式千奇百怪，签名聚类靠规则，同一问题的不同写法可能被拆成两类。

### 3.8 依赖分析

- **给我看什么**：页面上方第一张卡是「分析选项」（联网开关 + 「重新分析」，
  `DependenciesView.body`）；
  然后是四枚读数「依赖总数 / 运行时 · 开发 / 版本过旧 / 漏洞数」
  （`DependenciesView.DependencySummaryGrid.body`）、
  「风险总览」（`DependenciesView.DependencyOverviewSection.body`）、按生态分组的依赖表、
  「安全公告」（`DependenciesView.DependencyAdvisoriesSection.body`）。
  每行依赖右侧有五种状态之一：
  **「有漏洞」「过旧」「正常」「仅版本比对」「未核对」**
  （`DependencyVerdictRows.DependencyRowStatus.text`）。
- **数字怎么算**：
  - 支持的清单文件共 16 个文件名：`package.json`、`pom.xml`、`build.gradle`、`build.gradle.kts`、
    `settings.gradle`、`settings.gradle.kts`、`Package.swift`、`requirements.txt`、`pyproject.toml`、
    `setup.py`、`Pipfile`、`go.mod`、`Cargo.toml`、`Podfile`、`Gemfile`、`packages.config`
    （`ManifestParsers.swift` 的 `ManifestFileName.table`；`requirements*.txt` 变体按 Python 处理，
    规则在同一个文件的 `ManifestFileName.ecosystem`）。
    扫描深度不超过 6 层、不跟随符号链接、Maven 多模块最多展开 200 个
    （`ManifestDependencyAnalyzer.swift` 的 `defaultMaxDepth`、`maxMavenModuleExpansions`，
    符号链接那一跳在 `ManifestDependencyAnalyzer.discoverManifests`）。
  - **依赖总数只算清单里直接声明的**，不含锁文件解析出的传递依赖
    （界面原话 `DependenciesView.DependencySummaryGrid.body`），锁文件只在旁边标注
    「只说明可复现，未计入依赖数」（`DependencyEcosystemSection.body`）。
  - 每个生态默认只显示 40 行，其余收进「展开其余 N 项」（`DependencyEcosystemSection.rowLimit`）。
- **什么时候会不准**：**这一页是「没查 ≠ 安全」最容易翻车的地方，必读第 4.1 节。**
  另外版本新旧判定依赖内置版本快照，快照没收录的包返回「未核对」而不是「过旧」
  （`DependencySnapshot.swift` 里 `DependencySnapshot.snapshotDate` 的注释：没把握的包一律不收录，查不到返回 nil）。
- **离线判据现在会自报快照日期**（#25 接线、#35 收掉假精度）：「未核对」磁贴的副标题与
  「联网核对说明」那条提示都会在句尾接上「快照截至 2026-09-19（距今时长）」，
  例如「未联网核对，仅内置快照（覆盖 npm / Maven / Python），快照截至 2026-09-19（昨天）…」。
  这一句只由 `DependencySnapshot.asOfText` 产出一份、两处共用
  （渲染点 `DependencyVerdictRows.DependencySafetyVerdict.summaryCaption`
  与 `ManifestDependencyAnalyzer.offlineCaveat`，后者写进 `DependencyReport.networkLookupNote`
  再由依赖页提示行显示）。**日期只到天**：#35 删掉了旧的 `17:05`，因为那张表只有
  「哪天抄的」这一级依据，分钟是写代码那一下的挂钟（见第 4.1 节末尾）。

### 3.9 健康评分

- **给我看什么**：分数环 + 等级 + 趋势 + 一句结论，旁边一句常驻声明
  「启发式加权计算，未调用外部模型」（常量 `HealthView.HeuristicClaimLine.claim`，
  渲染与悬停说明在同一个 `HeuristicClaimLine.body` 里）；这条声明另在
  `HealthHero.narrativeColumn`、`HealthNotScoredCard`、`HealthNoInputCard` 三处复用；
  「维度分量」表（`HealthComponentTable.body`）；缺失维度披露
  （汇总句 `HealthBreakdown.normalizationSummary`、区块 `HealthComponentTable.missingBlock`）；
  优点 / 问题 / 建议；「评分趋势」（`HealthAdviceCards.HealthTrendCard.body`）。
- **数字怎么算**：综合分 = Σ(维度得分 × 归一化权重)，全部由本机规则从扫描结果算出，
  **不访问网络、不调用任何外部模型**（悬停说明原样是这句，`HealthView.HeuristicClaimLine.body`）。
  九个维度与各自的原始权重（`HealthScore.swift` 的 `HealthDimension` 维度名、`HealthDimension.defaultWeight` 权重）：

  | 维度 | 原始权重 | 维度 | 原始权重 |
  |---|---|---|---|
  | 复杂度 | 0.18 | 提交活跃度 | 0.12 |
  | 运行稳定性 | 0.16 | 依赖健康 | 0.10 |
  | 代码质量 | 0.14 | 测试覆盖 | 0.10 |
  | 重复度 | 0.13 | 注释与可维护性 | 0.08 |
  | 协作分布 | 0.09 | | |

  （模型里的维度名是「重复度」，但**界面上这一行显示成「重复代码率」**——
  视图层做了映射而不动冻结契约，`HealthComponentTable.DimensionDisplay.overrides`。）
  ⚠ 这九个原始权重加起来是 **1.10**，不是 1.0（详见第 4.4 节与第 7 节待确认清单）。
  各维度的打分锚点表在 `ScoreCurves.swift` 的 `HealthCurves`，测试覆盖的分段得分在
  `WeightedHealthScorer.swift` 里 `WeightedHealthScorer.evaluate` 的 `.testing` 分支。
  **「测试覆盖」这一维喂进去的是生产码口径那个数**（#37，见第 4.6 节）：
  评分器读的仍是 `CoverageMetrics.overallLinePercent`，只是这个属性的含义从
  「报告里所有文件」收窄成「仅生产码」，所以同一份报告改口径前后分数会动。
  等级边界：A ≥85、B 70–84、C 55–69、D 40–54、E <40（`Project.swift` 的 `HealthGrade.init`）。
- **什么时候会不准**：分数低不一定是项目差，很可能是**有维度没证据可计分**（第 4.4 节）。
  「运行稳定性」在**一行日志都没扫到**时已经**不再计分**（缺陷 #46 改掉了旧的"按默认值 85 计入"）：
  `WeightedHealthScorer.evaluate` 的 `.stability` 分支先判 `logs.totalLinesScanned == 0`，命中就整维缺席、
  权重等比摊给在场维度，只留一条建议「没有可扫描的日志，运行稳定性不参与本次评分…」。
  全部维度都缺证据时**直接不给分**：页面写「本次没有任何维度输入，因此不给综合分。」并解释为什么
  （`HealthView.HealthNoInputCard.body`），不画 0 分环；从没分析过则是「尚未计算，不给分也不着色」
  （`HealthView.HealthNotScoredCard.body`）。「评分趋势」少于两个点时不画线，
  提示「至少完成两次分析后可以看到趋势。少于两个点时这里不画线。」（`HealthAdviceCards.HealthTrendCard.body`）。

## 4. 数据口径（看到数字前先读这节）

README 的「数据口径」一节已列了骨架，这里补齐**为什么**和**界面上具体长什么样**。

### 4.1 「0 个漏洞」有三种含义

判定逻辑在 `DependencyVerdictRows.DependencySafetyVerdict`：先看命中数，再看**是否真的做过比对**
（字段是 `DependencyReport.hasVulnerabilityCoverage`）。三种情形：

| 情形 | 界面上的说法 | 你该怎么读 |
|---|---|---|
| 有命中 | 「命中 N 条内置快照与安全公告」 | 真有问题，按公告升级 |
| 做过比对、零命中 | 「全部 N 项已比对，未发现已知漏洞」或「X / Y 项已比对，未发现已知漏洞」 | 这才是「干净」这个结论 |
| 没联网也没拿到任何在线公告 | 「未联网核对，仅内置快照（覆盖 npm / Maven / Python），快照截至 2026-09-19（昨天）· X / Y 项有版本数据」，可能还带「未覆盖生态：…」 | **未判定，不是安全** |

只有第二种允许出现绿色「安全」类结论（代码里那个唯一判据叫 `mayClaimSafe`，
`DependencyVerdictRows.DependencySafetyVerdict`）。漏洞数读数的后缀也会随之变成
「条已核对」或「条（未核对）」（`DependenciesView.DependencyOverviewSection.body`）。
未核对徽标悬停原文：「默认不联网时漏洞判定恒为 0 条，这是「没有查」，不是「没有病」。」
（`DependencyVerdictRows.SafetyVerdictBadge.body`）。

**内置离线漏洞规则一共 10 条，只写了 npm（2 条）、Maven（5 条）、Python（3 条）三个生态**
（数组是 `VulnerabilitySource.bundled`，逐条 CVE 编号看每条的 `KnownVulnerability.cveIdentifiers`；
复算：`grep -c '            id: "TCODER-' Sources/TcoderMonitor/Services/Dependencies/VulnerabilitySource.swift` → 10）；
Gradle 与 Maven 坐标互通所以也受益（`DependencySnapshot.lookupScopes`）。
**SwiftPM、CocoaPods、Go、Cargo、RubyGems、NuGet 在离线时没有任何漏洞结论可给**。

再退一步，**在线核对也救不了全部**：OSV 侧只支持 npm / Maven(含 Gradle) / PyPI / Go / crates.io /
RubyGems / NuGet，**SwiftPM 与 CocoaPods 连在线都不查**（`DependencyNetworkLookup.swift` 的
`OsvPackageQuery.osvEcosystem` 对这两个生态返回 nil），界面在这种情况下会直说
「本项目没有可在线查询的生态（SwiftPM / CocoaPods 不在 OSV 覆盖范围内）」——这句话由
`ManifestDependencyAnalyzer.applyNetworkKnowledge` 写进 `DependencyReport.networkLookupNote`。

还有一层：版本号写成 `"*"`、`workspace:*`、分支名、修订号这类**无法比较**的值会被跳过，
不参与比对（离线侧的判据是 `KnownVulnerability.comparableCore`，被跳过的条数由
`ManifestDependencyAnalyzer.offlineCaveat` 数出来并写进提示），
所以「X / Y 项有版本数据」里的 Y−X 就是这部分。

内置快照有截止日期（代码里是 2026-09-19，`DependencySnapshot.snapshotDate`）。
**这个日期现在会直接显示在依赖页上**（#25）：离线判据句与「未核对」磁贴副标题都在句尾接上
「快照截至 2026-09-19（昨天）」，两个渲染点共用同一份文案 `DependencySnapshot.asOfText`，
免得分析器写一遍、视图再写一遍然后各自腐烂。括号里那段是**距今时长**，
由 `LogRecency.describe` 生成，所以它是「昨天 / N 天前 / N 个月前」这类相对说法，会变。

这条为什么值得单独说：**1 天前的快照和 1 年前的快照，以前在界面上长得一模一样**——
「漏洞判定只依据内置快照」这句话不带日期，用户读到「漏洞数 0」时无法判断这个结论有多旧，
而内置快照是写死在代码里的一份静态表，不会自己更新。现在这句话自己交代保鲜期。

日期**只到天**（#35）：旧实现把 `hour = 17` / `minute = 5` 写死在造日期的那一下，
渲染出来是「快照截至 2026-09-19 17:05」，而那张表只有「哪天抄的」这一级依据，
分钟级没有任何出处（那个时刻还是兜底常量的年份写错成 2025 的同一处挂钟），已删。
形状由 `HonestyP1SnapshotDateTests.swift` 钉住：日期段是十个字符的 年-月-日，整句不含时分冒号。
（第 7 节待确认清单里的第 2 条已随之关闭。）

### 4.2 提交总数 ≠ 作者榜求和，这是设计如此

「总提交数」含合并提交，作者榜与增删行用 `--no-merges` 统计。
Git 洞察页顶部有一条常驻口径条把差额讲清（`GitInsightsSections.GitRepositorySourceSection.discoveryDetail`），
三种文案：

- 未打满窗口：「N（含 M 次合并）· 作者与代码行统计基于 K 次非合并提交」
  ——此时差额**全部**是合并提交（`GitHistoryScope.windowLimit`）。
- 打满了窗口：「… 作者与代码行统计只覆盖最近 K 次非合并提交，更早的历史未纳入」
  ——差额 = 合并提交 **+ 没读到的更早历史**，不能全算成合并
  （判据是 `GitHistoryScope.Basis.windowCapped`，那句文案出自 `GitHistoryScope.headline`）。
- 旧报告里没有基准字段：明说「这份报告没有记录非合并提交数，作者与代码行仍按旧口径统计…重新分析后可拆分」
  （判据是 `GitHistoryScope.Basis.unknown`，同一句文案也在 `GitHistoryScope.headline`；
  「口径未知」这四个字是那个 case 的注释用词，不是界面原话）。

### 4.3 大仓库的历史是按窗口分析的

窗口上限 20,000 条非合并提交（`ShellGitAnalyzer.swift` 的 `ShellGitAnalyzer.maxCommits`）。
超限时页面做三件事：磁贴标题改成「窗口跨度」「窗口内作者」（`GitInsightsView.GitInsightsMetricGrid.body`）、
卡标题追加「 · 近 N 次提交窗口内」（`GitHistoryScope.authorTileCaption`）、
口径条用警告色并补一句「趋势、时段分布与作者占比都只是这段窗口的分布，不代表全部历史。」
（`GitInsightsSections.GitCommitScopeSection.body`）。
**注意两个字段不是一回事**：界面判断「是否被窗口截断」用的是派生判据
`GitHistoryScope.isWindowTruncated`（非合并窗口打满才是真），**不是**契约字段
`GitInsights.historyTruncated`——后者按 `已解析条数 < 全量提交数` 赋值，被合并提交污染，
本仓库 2026-09-20 实测 `git rev-list --count HEAD` = 290（含 127 次合并、非合并 163），
远未打满 20,000 的窗口，它照样是真。所以本文按界面行为描述，不按字段名描述。

### 4.4 健康评分：缺证据不给分，权重等比摊分

缺证据的维度直接 `return nil`，**不进分量表、不参与计分、也不得分**
（每个分支开头的 `guard` 就是判据，逐条列在下面那张表里；全部在 `WeightedHealthScorer.swift` 的 `evaluate` 内，`:76,89,119,133,149,158,196,213,217,242,251,254,272`）。
然后评分器把分量表的权重**除以在场权重之和**归一到 1.0，使界面顶部那句「综合分 = Σ(得分 × 归一化权重)」
（`HealthComponentTable.body` 的卡副标题）能复现综合分（归一在 `WeightedHealthScorer.score` 的 `:45-48`，紧接 `guard totalWeight > 0`）。
界面那句话说什么由 `HealthBreakdown.normalizationSummary` 分三种情况决定（`HealthComponentTable.swift`）：

- 有维度缺席：「缺失 N 个维度不参与计分、也不按 0 计入，其份额已按在场维度等比摊入。」+ 明细
  （明细由 `HealthBreakdown.shiftNotes` 生成）；
- 无缺席、且权重表合计就是 100%：「…没有维度缺席；权重未做摊分，乘数即表内原始值。」；
- **无缺席、但权重表合计不是 100%**（本 App 就是这种，合计 110%）：
  「…但内置权重表合计 110%，评分器发布前已整体折算，故各乘数不等于表内原始值。」

哪些情况会让维度缺席（这一条直接决定你的分数）：

| 维度 | 计分的最低证据 | 出处（`WeightedHealthScorer.swift` 的 `evaluate`） |
|---|---|---|
| 复杂度 | 代码扫描有结果，且测到全仓均值或非空热点榜 | `.complexity` 分支两道 `guard` `:76,89` |
| 重复代码率 | 代码扫描有结果且有效码行 >0 | `.duplication` 分支 `:119` |
| 代码质量 | 文件数 >0 | `.codeQuality` 分支 `:133` |
| 注释与可维护性 | 总行数 >0 | `.documentation` 分支 `:149` |
| 提交活跃度 | 有 Git 数据且提交数 >0 | `.activity` 分支 `:158` |
| 协作分布 | 上一条之外还要求有榜首作者 | `.busFactor` 分支 `:196` |
| 运行稳定性 | `inputs.logs` 在场**且**真扫到日志（`totalLinesScanned > 0`）；零日志时整维缺席、只留一条建议（#46） | `.stability` 分支 `:213,217` |
| 依赖健康 | 依赖数 >0 **且漏洞核对状态为已核对**；未核对或查询失败整维缺席 | `.dependencies` 分支 `:242,251,254`、`VulnerabilityEvidence.classify` |
| 测试覆盖 | 仓库真的产出了覆盖率报告且有**生产码**行分母（#37：`CoverageMetrics.overallLinePercent` 只算 `CoverageScope.isProductionSource` 为真的记录，见第 4.6 节） | `.testing` 分支 `:272-273`、`CoverageMetrics.hasData` |

两个容易忽略的后果：

1. 「依赖健康」默认离线时**必然缺席**（未核对 → 不计分），所以离线扫描的综合分
   不含这一维度，权重被摊到别的维度上（提示文案「未做在线漏洞核对，依赖健康本维度暂不计分；
   开启「联网核对」后重扫才有结论。」，`WeightedHealthScorer.swift` 的 `evaluate` 里 `.dependencies` 分支）。
2. 「未调用外部模型」这句声明**只限评分本身**，不代表整个 App 不联网——
   依赖页的在线核对是真会发请求的（第 5 节）。

### 4.5 内存口径

已用内存 = 总量 −（free + speculative + purgeable），**与活动监视器一致**；
inactive（文件缓存）**仍算已用**，所以这个数会比你以为的「真实占用」大
（`Services/Performance/SystemSampler.swift` 的 `VmCounters.reclaimableBytes` 是可回收量、`:155-156` 是口径注释、
`SystemSampler.memoryUsedBytes` 是实现 `:160-168`，注释明说 inactive 是文件缓存但监视器仍计入已用）。
页大小取 `vm_kernel_page_size`，Apple Silicon 上是 16 KB（`:253`，注释 `:248`）。
瞬时不一致有兜底：若可回收量算出来不小于总量，退化为 `active + wired + compressed`（`:163-165`）。
**取数失败时不再冒充满负荷**：早期版本 `host_statistics64` 一失败页计数全为 0，
会把内存画成接近 100% 占满（《20 WS-D 诚实性审计》P1 #10）；现在失败路径返回 nil、
界面显示 `--` 并声明被剔除的点数（`SystemSampler.vmCounters` 与 `SystemSampler.memoryUsedBytes` 的可选返回、
`LiveReadings.memoryUsedBytes` 与 `memoryGapReason`）。
换句话说：**再看到内存瞬间打满且曲线是一条竖线，那就是真的打满**。

### 4.6 覆盖率只读现成报告，不代跑测试

「覆盖率」这一页/这块**不会执行你的测试**：分析器只做「解析已存在的报告文件」，
`CoverageAnalyzer.swift` 顶部注释原话是 "Nothing here runs a test suite — it only parses existing
reports"——**那是代码注释，界面上不显示**。全仓唯一的子进程调用是 `git`（`SharedUtilities.swift`
的 `Shell.blockingRun`，调用方只有 `ShellGitAnalyzer.swift` 的 `ShellGitAnalyzer.run`），没有任何跑测试的路径。

- 认得五种报告（文件名白名单 `CoverageAnalyzer.wantedNames`，按名分派在 `CoverageAnalyzer.parse`）：
  `lcov.info` / `lcov.dat`、`coverage-summary.json`（istanbul / nyc）、`jacoco.xml` / `jacocoTestReport.xml`、
  `coverage.xml`（coverage.py）、`clover.xml`。
- 发现限制：深度 ≤6、最多 40 个文件、单文件 ≤20,000,000 字节（`CoverageAnalyzer.swift` 的
  `discoverReportFiles` 与 `CoverageAnalyzer.maxReportBytes`）。
- **聚合只取分母最大的 6 份**报告（`CoverageAnalyzer.rank` 里那句 `prefix(6)`）。多模块仓库里
  「整体行覆盖」实际是这 6 份的合计，不是全项目。
- **没有报告时这块整块不出现**，不是空态卡、更不是 0%：`DashboardView.swift` 的 `DashboardView.coverageStrip`
  外面就是一层 `coverage.hasData` 判断，为假时连分隔线都不画——README「数据口径」同一条。代码注释里那句
  「测试覆盖率只在仓库真出了报告时才出现，没报告就不画，避免读成一个假的 0%」写的是这个意图，**界面上不会显示它**。
  这条口径由 `RealRepositoryEvidenceTests.swift` 钉住（见 README「验收脚手架」）。

**主读数是「仅生产码」口径，全量口径降级为次要读数（#37）。**
覆盖率那块上最醒目的读数「生产码行覆盖」（`CoverageMetrics.overallLinePercent`）只把生产码算进分母，
四条排除规则任一命中即不算生产码（`CoverageScope.isProductionSource`，四个标记各是一个常量）：
路径含 `/Tests/`、含 `PackageTests`、含 `/.build/`、文件名以「Tests.swift」结尾。
口径本身写在读数旁边（`DashboardView.coverageCaliberLine`），原话是
「口径：仅生产码（已排除 Tests/、PackageTests、.build、*Tests.swift），含测试代码 64.2%（不用于评分） · 差 17.3% 来自测试代码」。

- **为什么要换口径**：测试代码天然接近满覆盖，把它留在分母里等于给健康分留一个
  「不必改善生产码也能涨」的增长项。这不是推演——本仓库实测测试码占全量分母 **43.83%**、
  自身覆盖 **86.38%**；同一套统计在 `ee8e7b9` 是全口径 64.00%，期间**一行生产码都没改**、
  只往 `Tests/` 加了 140 行测试，就自己涨到 64.19%。这条性质现在由
  `Tests/TcoderMonitorTests/CoverageProductionScopeTests.swift` 钉住。
- **本仓库的实测两个数**（`1e6319d` 上测，README「数据口径」是同一份证据；分母是本次 lcov 的 163 条记录）：
  全口径 **64.19%**（27047/42137），仅生产码 **46.85%**（11080/23651）。界面各带一位小数（46.9% / 64.2%）。
- **全量口径没有丢**：它降级成次要读数，仍读得到（`CoverageMetrics.allSourcesLinePercent`），
  但明确标注「不用于评分」——只把高的那个摆出来是不诚实的。两份数字差不足 0.05 个百分点时，
  那句话改说「与含测试代码的口径一致」。
- **对本仓库的端到端后果（要认账）**：同一份真 lcov、只换口径，测试覆盖分量 **78 → 62 分**，
  **总分 73 → 72**。分数变低是这次修改预期的、正确的结果，不是回归；README「数据口径」记了同一条。
- **报告没有源文件粒度时不假装区分过**：五种格式里只有 lcov 带 `SF:` 逐文件记录，
  所以只有它能真的把测试码从分母里剔出去（`CoverageAnalyzer.parseLCov`）；其余四种标成
  `CoverageReport.ScopeGranularity.aggregateOnly`，此时界面明说
  「口径：报告只有汇总粒度，未区分测试代码」，而不是让一个没区分过的数字顶着「生产码」的标签
  （`DashboardView.coverageCaliberLine` 的兜底分支；能不能区分看 `CoverageMetrics.scopeIsSeparated`）。

**读数旁边会报「这些数是多旧的」（#38）。**
覆盖率产物是仓库自己生成的本地文件——被 `.gitignore` 挡着、没有 git 历史，
所以**一份几天前的 lcov 与刚刚跑出来的那份在界面上原来长得一模一样**，
陈旧数据可以长期冒充新鲜结论灌进健康评分。现在读数下方多一行小字说清年龄：

- 生成时间取自**报告文件自身的 mtime**，在五种格式共同的解析出口补一次
  （`CoverageAnalyzer.fill`），读不到就留空；**绝不允许拿本次分析时刻顶替**，
  那等于把陈旧报告洗成新数据。
- 加权读数是把几份报告合起来算的，所以它的新鲜度只能等于**最陈旧那份**：
  那句按最旧的说（`CoverageMetrics.generationSummaryText`），
  形状是「最旧报告生成于 2026-09-19 22:41（1 天前）」，精确到分钟（这次是文件系统真实记录的）。
  说成「最新的那份」就是拿好消息骗人。
- 取不到时间的报告**单独计数**、失败面往大报（「另 N 份无生成时间」），
  多份时还会补「共 N 份」，免得读者以为那是一个数。
  **注意**：那句「共 N 份」说的是**入选**的那几份——聚合本来就只取分母最大的 6 份
  （`CoverageAnalyzer.rank`），它不等于「仓库里找到几份」（见第 7 节第 7 条）。
- **整批都没有时间时显示「报告为未知生成时间（不按新鲜数据计）」，而不是不显示**
  （单份的说法在 `CoverageReport.generationText`）；一份报告都没有时整句不出现，不编造。

## 5. 隐私

1. **全部分析在本机完成，不上传任何源码内容**（README「数据与隐私」）。
2. **在线查询默认关闭**，需要手动开：开关在「依赖分析」页第一张卡「分析选项」里，
   标题「分析时联网查询最新版本与漏洞库」（默认值 `false` 是 `AppState.allowNetworkLookups`；
   界面 `DependenciesView.NetworkOptionsCard.body`）。
   开启后**不会立刻生效**，页面就写着「开启后需要重新执行分析才会生效。」
   （`DependenciesView.NetworkOptionsCard.statusCaption`），
   必须再点一次「重新分析」。
3. **会连哪些地址**：只有 npm registry 与 OSV.dev，两个域名写死在
   `DependencyNetworkLookup.osvHost` 与 `npmRegistryHost`；会话是临时的、不带 cookie 也不落缓存
   （`DependencyNetworkLookup.swift` 的 `session`，`:337,341,343`）。npm 侧是 GET；
   **OSV 的批量查询接口是 POST**，请求体里只有包名与版本这一类查询条件
   （`OsvClient.swift` 的 `DependencyNetworkLookup.osvQueryBatch`，逐包回退 `osvQuerySingle` 同样是 POST）。
   换句话说：只读语义，但不是「只发 GET」。
4. **超时**：单次请求硬超时 5 秒（`DependencyNetworkLookup.requestTimeout`，npm 与 OSV 共用这一个常量）。
   但 npm 与 OSV 是**串行**发起的（先 `await` npm 再 `await` OSV，
   `ManifestDependencyAnalyzer.applyNetworkKnowledge`），所以整个在线阶段最长接近 10 秒而不是 5 秒
   （README「数据与隐私」实测值：黑洞地址下两边各 5.006s）。
   超时/失败会降级为内置离线快照并在页面写明，例如
   「OSV 查询超过 5 秒硬超时，本次在线漏洞结果整体放弃（含已取回但未来得及返回的公告）」
   （`DependencyNetworkLookup.osvBatch` 的 `.timedOut` 分支）、「达到时间预算，剩余 N 个包未查询」
   （`NpmClient.swift` 的 `DependencyNetworkLookup.performNpmLookup`）。
5. **进程监控只读**：不向任何进程发信号、不 kill、不重启、不附加调试器
   （纪律注释写在 `ProcessInspector.swift` 顶部的文件注释里；界面声明
   `PerformanceProcessTable.PerformanceProcessTableCard.coverageNote`「只读展示，不提供任何进程操作」——
   这是拿不到进程计数时的兜底分支，注意 `ProcessSortKey.title` 返回的是两个**排序列名**、不是这句话、
   `PerformanceMatcherEditor.body`「只读观测，不干预任何进程」、
   `PerformanceProcessGroups.PerformanceGroupCard.header`「只删规则，不干预任何进程」）。
   用到的只有 `sysctl` / `proc_listallpids` / `proc_pidinfo` / `proc_pidpath` / `proc_pid_rusage`
   这几类查询接口（调用点是 `ProcessInspector.processCount`、`listAllPids`、`bsdInfo`、`taskInfo`、
   `openFileCount`、`executablePath`、`rusageInfo`）。
   仓库里唯一的 `terminate()` 是给**自己起的 git 子进程**做超时收尾的
   （`SharedUtilities.swift` 的 `Shell.blockingRun`，调用方只有 `ShellGitAnalyzer.run`），与外部进程无关。
6. **本 App 没有 macOS 沙盒**（第 2.1 节），意味着它能读到你选中的目录树里的东西——
   所以**只添加你打算被扫描的目录**。

## 6. 常见问题

**Q：我的健康分比预期低，是不是项目真这么差？**
先看「维度分量」表和缺失维度那一句。缺证据的维度**不给分也不白送分**，
它的权重会被摊到别的维度上（第 4.4 节）。常见拉分点：没跑过覆盖率（「测试覆盖」缺席）、
没开联网核对（「依赖健康」缺席）、一行日志都没扫到（「运行稳定性」缺席，#46）、非 Git 目录（两个 Git 维度缺席）。
这些情况下你的分数不是"项目得分"，而是"在场指标的得分"。

**Q：依赖页为什么全是「未核对」？**
两种原因：①没开联网开关（默认关，`AppState.allowNetworkLookups`），或开了但没重新分析
（「开启后需要重新执行分析才会生效。」，`DependenciesView.NetworkOptionsCard.statusCaption`）；
②该生态没有内置规则——离线只有 npm / Maven / Python 共 10 条
（`VulnerabilitySource.swift` 的 `VulnerabilitySource.bundled`），SwiftPM 与 CocoaPods **连在线都不查**
（`OsvPackageQuery.osvEcosystem` 对它们返回 nil）。这是"没查"，不是"安全"。

**Q：第一次扫描很慢？**
正常。代码扫描要遍历目录树（上限 60,000 文件，`ScanOptions.maxFiles`）、
Git 要读最多 20,000 条提交的历史（`ShellGitAnalyzer.maxCommits`）、日志要扫最多 60 个文件
（`FileLogAnalyzer.maxDiscoveredFiles`），而这些阶段是**串行**跑的
（阶段文案在 `SharedComponents.swift` 的 `AnalysisPhase.label`）。
开了联网再叠最长约 10 秒（第 5 节第 4 条）。

**Q：「总提交数」和贡献者页的提交加起来对不上？**
不是 bug，差额就是合并提交（或更早的未读历史），Git 页顶部的「提交统计口径」条会直接告诉你
差额是多少、以及作者榜是基于多少个非合并提交算的（第 4.2 节）。

**Q：Git 页突然变成「尚未分析 Git 历史」，之前的数据没了？**
最可能是那次 `git log` 撞上 60 秒超时（`ShellGitAnalyzer.swift` 的 `ShellGitAnalyzer.init` 参数 `logTimeout`）。
本轮失败时上一轮的 Git 结果**不会被保留**（`AppState.scan` 每次新建报告），
页面会退回未分析空态（`GitInsightsSections.GitDataAbsence.emptyState`），总览页同时给一条
「未能完成：Git 分析」并可点重试（`DashboardView.failureCard`）。
大仓库建议接上电源后重试；**这一条是已知缺陷，不是你的操作问题**（见第 7 节）。

**Q：数据存在哪里？怎么清空？**
`~/Library/Application Support/TcoderMonitor/`（拼这段路径的是 `ProjectStore.resolveStorageDirectory`），
删掉这个目录即全清；只想撤一个项目就用侧栏右键「移除」（`ProjectSidebar.rowContextMenu`）。

**Q：为什么性能页的内存比 `top` 显示的大？**
口径不同但和活动监视器一致：文件缓存的 inactive 页也算已用（第 4.5 节）。

**Q：示例项目的分数能拿去汇报吗？**
不能。那是 `DemoData.swift` 里写死的样例数字（第 1 节），
而且示例项目**点「重新分析」是无效的**（「示例项目已内置数据，无需扫描。」，
`AppState.scan` 开头遇到示例项目就直接写这句 `lastError` 返回）。
