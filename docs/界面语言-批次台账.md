**这张表原来自于一把太松的尺子，现在按同一把严尺子重测过了**（划线数字是当时记的）：

B 类还要先登记键，报成 A 会让人以为那 14 句随手就能清完。

三批（`en-before` / `en` / 见 §6.17 的 `en-p16`）都用收紧后的同一把尺子重测，
所以三列可比。含中文总次数 410 / 232 不受分类器影响（那是数片段的，不数类别）。

根因是 `.help(_:)` 收成品 String、**自己不查目录**，而 tooltip 那三把尺子只数槽位与
长句数，没一把问"这句话查没查表"；A 类里那些句子**早就登记在目录里**，只是没人去查
（「键存在 ≠ 查得中」在英文态直接可见）。这一笔把 16 处视图层裸中文 `.help(` 包进查表、
补 7 条英文键，并立 `TooltipLocalizationGuardTests`（零容忍 + 三条元测试）防退化。

**边界要说白，别让人以为英文态收口了**：按双语守卫自己的口径数，视图层未包查表的
中文字面量还有 **750 处 / 44 个文件**（最大几份：`GitInsightsSections` 52、

### §6.20 把"文档引用的守卫"真的接上判活：一次自毒

§6 第 8 条那条盲区本轮补掉了，过程里撞到一个值得记的坑。

**盲区形状**：`DocReferenceRatchetTests` 的符号索引原先只吃 `TcoderMonitor/Sources/**`，
而锚点正则要求**至少一个点**。于是文档里引用一条测试名，
写「BorderlessDetailGuardTests.test_某条」这种三段式判"找不到"（红），写裸名「test_某条」则**压根不成锚**（不校验）。
两种写法都不能"被盯"—— 前几轮我在文档里点名的守卫，改名或删掉都不会让门禁红。

**补法**：加第二份索引 `Tests/**`，判活取两侧并集；再把扫描面内的 5 条裸名
升级成 `类.用例` 三段式（现在它们真的被盯着）。元测试两条一起上：
Tests 侧的名字必须判活，**两边都没有的名字必须仍然判死** —— 只写前一条等于把判据关掉。

**自毒（这节存在的理由）**：第一版按"全标识符"扫 `Tests/**`，
`testEndToEndCanaryAgainstTheRealIndex` 里那条金丝雀 「WsvCanaryDeadType.someMember」
当场**被判活** —— 那个假名字只是字符串字面量，却躺在测试文件里，被自己的索引收了进去。
⇒ 判活的集合一旦包含"哪里提到过这个名字"，金丝雀就再也测不出判据失效。
改成**只收声明**（`func test…` 与类型名）后金丝雀恢复判红。
这条与 §6.13（读数器按行吃多行载荷）、§6.19（探针阈值看不见灰字）同族：
**尺子的输入面一旦比它的判据宽，它就开始给自己发绿条。**

补完当天它就咬了两次：本节初稿里当示例写的两个假名（金丝雀那一个、以及一个
「test_某条」形状的占位名）都被判成死引用、门禁当场红。
⇒ 从今往后**文档里写的名字真的有人在看**；示例性/假设性的点号名一律写「」，反引号只留给真锚点。

**没补的两小截**（写在 §6 第 8 条里，不藏）：校验器只读 6 份文档，
`功能真实性清单` / `中英双语方案` / `界面乱点清单与修复进度` 里的测试名仍不被校验；
其中 `test_shadowOnlyInsideFloatingBranch` 在 `Tests/**` 已找不到同名用例 —— 是真 rot，只是没人看见。

### §6.24 批次 `page_edges` 两态通用：把"深色那一半没有边距判据"这个洞补掉

验收口径写的是"**深浅两态**九页全部实拍复核通过"，而边距这把尺子只量浅色 ——
也就是说这句话里深色那一半，**在边距这个量上从来没有判据**，只有均亮/暗像素占比那组读数。
这不是"深色量出来没问题"，是"深色没量过"。

**为什么旧版只认绝对阈值 ≥252**：浅色画布 247、卡面 254，差 7 阶；深色画布 19、卡面 37，差 18 阶。
两态**都是卡面比画布亮**，所以一条 `luma ≥ 画布 + 5` 同时覆盖两侧，浅色侧还恰好等价于旧的那条。
基准从"猜"改成"量"：取**侧栏与内容列之间那道缝**（实测 x 21.8%–23.2% 九页两态恒为画布）的众数，
邻域占比不足 85% 就**拒绝出数**。

翻过两次车，都写进脚本注释（不写就等于留给下一个人再翻一次）：
- 先按"内容列里两个主峰取较暗者"定基准 ⇒ **健康评分顶拍那张大环形卡铺满内容列**，
  采样带里剩不下第二个峰，于是一把已经量过 18 张浅色图的尺子当场退化成"读不出数"。
  换判据就是换尺子，旧夹具全绿不代表新尺子在现场还灵。
- 再按**单值**占比要 80% ⇒ 浅色全灭。实测那条缝是 247±3 阶的抖动
  （247 只占 62%，加上 244/245/246 才 97%）。改成**邻域合起来算**，而不是把阈值调低 ——
  调低会让"半条缝其实是侧栏"这种真的混采也放行。
- 深色侧还有一处旧账：贴左缘的**侧栏比画布亮**（实测 30 阶 vs 19），
  不排掉它，卡缝那一行的"最宽带"就是侧栏（旧版"逐行取众数"量出 8–280 正是这个形状）。
  现在起点正好落在扫描下界上的带子一律不算自然边缘。

**正对照**（`selfcheck`）从两张变四张：浅/深两态各一组已知边距（304 与 320），
深色那组**带一条贴左缘、比画布亮的侧栏**，专门复现上面那个坑；
另加一条**负对照**：整幅同亮度时必须拒绝出数（拿不到基准就猜一个继续量，是最坏的形状）。
现量结果：**36 张全部出数**，浅色左 304 / 右 1255，深色左 304 / 右 1256
（1pt 差是阈值取整，不是错位），`总览` 页尾右边缘 767/768 仍是底部双列栅格左列的边。

**这条尺子的边界要说清**：它量的是"两态各自内部齐不齐"，**不是"深色取值对不对"** ——
深色配色仍是推导值（乱清单 §6 第 1 条，没有 AiX 深色参考图可对）。

### §6.30 一次"门禁红了"的归因：真值必须和被测数据同快照（不是放宽容差）

`1171 / 0 失败` 之后 12 分钟，同一批代码重跑门禁红了 3 条，全在自扫描那一路：
`totalCommits` 报 **985** 而 `git rev-list --count HEAD` 读到 **1059**、
`commitsAnalyzed` 680 vs 735、作者集中度 0.7794 vs 0.7959。

**先证机制再动手**（三个候选，两个被证据排除）：
① 分析器窗口上限？排除——`ShellGitAnalyzer.maxCommits = 20_000`，1059 远没到；
② 报告是缓存的旧文件？排除——`selfScan()` 是**现扫**，只是进程内缓存一次；
③ **取数时刻不同**：成立。`reflog` 里 `766e497 → 985` 证明"985"是那次运行期间
   真实存在过的 HEAD；随后 `merge ws/perf-base` 一次带进 74 个提交（现在 1059）。
   也就是说：**扫描在 t0 取了快照，断言在 t1 才现取真值，而 t0→t1 之间别的流往共享主树合了一笔。**
   同一份代码在树安静时重跑 → 1171/0。

**修法不是把 5 个点容差放宽**（那是把尺子锯短），而是让真值**进同一份快照**：
快照结构体 `SelfScan` 里新增的那一格 git 真值，在 `make()` 中紧贴 git 分析取一次
（`all` / `nonMerge` / `merges` / `topShare`），六条断言一律改读它。
顺带把 `revListCount` / `independentTopAuthorShare` 改成 static 并由快照复用
——**不复制第二份 Process 实现**，也不留无调用方的死代码。
`git` 取数从此全仓只有测试基座 `SelfScanHarness` 的那个静态取数出口一处（实例方法 `runGit` 只是它的转发）。

**这条对验收口径的意义**：「全量门禁 0 失败」这句话**必须连着"在哪棵树上、树静不静"一起读**。
主树是共享集成树，跑一轮 test 要 3~5 分钟，期间任何一次 merge 都会让"现取真值"类断言漂红。
以后我报门禁数字，会同时给 `git log -1` 与"跑完再量一次 rev-list 是否等于跑时读数"。
